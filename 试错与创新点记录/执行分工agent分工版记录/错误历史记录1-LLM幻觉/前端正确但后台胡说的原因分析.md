# 前端正确但后台胡说的原因分析

## 1. 现象概述

本次使用 `run_web.bat` 启动 Web 服务后，前端页面保存记录：

```text
E:\SWMM_Agentic\SWMM-Agentic\试错与创新点记录\错误历史记录1\SWMM-2D-Agentic ChatHistory1.html
```

显示结果是正确的。用户请求：

```text
请列出 models 下的模型项目，并检查它们是否完整。
```

前端最终返回了 `songhua_swmm_2d` 的完整性检查 JSON：

```json
{
  "model_name": "songhua_swmm_2d",
  "ready": true,
  "problems": [],
  "baseline_inp": "E:\\SWMM_Agentic\\SWMM-Agentic\\models\\songhua_swmm_2d\\swmm\\scenarios\\baseline\\model.inp",
  "static_model": {
    "ok": true,
    "grid_shape": [552, 633],
    "cell_size": 15.0,
    "mapped_nodes": 10040,
    "flow_cells": 88647
  }
}
```

但是后台截图：

```text
E:\SWMM_Agentic\SWMM-Agentic\试错与创新点记录\错误历史记录1\c45163dd98b8e1b3fc080be08628445a.png
```

显示控制台里又出现了大量与 SWMM-2D 无关的内容，例如“哈希表”“枚举”“两数之和”“LeetCode”等。

这形成了一个表面矛盾：

```text
前端看起来正确
后台却在胡说
```

## 2. 后台实际发生了什么

从截图可以看出，后台并不是一开始就胡说，而是经历了两个阶段。

### 2.1 第一阶段：工具调用成功

后台先收到用户请求：

```text
task: 列出models目录下的所有SWMM-2D模型项目
path of the file:
```

随后 `TaskExecutor` 真实调用了工具：

```text
ToolCallRequestEvent
name='list_swmm_2d_models'
```

工具返回了正确结果：

```json
[
  {
    "model": "songhua_swmm_2d",
    "has_model_yaml": true,
    "static_ready": true,
    "baseline_inp": true
  }
]
```

然后 `TaskExecutor` 也生成了正确的：

```text
Final Answer:
在models目录下发现1个SWMM-2D模型项目：songhua_swmm_2d，
该项目包含model.yaml配置文件，CA2D静态模型已准备就绪，并且有基准SWMM输入文件。
```

所以，本轮任务其实已经有了有效答案。

### 2.2 第二阶段：内部 Agent 没有及时停止

问题出现在正确 `Final Answer` 之后。

后台继续出现多段：

```text
TextMessage (TaskExecutor)
# 1. 两数之和
...
哈希表
...
枚举
...
来源：力扣（LeetCode）
```

这说明内部 `TaskExecutor` 在已经给出正确答案后，没有被立即终止，仍然继续生成了后续文本。后续文本与 SWMM-2D 任务无关，属于 LLM 跑偏输出。

这不是工具执行结果，而是模型文本输出。

## 3. 为什么后台会胡说

后台胡说的直接原因有三个。

### 3.1 Console 会打印内部所有消息

`main.py` 中 `TaskExecutor` 使用了：

```python
stream = team.run_stream(...)
result = await Console(stream)
```

`Console(stream)` 会把内部 agent 的流式事件全部打印到后端控制台，包括：

- ThoughtEvent；
- ToolCallRequestEvent；
- ToolCallExecutionEvent；
- ToolCallSummaryMessage；
- TextMessage；
- 正确 Final Answer；
- 后续跑偏文本。

所以后台截图展示的是“内部全过程日志”，不是最终返回给前端的答案。

### 3.2 TaskExecutor 内部队列仍可能继续生成

`TaskExecutor` 内部是一个小型 `RoundRobinGroupChat`：

```python
team = RoundRobinGroupChat(participants=[task_executor], max_turns=4)
```

如果内部终止条件不够强，或者模型在 `Final Answer` 后没有输出明确终止信号，那么 `max_turns=4` 允许它继续说几轮。

这就解释了为什么截图里会看到：

```text
Final Answer: 正确结果
TextMessage: 两数之和
TextMessage: 两数之和
TextMessage: 两数之和
```

也就是说，系统已经得到正确结果，但后台内部 agent 还在“多说”。

### 3.3 LLM 服务出现了无关内容污染

“两数之和”“哈希表”“枚举”这种内容与当前 SWMM-2D 上下文完全无关。它不是路径错误，也不是 SWMM 工具错误，而是 LLM 文本生成阶段的无关输出。

可能原因包括：

- 模型服务端返回了被污染的通用编程题内容；
- 当前提示词仍允许模型自由生成解释；
- 内部 agent 在工具调用完成后缺少强终止；
- 多轮上下文中存在过往无关输出，被再次激活；
- 工具结果已经足够，但模型仍被要求继续反思或补充。

这类现象可以归类为：

```text
post-tool hallucination
```

即工具调用之后的幻觉输出。

## 4. 为什么前端显示是正确的

前端正确，不是因为后台没有胡说，而是因为 Web 层对最终返回内容做了筛选。

### 4.1 Web API 不直接返回 Console 全量日志

前端请求 `/api/chat` 后，后端执行：

```python
result = await team.run(task=task)
return extract_reply(result.messages)
```

前端收到的是 `extract_reply()` 的输出，不是 `Console(stream)` 打印出来的全部内部日志。

这意味着：

```text
后台日志 = 全部内部过程
前端回复 = 被 extract_reply 筛选后的最终文本
```

两者不是同一个东西。

### 4.2 extract_reply 会优先寻找有效 Final Answer

`web_app.py` 中的 `extract_reply()` 逻辑大致是：

```python
for _source, text in reversed(collected):
    if "Final Answer:" in text and not is_unrelated_reply(text):
        return text.split("Final Answer:", 1)[1].strip()
```

也就是说，只要消息列表中存在一个非无关的 `Final Answer:`，前端就会优先取它。

截图中确实存在正确的：

```text
Final Answer: 在models目录下发现1个SWMM-2D模型项目...
```

所以前端能够拿到正确结果。

### 4.3 extract_reply 会识别并跳过无关回答

`web_app.py` 中还有 `is_unrelated_reply()`，用于识别这类无关内容：

```python
unrelated_markers = [
    "leetcode",
    "两数之和",
    "哈希表",
    "二叉搜索树",
    "监控二叉树",
    "rust的hashmap",
    "TreeNode",
    "class Solution",
    "vector<int>",
]
```

因此，即使后台出现了“哈希表”“两数之和”，前端最终回复时也可能将其判定为无关内容，不作为有效答案返回。

这就是前端看起来正常的关键原因：

```text
正确工具结果存在
+ 前端只抽取有效 Final Answer
+ 无关 LeetCode 内容被识别为无效
= 前端显示正确
```

## 5. 这次现象的本质

这次现象不是“前端和后台谁对谁错”，而是系统存在两个不同层级：

```text
内部执行层：产生完整过程日志，包含工具调用、正确答案和后续跑偏文本
对外展示层：从内部日志中筛选一个最终回复展示给用户
```

所以更准确的判断是：

> 前端正确，是因为展示层有一定的结果筛选和无关回答拦截能力；后台胡说，是因为内部执行层仍然没有做到工具完成后的强终止和日志清洗。

这说明系统已经具备了初步的“输出防线”，但“执行过程防线”还不够。

## 6. 风险分析

虽然这次前端返回正确，但不能因此认为问题已经解决。

主要风险包括：

1. **后台日志污染**

   后台大量无关内容会干扰调试，让人难以判断真实工具执行状态。

2. **有效答案可能被覆盖**

   如果某次无关内容也包含 `Final Answer:`，或者正确答案没有 `Final Answer:`，前端筛选可能失败。

3. **浪费请求时间和 token**

   工具已经完成后，模型继续生成无关内容，会增加延迟和成本。

4. **污染会话上下文**

   如果后台无关内容进入后续 transcript，可能影响下一轮任务。

5. **论文可靠性评价会受影响**

   仅看前端成功率可能高估系统可靠性；必须同时评价内部执行日志中的幻觉率、伪调用率和无效续写率。

## 7. 可归纳的新问题类型

这次问题可以记录为：

```text
有效工具调用后的无关续写
```

英文可写为：

```text
Post-tool irrelevant continuation
```

也可以归入更大的问题族：

```text
Agent execution trace contamination
```

中文可称：

```text
Agent 执行轨迹污染
```

其特点是：

- 工具调用本身可能是正确的；
- 中间已经出现正确结论；
- 但内部 agent 没有停止；
- 后续生成无关内容；
- 前端可能通过筛选隐藏问题；
- 后台日志暴露了执行层不稳定。

## 8. 后续改进方向设想

本记录仅做分析和畅想，不立即实施。

### 8.1 工具成功后强终止

当 `TaskExecutor` 调用确定性工具并得到有效结果后，可以立即返回，不再让 LLM 继续生成多轮文本。

例如：

```text
ToolCallExecutionEvent success -> return tool result -> stop internal team
```

这可以减少 post-tool hallucination。

### 8.2 将 Final Answer 作为终止条件

内部 `TaskExecutor` 可以加入终止规则：

```text
TextMentionTermination("Final Answer:")
```

或者更严格：

```text
只要出现非无关 Final Answer，就结束该 agent loop。
```

### 8.3 区分内部日志和用户可见日志

后台日志可分级：

- `DEBUG`: ThoughtEvent、内部草稿；
- `INFO`: 工具调用和工具结果；
- `WARN`: 伪工具调用、无关回答；
- `FINAL`: 最终返回给前端的内容。

这样后台不会给人一种“系统最终在胡说”的错觉。

### 8.4 对内部日志做污染标记

当检测到：

- `LeetCode`
- `两数之和`
- `哈希表`
- `TreeNode`
- `class Solution`

这类无关文本时，不仅前端跳过，还应在后台标记：

```text
unrelated_internal_message_detected = true
message_discarded = true
```

### 8.5 防止无关内容进入 transcript

如果无关文本只是内部 agent 输出，不应写入用户会话历史。

会话历史应只保存：

- 用户请求；
- 实际执行的工具；
- 工具结果摘要；
- 最终有效答复。

### 8.6 建立执行轨迹审计

每轮任务可以生成结构化审计记录：

```json
{
  "user_request": "请列出 models 下的模型项目，并检查它们是否完整。",
  "valid_tool_calls": ["list_swmm_2d_models"],
  "valid_final_answer_found": true,
  "unrelated_internal_messages": 3,
  "frontend_reply_source": "valid_final_answer",
  "frontend_reply_status": "correct",
  "backend_trace_status": "contaminated"
}
```

这样可以同时解释：

```text
为什么用户看到的是正确结果
为什么后台仍然显示污染内容
```

## 9. 对论文创新点的启发

这次现象可以进一步支撑前面记录的：

```text
模型结构感知工具编排与失败恢复机制
```

同时可以新增一个更细的可靠性问题：

```text
执行轨迹污染控制
```

论文中可以强调：

> 在面向真实水动力模型的 Agent 系统中，可靠性不仅体现在最终回答是否正确，还体现在执行轨迹是否干净、工具调用是否真实发生、错误恢复是否可控、无关生成是否被及时阻断。

可加入评价指标：

- Post-tool hallucination rate；
- Internal trace contamination rate；
- Valid answer extraction accuracy；
- Frontend-backend consistency；
- Unrelated internal message count；
- Effective termination rate after successful tool execution。

## 10. 本次案例结论

本次案例说明：

1. SWMM-2D 模型查询工具实际执行成功。
2. 前端显示正确，是因为 Web 层筛选到了有效 `Final Answer`，并跳过了无关 LeetCode 内容。
3. 后台胡说，是因为内部 `TaskExecutor` 在正确工具结果后没有及时终止，继续产生了无关文本。
4. 这暴露的不是单纯问答幻觉，而是 Agent 执行轨迹污染和 post-tool hallucination。
5. 后续系统应从“只保证前端最终答复正确”升级为“保证内部执行过程也可控、干净、可审计”。

一句话总结：

> 前端正确说明已有结果筛选防线；后台胡说说明执行层还缺少强终止、污染标记和审计机制。
