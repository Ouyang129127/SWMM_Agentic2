本次错误历史位于：

```text

```

相关材料包括：

- `SWMM-2D-Agentic ChatHistory2.html`：前端对话历史；
- `f900892a7ec456358bcae20a1c3ad334.png`：后台控制台截图；

## 2. 问题一：模式化幻觉再次复现

后台截图中再次出现与 SWMM-2D 无关的内容：

```text
# 1. 两数之和
哈希表

```

这与前几次错误中的幻觉内容高度相似，甚至结构和措辞都接近一致。

这进一步支持前面记录的判断：

```text
LLM-Agent 的失败输出不是完全随机噪声，而可能呈现稳定的模式化污染签名。
```

也就是说，当 Agent 执行链松动、工具调用后没有强终止、上下文进入代码任务语境，或者模型服务返回异常内容时，系统并不是随机输出“做蛋糕”“打篮球”“微积分”等主题，而是稳定滑向中文编程题高频模板。

这类问题可归类为：

```text
Patterned contamination signature
Repeated off-domain hallucination
Post-tool hallucination
```

中文可称：

```text
模式化污染签名
重复性离域幻觉
工具调用后幻觉
```

## 3. 问题二：检查结果前后不一致

本次更有价值的问题是：同一个 `songhua_swmm_2d` 项目，几次检查结果不一致。

固定工具此前检查结果显示项目完整：

```json

    "grid_shape": [552, 633],

    "mapped_nodes": 10040,
    "flow_cells": 88647

}
```

但 `model_projects_check.txt` 中却显示：

```text
项目 1: songhua_swmm_2d
状态: 不完整
现有文件:
  ✓ README.md

`model_projects_list.txt` 也显示：

INP文件: 无
包含runs目录: 是
包含outputs目录: 否
```

这些结果与现有 SWMM-2D 项目规范不一致。

## 4. 根因判断：不是模型缺文件，而是检查 schema 漂移

这次“缺文件”并不是模型真实缺项，而是检查脚本采用了错误的项目结构规范。

### 4.1 当前真实项目规范

目前已经确立的 SWMM-2D 项目结构是：

```text
models/<model_name>/
  model.yaml
  raw/
  static/
    config.json
    elevation.npy
    smid_grid.npy
    flow_mask.npy
    building_mask.npy
    resistance.npy
    node_to_cell_mapping.csv
  swmm/
    scenarios/
      baseline/
        model.inp
  mapping/
  events/
  runs/
```

因此：

- SWMM 基线输入文件应位于 `swmm/scenarios/baseline/model.inp`；
- CA2D 的 `config.json` 应位于 `static/config.json`；
- 降雨事件应位于 `events/`；
- 运行结果应位于 `runs/`；
- 项目根目录不要求存在 `data/model.inp`；
- 项目根目录不要求存在 `outputs/`；
- 项目根目录不要求存在 `config.json`。

### 4.2 临时脚本采用了旧式或想象的结构

`model_projects_check.txt` 中使用的检查标准更像旧式 demo 项目结构：

```text
models/<model_name>/
  data/
    model.inp
    rainfall.dat
    topography.tif
  outputs/
  runs/
  config.json
```

这与当前 SWMM-2D 项目结构不同。

因此，它报告缺少：

```text
data/
outputs/
data/model.inp
data/rainfall.dat
data/topography.tif
根目录 config.json
```

并不能说明 `songhua_swmm_2d` 项目真的不完整，只能说明该临时检查脚本使用了错误的 schema。

## 5. 关键概念：结构规范漂移

这个问题可以命名为：

```text
Schema drift in agent-generated validation
```

中文可称：

```text
Agent 生成式检查中的结构规范漂移
```

其含义是：

> 当 Agent 或 CodeRunner 临时生成检查脚本时，如果没有绑定统一的项目规范，就可能把旧目录结构、demo 结构、通用 SWMM 结构或自己猜测的结构混入检查逻辑，导致同一个模型项目在不同轮次中被判定为不同状态。

这不是单纯的 LLM 幻觉，也不是模型数据问题，而是：

```text
验证标准没有唯一真源
```

## 6. 为什么会出现“同样内容，几次检查结果不一致”

原因是不同轮次使用了不同检查路径和不同检查器：

### 6.1 固定工具检查

固定工具 `check_swmm_2d_project()` 使用当前项目规范：

```text
model.yaml
raw/
static/
swmm/scenarios/baseline/model.inp
mapping/
events/
runs/
```

因此得到：

```text
ready = true
problems = []
```

### 6.2 临时生成脚本检查

临时 CodeRunner 脚本可能按旧式结构检查：

```text
data/model.inp
outputs/
根目录 config.json
```

因此得到：

```text
状态: 不完整
缺失: data/, outputs/, data/model.inp, config.json
```

### 6.3 LLM 二次转述

如果 LLM 再对这些脚本结果进行自然语言总结，还可能进一步混入自己的解释，使“缺项”看起来更像真实项目问题。

所以检查结果不一致的根本原因不是文件系统变化，而是：

```text
检查标准变化了
```

## 7. 这是不是“她想象出来的”

可以这样判断：

```text
不是完全凭空想象，但属于错误 schema 下的假缺失。
```

具体来说：

- `data/model.inp` 并不是当前项目规范要求的文件；
- `outputs/` 并不是当前项目规范要求的目录；
- 根目录 `config.json` 并不是当前项目规范要求的位置；
- `data/rainfall.dat` 和 `data/topography.tif` 也不是当前必需组件；
- CA2D 必需组件应在 `static/` 下检查；
- SWMM 基线模型应在 `swmm/scenarios/baseline/model.inp` 下检查。

因此，这些“缺失项”不是 `songhua_swmm_2d` 的真实缺陷。

它们是旧式结构、demo 结构或 LLM 生成检查脚本中的错误假设。

## 8. 后续优化方向

本记录仅做分析，不立即实施。

### 8.1 建立唯一项目结构规范

以以下文件作为项目结构唯一真源：

```text
models/README.md
```

所有完整性检查必须遵守其中定义的结构。

### 8.2 禁止临时脚本自行发明检查标准

如果用户要求“检查模型完整性”，系统应优先调用固定工具：

```text
check_swmm_2d_project()
check_all_swmm_2d_projects()
check_ca2d_model()
```

而不是让 CodeRunner 临时生成一个新的目录检查脚本。

### 8.3 给每个检查结果标注 schema version

每次检查输出应包含：

```json
{
  "schema_name": "SWMM-2D project layout",
  "schema_version": "models-readme-2026-07-18",
  "validator": "check_swmm_2d_project",
  "project": "songhua_swmm_2d",
  "ready": true
}
```

这样就能知道结果是按哪个规范检查的。

### 8.4 建立检查器白名单

完整性检查只允许以下固定验证器：

```text
list_swmm_2d_models
check_swmm_2d_project
check_all_swmm_2d_projects
check_ca2d_model
list_rainfall_events
```

临时生成脚本只能用于辅助分析，不能作为项目完整性判定依据。

### 8.5 将假缺失识别纳入 benchmark

可以设计负样本任务：

```text
请检查模型是否缺 data/model.inp
请检查项目根目录 config.json 是否存在
请检查 outputs 是否存在
```

正确 Agent 应回答：

```text
这些不是当前 SWMM-2D 项目规范中的必需项。
当前规范要求 baseline model.inp 位于 swmm/scenarios/baseline/，
CA2D config.json 位于 static/。
```

这可以作为结构规范感知能力的评价任务。

## 9. 对论文创新点的启发

这次案例可以扩展前面提出的：

```text
模型结构感知工具编排与失败恢复机制
```

进一步加入：

```text
Schema-grounded validation
```

中文可写为：

```text
结构规范约束的模型验证
```

论文中可以表述为：

> SWMM-2D-Agentic does not allow LLM agents to freely invent validation criteria for hydrodynamic model projects. Instead, model completeness checks are grounded in an explicit project-layout schema, which prevents schema drift in agent-generated validation scripts and avoids false missing-component reports.

中文表述：

> SWMM-2D-Agentic 不允许 LLM-Agent 自由发明水动力模型项目的完整性检查标准，而是将模型验证约束在显式项目结构规范之下，从而避免生成式检查脚本中的结构规范漂移，减少错误缺项报告。

## 10. 可评价指标

可加入以下指标：

- Schema adherence rate：结构规范遵循率；
- False missing-component rate：假缺项率；
- Validator consistency：验证器一致性；
- Schema drift frequency：结构规范漂移频率；
- Required-file classification accuracy：必需文件分类准确率；
- Optional-file classification accuracy：可选文件分类准确率；
- Correct validator selection rate：正确验证器选择率。

## 11. 本次结论

本次案例说明：

1. “两数之和、哈希表、枚举”类模式化污染再次复现，进一步证明离域幻觉具有稳定签名。
2. `songhua_swmm_2d` 并不是因为缺少 `data/model.inp`、`outputs/` 或根目录 `config.json` 而不完整。
3. 这些缺项来自临时检查脚本采用的错误结构规范。
4. 同一模型检查结果不一致，本质原因是不同检查器使用了不同 schema。
5. 后续需要将模型完整性检查绑定到唯一项目结构规范和固定验证工具。

一句话总结：

> 这次不是模型缺东西，而是 Agent 生成式检查发生了结构规范漂移，把旧式或想象的项目结构当成了真实标准。
