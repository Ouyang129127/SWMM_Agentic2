# 降雨事件检查重复执行问题分析

## 1. 问题背景

本次记录来自一次 SWMM-2D-Agentic 前端实验。用户在前端完成模型完整性检查后，请求系统设计一次 SWMM-2D 内涝诊断流程，并在确认后执行步骤 2：检查可用降雨事件。

相关证据文件：

- 前端对话历史：`SWMM-2D-Agentic Chat5.html`
- 后台运行记录：`cmd记录.txt`
- Codex 附件日志：`pasted-text.txt`

用户观察到：后台 agent 在执行降雨事件检查时重复执行了很多次，似乎停不下来；手动按下 `Ctrl+C` 后，前端反而返回了正确结果。

经对照后台日志和前端 HTML，该观察基本准确。

## 2. 前端看到的现象

前端历史中，用户只进行了一次步骤确认：

1. 用户请求：`帮我设计一次 SWMM-2D 内涝诊断流程，并一步一步执行。`
2. Agent 给出流程，并提示下一步执行步骤 2：查看可用降雨事件。
3. 用户回复：`继续`
4. 前端最终返回：`步骤2完成：降雨事件检查结果`

前端结果中给出的结论是正确的：

- 模型项目：`songhua_swmm_2d`
- 降雨事件文件：`models/songhua_swmm_2d/events/rain1.txt`
- 文件大小约 `0.14 KB`
- 第一行显示单位为 `mm/h`

也就是说，从用户界面看，这一步最终像是正常完成了。

## 3. 后台实际发生的现象

后台日志显示，这一步并不是一次工具调用后结束，而是进入了 `CodeRunner` 内部的 `coder/coder_user` 多轮循环。

统计结果：

- `coder` 消息约 12 次
- `coder_user` 消息约 11 次
- `user` 任务消息约 3 次

后台围绕同一个降雨事件检查目标连续生成并执行了多段脚本，包括：

1. 列出 `events/` 目录下的降雨文件，保存为 `rainfall_events_list.txt`
2. 读取并验证 `rainfall_events_list.txt`
3. 读取 `rain1.txt` 并生成降雨摘要
4. 绘制降雨 hyetograph
5. 再次生成降雨清单
6. 检查路径格式并修正
7. 生成完整降雨事件报告
8. 做最终任务验证
9. 再次启动 `rainfall_events_inventory.txt` 清单生成
10. 试图读取 `rainfall_events_inventory.txt`

其中，早在第一次或第二次脚本执行后，核心信息已经足够：

```text
Rainfall events list saved to: rainfall_events_list.txt
Summary: Found 1 rainfall event file(s)
  - events\rain1.txt
```

但后台并没有就此停止，而是继续扩展出摘要、绘图、报告和验证等额外动作。

## 4. 关键判断一：本该走 TaskExecutor，却被路由到了 CodeRunner

检查降雨事件本来有固定工具支持：

- `list_rainfall_events(model_name="")`

按照系统设计，这类任务应该由 `TaskExecutor` 调用固定工具完成，而不应该交给 `CodeRunner` 临时生成脚本。

`prompts.py` 中已经有规则：

```text
If the task asks where rainfall events are or whether an event file exists, call TaskExecutor with list_rainfall_events.
```

但是后台日志显示，实际任务进入了 `CodeRunner`，因为日志中出现了典型的 `CodeRunner` 输入格式：

```text
task: 检查模型项目 songhua_swmm_2d 中 events/ 目录下的降雨事件文件，列出所有可用的降雨事件文件及其路径
name of file to be saved: rainfall_events_list.txt
SWMM status: models/songhua_swmm_2d/swmm/scenarios/baseline/model.inp
```

这说明 Orchestrator 很可能把“列出降雨事件并保存清单文件”理解成了一个代码生成/文件保存任务，于是调用了 `CodeRunner`。

因此，第一个问题不是“没有工具”，而是：

> 有固定工具，但固定工具路由只靠 prompt 约束，没有被代码层强制执行。LLM Orchestrator 在多轮上下文中仍可能误路由到 CodeRunner。

## 5. 关键判断二：CodeRunner 停不下来的直接原因

`CodeRunner` 的终止条件位于 `main.py`：

```python
text_termination = TextMentionTermination(text="===TASK DONE===", sources=["coder_user"])
max_message_termination = MaxMessageTermination(20)
termination = text_termination | max_message_termination
```

也就是说，只有当 `coder_user` 的输出中出现：

```text
===TASK DONE===
```

`CodeRunner` 小队才会停止。

但后台日志显示，前面多轮中，`coder` 经常生成如下结构：

```text
```python
# 代码主体
save_rainfall_events_list("rainfall_events_list.txt")
```

print("===TASK DONE===", flush=True)
```

关键问题是：`print("===TASK DONE===")` 被放在了代码块外面。

`CodeExecutorAgent` 只执行 fenced code block 里的 Python 代码，不会执行代码块外部的普通文本。因此，虽然日志里能看到 `print("===TASK DONE===")`，但它没有真正进入 `coder_user` 的执行输出。

于是终止条件没有触发，`CodeRunner` 继续下一轮，开始生成“验证脚本”“摘要脚本”“绘图脚本”“修正格式脚本”等重复或扩展任务。

后面日志中只有一次真正出现了执行器输出：

```text
===TASK DONE===
```

这说明终止信号不是没有设计，而是早期多轮没有被实际执行出来。

## 6. Ctrl+C 后前端返回正确结果的解释

用户按下 `Ctrl+C` 后，后台出现：

```text
INFO:     Shutting down
INFO:     Waiting for connections to close. (CTRL+C to force quit)
```

这说明服务开始关闭，并等待当前请求收尾。

由于前面重复执行过程中已经生成了正确的降雨事件证据，前端最终拿到了一条正确总结：

- 找到 1 个降雨事件文件
- 文件为 `rain1.txt`
- 路径位于 `models/songhua_swmm_2d/events/rain1.txt`

因此，“Ctrl+C 后前端返回正确结果”并不矛盾。更合理的解释是：

> 正确结果早已产生，但后台 agent loop 没有及时停止，导致前端一直等待。`Ctrl+C` 触发服务关闭过程后，已有结果被释放或被上层汇总返回。

## 7. 本次问题链条

本次问题可以概括为以下链条：

```text
用户确认执行步骤2：检查降雨事件
        ↓
该任务本应走 TaskExecutor.list_rainfall_events
        ↓
Orchestrator 误路由到 CodeRunner
        ↓
CodeRunner 生成脚本并实际找到了 rain1.txt
        ↓
终止 print 被放到代码块外，没有被 coder_user 执行
        ↓
TextMentionTermination 收不到 ===TASK DONE===
        ↓
CodeRunner 继续生成重复/扩展脚本
        ↓
后台表现为重复执行、停不下来
        ↓
用户 Ctrl+C 后，前端返回了已有的正确检查结果
```

## 8. 初步根因

### 8.1 路由层根因

固定检查任务没有在代码层进行强制路由。虽然 prompt 中规定降雨事件检查应由 `TaskExecutor` 执行，但 LLM Orchestrator 仍可能因为“保存文件”“列出并显示”等措辞把任务转给 `CodeRunner`。

### 8.2 执行层根因

`CodeRunner` 的停止机制过度依赖 `coder_user` 输出中的 `===TASK DONE===`。当 `coder` 把终止 print 放在代码块外时，执行器不会运行它，终止条件就失效。

### 8.3 任务边界根因

`CodeRunner` 在完成核心任务后，没有足够强的“一次成功即停止”约束，容易继续生成验证、摘要、绘图、修正等追加动作。这些动作对当前任务不是必需的，却会拉长执行链。

## 9. 后续修复方向

本文件仅做问题分析，暂不改代码。后续可考虑分层修复：

1. 在 `web_app.py` 或 `main.py` 的确定性路由层增加降雨事件检查拦截：
   - 只要用户请求包含“降雨事件”“降雨文件”“rainfall event”“events/”等检查/列出意图，直接调用 `list_rainfall_events`
   - 不再交给 Orchestrator 自由判断

2. 在 Orchestrator prompt 中进一步强化：
   - 降雨事件检查属于 official validation，不允许 route to CodeRunner
   - 即使用户要求保存清单，也应先由 `TaskExecutor` 获取 evidence，再由解释层或轻量保存逻辑处理

3. 修复 `CodeRunner` 的终止机制：
   - 降低 `max_turns`
   - 在第一次 `coder_user` 成功执行且无错误时可提前停止
   - 或在代码执行后由包装层补充终止信号，而不是完全依赖模型把 `print("===TASK DONE===")` 放进代码块

4. 修改 `coder_prompt`：
   - 明确 `print("===TASK DONE===", flush=True)` 必须在同一个 Python code block 内
   - 不允许在代码块外输出终止 print

5. 对固定工具已有覆盖的任务禁用 CodeRunner：
   - 模型完整性检查
   - CA2D 静态模型检查
   - 降雨事件列出
   - 官方 rainfall-to-SWMM-to-CA2D 耦合模拟

## 10. 对论文/创新点的启示

这次错误记录可以作为 SWMM-2D-Agentic 可靠性设计的反例材料：

- 单靠 LLM prompt 进行工具路由并不稳定；
- 对工程模型任务，固定工具链需要代码级 gatekeeper；
- agent loop 必须有明确、可执行、可观测的终止条件；
- 前端返回正确结果并不代表后台执行轨迹干净；
- 可靠性评价应同时记录 final answer 与 execution trace。

可提炼为论文中的一个问题类型：

> Repeated tool-loop after correct evidence acquisition

或中文表述：

> 正确证据已获取后的重复执行循环

这类问题体现了 agentic workflow 中“结果正确”和“执行过程可靠”之间的差异，对后续提出 tool-first routing、evidence-preserving explanation 和 loop termination control 都有支撑价值。
