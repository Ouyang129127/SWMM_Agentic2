# 模型结构感知工具编排与失败恢复

## 记录背景

在使用 `run.bat` 启动命令行服务后，系统执行默认任务：

```text
List available SWMM-2D model projects under the project-root models directory,
then check each discovered model project for model.yaml, baseline SWMM scenario,
CA2D static model, mapping, events, and runs structure.
```

实际执行过程中出现了以下问题：

1. Orchestrator 将 `models/` 作为 `TaskExecutor` 的 `path` 参数传入。
2. TaskExecutor 将 `models/` 误解释为一个具体模型项目名，尝试访问 `models/models`。
3. 失败后系统又尝试将项目根目录 `.` 当作 SWMM `.inp` 文件检查，触发目录读取错误。
4. 后续 LLM 输出了 DSML 形式的伪工具调用文本，但该文本并未真正执行。
5. 最终模型跑偏，输出了与 SWMM-2D 完全无关的 LeetCode “两数之和”内容。

这说明问题不只是普通幻觉，而是 Agent 在真实工程文件系统中存在更具体的可靠性风险：

```text
路径语义误判 -> 工具选择错误 -> 错误恢复失控 -> 伪工具调用 -> 无关回答
```

## 工程根因

这次失败揭示了 SWMM-2D-Agentic 中一个关键问题：

> Agent 需要理解模型工程目录的语义，而不能只把路径当作普通字符串。

对于 SWMM-2D 项目，不同路径具有不同语义：

- `models/`: 多模型项目注册表；
- `models/<model_name>/`: 单个模型项目根目录；
- `models/<model_name>/static/`: CA2D 静态模型目录；
- `models/<model_name>/swmm/scenarios/<scenario_name>/model.inp`: SWMM 场景输入文件；
- `models/<model_name>/events/`: 降雨事件目录；
- `models/<model_name>/runs/<run_id>/`: 模拟输出目录。

如果 Agent 不区分这些语义，就容易出现：

- 将 `models/` 误判为模型项目；
- 将项目根目录误判为 `.inp` 文件；
- 将 `models/<model_name>` 与 `models/<model_name>/static` 混用；
- 在工具调用失败后盲目尝试无关路径；
- 生成看似工具调用、实际未执行的伪调用文本。

## 可发展为论文创新点

这个问题可以提升为论文中的一个方法贡献：

> **Model-aware tool orchestration and failure recovery for SWMM-2D engineering workflows**

中文可表述为：

> **面向 SWMM-2D 工程工作流的模型结构感知工具编排与失败恢复机制。**

其核心思想是：

> SWMM-2D-Agentic 不仅需要将自然语言任务转化为工具调用，还需要显式理解水动力模型项目的目录语义、文件角色和工具适用边界，从而避免路径误判、工具误用、伪调用和错误恢复失控。

这可以作为 evidence-grounded diagnosis 之外的另一类可靠性贡献：

- evidence-grounded diagnosis 约束的是“诊断结论是否有模型证据”；
- model-aware orchestration 约束的是“执行过程是否正确调用了模型、文件和工具”。

## 建议论文表述

可以在论文中增加如下表述：

> In addition to evidence grounding at the diagnosis stage, SWMM-2D-Agentic introduces a model-aware tool orchestration mechanism that explicitly distinguishes project registries, model roots, static CA2D assets, SWMM scenario files, rainfall-event inputs, and run-output folders. This design prevents common LLM-agent execution failures, such as treating directories as input files, confusing project roots with static model folders, generating non-executed pseudo tool calls, and performing uncontrolled recovery after tool failures.

中文表述：

> 除诊断阶段的证据约束外，SWMM-2D-Agentic 还引入模型结构感知的工具编排机制，显式区分项目注册目录、模型项目根目录、CA2D 静态模型目录、SWMM 场景输入文件、降雨事件文件和运行输出目录。该机制用于避免 LLM-Agent 在真实工程文件系统中常见的执行失败，例如将目录误作输入文件、混淆项目根目录与静态模型目录、生成未执行的伪工具调用，以及在工具失败后进行无控制的路径试探。

## 可评价指标

这部分可以扩展为 Agent 可靠性 benchmark 的一类任务：

### Execution Reliability Tasks

任务示例：

1. 用户只说“检查 models 下所有项目”，系统应调用项目发现和批量检查工具。
2. 用户给出 `models/songhua_swmm_2d`，系统应识别为项目根目录。
3. 用户要求检查 CA2D 静态模型，系统应定位到 `models/<model_name>/static/`。
4. 用户要求运行 `rain1.txt + baseline + test01`，系统应组合 rainfall、scenario 和 run_id。
5. 用户给出错误路径，系统应报告路径语义错误，而不是盲目尝试 `.inp` 或根目录。
6. LLM 输出伪工具调用文本时，系统应拦截并提示未执行。
7. LLM 输出与任务无关内容时，系统应拦截并标记为无效回答。

可量化指标：

- Path semantic accuracy：路径语义识别准确率；
- Tool routing accuracy：工具路由准确率；
- Pseudo-call rate：伪工具调用率；
- Failure recovery success rate：失败恢复成功率；
- Invalid retry count：无效重试次数；
- Directory-as-file error rate：将目录误作文件的错误率；
- Unrelated response interception rate：无关回答拦截率；
- End-to-end execution success rate：端到端执行成功率。

## 后续改进设想

这部分暂不立即实施，但可以作为系统下一阶段设计方向。

### 1. 建立模型项目注册表

在 `models/` 下维护显式项目索引，例如：

```text
models/
  registry.json
  songhua_swmm_2d/
  hebei_swmm_2d/
  hunan_swmm_2d/
```

`registry.json` 可记录：

- model_name；
- project_root；
- default_scenario；
- static_model_dir；
- events_dir；
- runs_dir；
- available_scenarios；
- available_rainfall_events。

这样 Agent 不需要盲猜目录结构，而是先读取注册表。

### 2. 引入路径语义分类器

在工具调用前，先对路径做确定性分类：

```text
models/                                      -> model_registry
models/<model_name>/                         -> model_root
models/<model_name>/static/                  -> ca2d_static_model
models/<model_name>/swmm/scenarios/...inp    -> swmm_input_file
models/<model_name>/events/rain1.txt         -> rainfall_event_file
models/<model_name>/runs/<run_id>/           -> run_output_dir
```

分类结果再决定可调用工具，而不是让 LLM 直接决定。

### 3. 设计工具调用前置校验层

每个工具声明自己的输入类型：

- `check_all_swmm_2d_projects`: 需要 `model_registry`；
- `check_swmm_2d_project`: 需要 `model_name` 或 `model_root`；
- `check_ca2d_model`: 需要 `ca2d_static_model` 或可解析到 static 的 model_root；
- `is_runnable_inp`: 只能接收 `.inp` 文件；
- `run_swmm_2d_project_from_rainfall`: 需要 model_name、rainfall_file、scenario_name、run_id。

如果输入类型不匹配，系统应直接拒绝该工具调用，并给出可恢复提示。

### 4. 将 LLM 输出与真实工具事件分离

系统日志应区分：

- 模型文本建议；
- 真实 ToolCallRequestEvent；
- 真实 ToolCallExecutionEvent；
- 未执行的伪工具调用文本。

如果出现 DSML/XML/JSON 伪调用，应标记为：

```text
pseudo_tool_call_detected = true
executed = false
```

这可以用于论文中的 failure analysis。

### 5. 失败恢复应有限状态化

不要让 LLM 在失败后自由乱试路径，而是定义恢复策略：

```text
path_not_found -> list available projects
directory_given_to_file_tool -> classify path and suggest correct tool
missing static files -> report missing static components
missing rainfall file -> list rainfall events
multiple models found -> ask user to choose model_name
pseudo tool call detected -> retry with bound tool interface or stop
unrelated response detected -> discard and retry once
```

这可以形成一个 Failure Recovery Agent 或 Execution Guard。

### 6. 建立 Agent 执行审计日志

每次任务保存结构化日志：

```json
{
  "task_id": "...",
  "user_request": "...",
  "path_semantics": "...",
  "selected_tool": "...",
  "tool_input": {},
  "tool_output": "...",
  "failure_type": null,
  "recovery_action": null,
  "final_status": "success"
}
```

这类日志既能调试系统，也能作为论文 benchmark 数据来源。

### 7. 构建负样本 benchmark

除了正常任务，还要故意设计“容易出错”的任务：

- 只给 `models/`；
- 只给 `models/songhua_swmm_2d`；
- 把 static 目录写成项目根目录；
- 把项目根目录写成 `.inp`；
- 给不存在的 rainfall；
- 给多个平行项目但不指定 model_name；
- 给中文模糊任务；
- 给半截任务，例如“继续执行刚才那个模拟”。

这些负样本能体现系统是否真正可靠，而不是只在理想输入下跑通。

## 论文价值判断

这部分有论文价值，因为它回应了 LLM-Agent 在工程模型应用中的核心质疑：

> LLM-Agent 在真实、复杂、层级化的工程文件系统中，是否能可靠地找到正确模型、选择正确工具、执行正确流程，并在失败时可控恢复？

如果能把这个问题系统化，本文的创新就不只是“LLM 调 SWMM”，而是：

> 提出了一套面向复杂水动力模型项目的可靠 Agent 执行机制。

这与大规模 SWMM-2D 模型非常契合，因为真实项目往往包含多个模型、多种情景、多类输入输出和复杂结果目录。越是真实工程系统，路径语义和执行可靠性越重要。
