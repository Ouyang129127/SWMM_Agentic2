## 4. 虚假内容判定

以下内容可明确判定为虚假或不可信：


判定依据如下：

1. 真实 `workflow_state.json` 仍为 `EVIDENCE_READY`，并未进入 `DIAGNOSIS_READY` 或 `VERIFIED_READY`。
2. 真实 run 目录下没有 `diagnosis/`、`verification/` 和 `report/` 文件夹。
3. 当前真实 `DiagnosisAgent` 的规则机制通常按每类 top_n 生成诊断结论。此前真实案例中，`rain1` 通常为 50 条左右，`rain4` 通常为 40 条左右，不符合“1,000 条诊断声明，高中低风险 200/300/500 条”这种整齐分布。
4. 当前后端 `ReportAgent` 的实现主要返回 Markdown 文本给前端显示，并未在该 run 目录中自动写入 `report/user_report.md` 或 `report/single_point_explanation.md`。

## 5. 初步原因分析

本次问题的本质不是“文件路径找不到”，而是：

> 对话工作台在没有真实调用后端工作流、没有读取真实 `workflow_state.json`、也没有检查目标文件是否存在的情况下，生成了阶段完成叙述。

换句话说，它把“下一步应该执行什么”或“理想情况下会生成什么”错误表述成了“已经执行完成并生成文件”。

这属于对话 Agent 的状态约束不足问题。它没有做到以下几点：

1. 声称某阶段完成前，必须读取真实 `workflow_state.json`。
2. 声称某文件生成前，必须检查目标文件是否存在。
3. 声称诊断条数、验证条数、unsupported rate 前，必须从真实 `diagnosis_claims.json` 或 `verification_report.json` 中读取。
4. 当前工作流只完成到 `EVIDENCE_READY` 时，不能继续自然语言续写成 `DIAGNOSIS_READY`、`VERIFIED_READY` 或报告完成。

## 6. 对系统可信性的影响

这个问题非常重要，因为 SWMM-Agentic2 的核心价值之一就是“证据约束”和“可追溯”。如果对话层可以在没有真实文件支撑的情况下声称阶段完成，那么会削弱整个 Agentic 工作流的可信性。

尤其对于论文写作和老师汇报而言，必须明确区分：

```text
真实执行结果
计划执行步骤
预期生成文件
Agent 自然语言说明
```

其中，只有真实文件和真实工作流状态能够作为实验结果或系统输出依据。

## 7. 后续整改建议

后续应对对话工作台或 Agent 回复逻辑增加硬约束：

1. **阶段完成校验**

   每次声称某阶段完成时，必须读取 `workflow_state.json`，确认 `state` 和 `completed_stages` 已真实更新。

2. **文件存在性校验**

   每次声称生成某个文件时，必须执行文件存在性检查，并最好返回真实路径。

3. **禁止虚构统计数字**

   诊断声明数量、风险等级分布、验证支持率、unsupported rate 等统计结果必须来自真实 JSON/CSV 文件，不能由语言模型估计或补全。

4. **前端显示区分“下一步”和“已完成”**

   如果当前状态为 `EVIDENCE_READY`，前端只能提示：

   ```text
   下一步可执行 DiagnosisAgent
   ```

   不能显示：

   ```text
   DiagnosisAgent 已完成
   ```

5. **ReportAgent 输出边界明确**

   当前 ReportAgent 若只是返回 Markdown 文本给前端，应避免在对话中声称生成了 `report/*.md` 文件。若后续确实需要落盘，则应显式实现写文件逻辑，并在完成后检查文件存在。
