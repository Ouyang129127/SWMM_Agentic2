# SWMM-Agentic2 内涝诊断工作台设计思辨

日期：2026-09-14  
目的：记录 SWMM-Agentic2 当前能力、目标产品、诊断逻辑和开发边界，避免以“组件名称”代替真实能力，避免由 LLM 对水力结果作无证据推断。

## 1. 最终想做成什么

目标不是一个“自动运行 SWMM 的聊天工具”，而是一个有人在回路的自然语言内涝诊断工作台。

```text
用户用自然语言提出任务
  ↓
Agent 给出计划、范围和拟执行步骤
  ↓ 用户确认
SWMM → CA2D 固定模拟链运行
  ↓
展示动态淹没结果和本次运行摘要
  ↓ 用户确认诊断范围或重点热点
构建热点、溢流节点、上下游管网和降雨之间的证据链
  ↓
输出诊断报告：事实、候选机制、证据、缺口和后续验证建议
  ↓
用户围绕同一 run、同一热点或同一节点继续追问与讨论
```

最终交付不应只有一句自然语言结论，而应至少包括：

- 可追溯的 `run_id` 与运行记录；
- 动态淹没图、最大深度图、关键时刻图；
- 编号化积水热点；
- 结构化诊断证据和核查状态；
- 正式诊断报告；
- 围绕该次运行持续进行的自然语言问答与验证建议。

## 2. 关键模型边界

当前系统采用 SWMM → CA2D 的单向耦合：

```text
降雨 → SWMM 汇水与管网水力计算 → 检查井溢流过程 → CA2D 地表漫流与淹没
```

因此：

- CA2D 负责回答“溢流水在地表淹到哪里、淹多深、持续多久”；
- SWMM 负责回答“为什么关键节点产生溢流”；
- 从 CA2D 积水区回到 SWMM 节点，是诊断上的逆向关联，而不是模型的双向水力耦合；
- 论文中不应额外强调未入井雨水形成的独立地表积水问题，重点保持在既有 SWMM–CA2D 耦合链条。

## 3. 分流制雨水管网的“满流”应如何理解

分流制包含雨水网和污水网，二者不能混为一谈。

- 重力流污水管通常按非满流设计；
- 雨水管道在选定的雨水设计重现期下按满流能力计算；
- “按满流计算”是管径设计边界，不代表希望任意雨强、任意时刻、每条雨水管都满流；
- 小雨和常遇雨下，多数管段应部分充满；设计雨型下，关键管段接近或达到满流可以是正常状态；超过设计标准时，可能承压、溢流和形成地表积水，应转向内涝风险与退水表现的诊断。

因此，Diagnosis Agent 不应使用“是否满流”作为简单故障判据，而应判断：

> 在当前雨型和设计标准下，该管段满流或承压是否超出预期，并且是否与节点溢流和地表热点在时间、空间和拓扑上相关。

第一阶段应聚焦分流制雨水管网。合流制需要额外纳入旱流污水、截流能力、CSO、污染负荷和污水厂接纳能力，不能与当前诊断规则混用。

## 4. 诊断逻辑：十大问题不是十个孤立答案

十大问题应分为三类。

### 4.1 直接事实

- 管段最大充满度、满流和超满流历时；
- 节点水位是否越过地面高程；
- 节点溢流量、溢流持续时间和反复溢流次数；
- 管段倒坡、管底高程突变、异常坡度；
- 降雨峰与节点/管段响应峰的时序关系。

### 4.2 候选机制

- 上游来水集中；
- 局部输水能力不足；
- 下游输水受限；
- 下游边界顶托；
- 泵站控制引发的水位波动；
- 高程或拓扑异常引发的局部壅水；
- 真实水力波动或数值不稳定。

### 4.3 核查与外部约束

- 数值结果是否对时间步和参数异常敏感；
- 结论是否符合实际管径、坡度、泵站、排口和历史易涝认知；
- 缺失边界、泵站或现场资料时，必须输出“不可判定”，而不能填补一个貌似合理的根因。

## 5. 程序如何执行“诊断推理”

编程不应假装直接证明唯一根因，而应执行可复核的规则推理。

```text
原始时序结果
  ↓
事实层 Facts：节点溢流、管段充满度、地表水深、降雨、边界、泵状态
  ↓
关系层 Relations：节点—管段拓扑、节点—网格映射、网格连通关系
  ↓
事件层 Events：起始、峰值、结束、持续时间、时序先后和重叠度
  ↓
规则层 Rules：工程师定义的证据模式
  ↓
候选机制 Hypotheses：有何机制线索、证据是否足够、缺什么数据
  ↓
核查状态 Verdict：FACT / CANDIDATE / UNRESOLVED / VERIFIED_CAUSE
```

例如，“下游输水受限”不能只由“下游管段满流”得出，而至少应检查：

```text
节点发生溢流
AND 该管段是节点直接下游管段
AND 管段在同一事件中接近或达到满流
AND 满流开始不晚于节点溢流
AND 两事件具有显著时间重叠
→ 下游输水受限：CANDIDATE
```

若要称“下游边界顶托”，还必须拥有边界水位时序，并证明边界水位先抬升、下游节点先响应且高水位向上游传播；否则结论只能是 `UNRESOLVED`。

## 6. 主因、次因的边界

单次模拟中的空间邻近、满流和时间重叠只能支持候选机制，不足以严谨判定主因或次因。

主因/次因需要对照情景或独立资料支撑，例如：

```text
基准情景
  ├─ 降低边界水位后重跑
  ├─ 改善关键管段能力后重跑
  ├─ 调整泵控规则后重跑
  └─ 改变上游来水削峰条件后重跑
```

比较同一热点的面积、深度、历时和风险损失变化后，才可以讨论机制贡献、主因、次因或协同因子。

在此能力建立之前，报告应使用：

- 已证实风险事实；
- 高/中/低证据候选机制；
- 待核查机制；
- 数据不足，暂不可判定。

## 7. LLM 与 Agent 的定位

LLM 不应替代 SWMM、CA2D、规则计算或核查；它应承担：

- 理解自然语言任务；
- 给出阶段计划并请求确认；
- 选择诊断对象、追问缺失资料；
- 调用固定模拟、证据、诊断和核查工具；
- 将已验证事实、候选机制和不确定性组织为工程语言；
- 根据用户追问检索同一 run 的相关证据并解释下一步验证路径。

确定性程序应承担：

- 模拟执行；
- 指标计算；
- 热点和事件构建；
- 拓扑追踪；
- 规则判断；
- 证据引用和结论核查。

关键原则：

> 没有结构化证据，不作事实结论；有信号但未验证，只能称候选机制；有对照情景或独立资料验证后，才允许称为已验证成因。

## 8. 当前 SWMM-Agentic2 已具备的能力

当前代码已经具备以下基础：

- 固定的降雨 → SWMM → 节点溢流 → CA2D 模拟链；
- `runs/<run_id>/` 级别的运行归档；
- 节点、管段和 CA2D 网格的结构化证据表；
- 节点中心的局部证据包：邻近积水网格、直接上下游管段及拓扑追踪；
- 基础风险信号：节点溢流、重复溢流、管段高负荷、长期满流、网格积水深度与历时、流向改变；
- 证据引用完整性核查；
- 由自然语言驱动、按阶段“继续”推进的 Web 工作流；
- CA2D 最大深度图、最终深度图和淹没 GIF。

## 9. 当前与最终工作台的关键差距

### 9.1 缺少热点中心对象

当前核心对象是单个 `Cell` 或单个溢流节点；尚未形成 `H-001` 形式的独立积水热点及其面积、位置、边界、起淹/峰值/退水时间和历时。

### 9.2 缺少事件层与时序推理

现有证据多为最大值和累计值。诊断需要将节点溢流、管段满流、热点积水、降雨过程转换为事件，比较发生先后和时间重叠。

### 9.3 缺少热点—候选节点关联机制

当前 CA2D 输出没有保存不同节点溢流水的来源标签，因此不能严谨输出“某节点对热点贡献 62%”。第一阶段只能基于映射位置、网格连通和事件时序输出候选关联节点及关联强度。

### 9.4 十大问题覆盖不足

当前较成熟的是管段满流、节点溢流、网格积水和流向改变等基础指标；边界顶托、泵控、高程异常、振荡判别、雨峰—流峰和工程认知校核仍需补充数据和规则。

### 9.5 现有核查不是因果验证

当前 VerificationAgent 验证的是证据 ID 是否存在、对象是否匹配、指标是否满足规则；这证明“结论有证据引用”，不证明“候选机制已经被因果证实”。

### 9.6 有动态结果，没有交互式动态分析地图

目前已有 GIF、PNG 和水深 TSV，但 Web 前端没有时间轴、播放控制、地图点击、热点/节点/管段联动和曲线查看。

### 9.7 有 Markdown 报告雏形，没有热点诊断报告和案例记忆

当前报告主要列出 Top-N 网格、节点和管段。最终报告应围绕单个热点组织“空间后果—候选节点—局部网络—候选机制—证据缺口—建议验证”。后续问答也应主动绑定 `run_id` 与 `hotspot_id`，而非依赖最近聊天文本推断。

## 10. 下一阶段唯一应优先打通的主线

避免继续堆叠 Agent 名称或泛化聊天功能。应优先完成：

```text
CA2D 网格时序
  ↓
积水热点 H-001、H-002……
  ↓
热点属性和时序过程
  ↓
热点关联候选溢流节点
  ↓
复用现有节点中心上下游证据包
  ↓
事件—拓扑—规则的候选机制诊断
  ↓
热点诊断报告
  ↓
围绕 run / hotspot / node 的持续自然语言交互
```

当这条主线走通后，系统才会从“具备多个组件的 SWMM Agent 项目”变为真正面向工程师的自然语言内涝诊断案例工作台。

## 11. 开发与论文表述的原则

1. 不以 Agent 名称替代可验证能力。
2. 不以 `supported` 证据引用状态替代因果验证。
3. 不把“满流”自动等同于“异常”或“瓶颈”。
4. 不让 LLM 越过证据和核查层宣布根因。
5. 先做分流制雨水管网诊断；合流制另立规则体系。
6. 用户确认应设置在关键决策关口，而非每个内部读写动作。
7. 每项新增功能都应能服务于：可复现 run、证据链、诊断案例、报告、交互或论文评价。
