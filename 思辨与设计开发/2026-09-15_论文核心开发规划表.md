# SWMM-Agentic2 论文核心开发规划表

日期：2026-09-15  
定位：本规划优先服务论文核心方法、可复现案例和实验评价；暂缓 GIS 交互地图、复杂前端、仪表盘和完整产品化工作台。

## 0. 总目标与完成判据

论文核心不是“LLM 自动回答内涝问题”，而是建立并验证一条可复现的证据约束诊断链：

```text
降雨事件与情景
  ↓
SWMM → CA2D 耦合模拟
  ↓
标准化原始结果与证据表
  ↓
积水热点 H-001、H-002……
  ↓
热点—候选溢流节点关联
  ↓
节点—上下游局部管网追溯
  ↓
十大问题的规则诊断与候选机制识别
  ↓
证据核查、缺口声明与案例报告
  ↓
多场降雨/多情景 benchmark 与论文图表
```

论文核心完成时，至少应达到：

1. 多个真实或准真实 SWMM–CA2D run 可复现；
2. 每个 run 自动生成热点、证据、诊断和核查成果；
3. 每条工程结论可追溯到具体 `run_id`、对象 ID、时段和证据 ID；
4. 不把“候选机制”写成已证实根因；
5. 形成可展示的典型案例和 benchmark 定量评价。

---

## 1. 阶段一：冻结研究边界与数据契约

### 要做什么

- 明确第一篇论文只针对**分流制雨水管网**；
- 明确 SWMM → CA2D 单向耦合边界；
- 固定每个 run 的目录、元数据和输出文件命名；
- 固定 Diagnosis Agent 的结论状态：`FACT`、`CANDIDATE`、`UNRESOLVED`、`VERIFIED_CAUSE`；
- 固定“十大问题”中当前可做、待补数据、暂不可判定的范围；
- 固定“满流不是自动异常”的判定原则。

### 主要输入

- `models/<model_name>/model.yaml`；
- SWMM INP；
- CA2D static 模型与节点—网格映射；
- 当前 `workflow_agents/schemas.py`、`diagnosis_rules.json`。

### 应形成的成果

- `研究边界与诊断术语说明.md`；
- 更新后的诊断数据 schema；
- 十大问题能力矩阵；
- 论文 Methods 的初步术语定义。

### 验收标准

- 任何开发者都能回答“CA2D 做什么、SWMM 做什么、何时可称候选机制、何时不可判定”；
- 任何报告均不再把单向耦合误写为双向耦合；
- 任何报告均不再把“满流”直接等同于“故障”或“瓶颈”。

### 本阶段不做

- 前端地图；
- LLM 自由定因；
- 合流制与 CSO 污染诊断；
- 泵站调度优化。

## 2. 阶段二：固化模拟运行与原始结果完整性

### 要做什么

- 审计并固定 `run_swmm_2d_project_from_rainfall` 的运行输出；
- 确保每次 run 都保留：降雨副本、专属 INP、SWMM 节点/管段/溢流时序、CA2D 水深时序、运行摘要和状态；
- 增加运行耗时、成功/失败原因、保存步长、时间步和工具链元数据；
- 为大规模模型和至少一个较小测试模型各建立可复现基线 run。

### 主要输入

- 当前 `tools.py` 固定模拟管线；
- `models/songhua_swmm_2d` 与其他可运行模型；
- 降雨事件文件。

### 应形成的成果

```text
models/<model_name>/runs/<run_id>/
  scenario_request.json
  summary.json
  run.yaml
  workflow_state.json
  rainfall_event.txt
  swmm/model_with_event.inp
  swmm/nodes.tsv
  swmm/links.tsv
  swmm/node_flooding.tsv
  ca2d/surface_depth.tsv
  ca2d/ca2d_max_depth.png
  ca2d/ca2d_final_depth.png
  ca2d/ca2d_animation.gif
```

### 验收标准

- 同一模型、降雨和情景可重复运行；
- run 的元数据足以定位输入、模型版本和输出；
- 失败 run 也保留明确错误信息；
- 不依赖 CodeRunner 临时生成官方模拟流程。

### 本阶段不做

- 扩展大量工程情景；
- 复杂报告排版；
- 结果的因果解释。

---

## 3. 阶段三：标准证据表与事件层

### 要做什么

- 保留并完善现有 `evidence_table.csv`；
- 在最大值、累计值和历时指标之外，构建“事件对象”；
- 将节点溢流、管段接近满流/超满流、地表积水、降雨过程切分为有开始、峰值、结束的事件；
- 计算时序先后、重叠时长、重叠比例和峰值时差；
- 解析 SWMM INP 中的节点高程、管底高程、管径、断面、坡度、管段类型和排口信息。

### 主要输入

- `swmm/nodes.tsv`；
- `swmm/links.tsv`；
- `swmm/node_flooding.tsv`；
- `ca2d/surface_depth.tsv`；
- 降雨时序；
- `model_with_event.inp`。

### 应形成的成果

```text
evidence/evidence_table.csv
evidence/node_overflow_events.json
evidence/link_hydraulic_events.json
evidence/rainfall_events.json
evidence/static_network_attributes.csv
```

每个事件至少含：

- `event_id`；
- 对象类型与对象 ID；
- 起始、峰值、结束时刻；
- 峰值、累计量、持续时间；
- 触发阈值；
- 对应证据 ID。

### 验收标准

- 系统能回答“管段 C-12 是何时满流、持续多久、是否早于节点 N-23 溢流”；
- 系统能回答“节点水位是否高于其地面高程”；
- 时间关系可由程序重复计算，不能依赖 LLM 描述；
- 时间步信息明确，避免用样本数量替代真实历时。

### 本阶段不做

- 直接宣称主因或次因；
- 仅凭相关性归因下游边界或泵站问题。

## 4. 阶段四：积水热点构建

### 要做什么

- 从 CA2D 水深时序中，以水深阈值和空间连通性识别积水区域；
- 在相邻时刻跟踪重叠区域，形成同一场雨中的完整积水事件；
- 为热点编号，例如 `H-001`；
- 计算热点位置、面积、深度、体积、起淹、峰值、退水和历时；
- 输出热点网格边界或网格集合。

### 主要输入

- `ca2d/surface_depth.tsv`；
- `static/cells.csv` 中的网格坐标、面积、行列和高程；
- 阈值配置文件。

### 应形成的成果

```text
hotspots/hotspots.json
hotspots/hotspot_summary.csv
hotspots/hotspot_cells.csv
```

每个热点至少含：

```text
hotspot_id
run_id
cell_ids / geometry
centroid_x, centroid_y
maximum_area_m2
maximum_depth_m
maximum_volume_m3
start_time, peak_time, end_time
duration_min
severity
```

### 验收标准

- 报告对象从 `Cell 115176` 升级为 `H-001`；
- 每个热点都能复现其面积、最大深度、位置和时间过程；
- 同一热点的多个网格不会被误写成多个独立内涝点；
- 研究者可抽查热点网格集合与 CA2D 水深结果的一致性。

### 本阶段不做

- Web GIS 交互；
- 复杂道路、建筑暴露度评估；
- 节点对热点的水量贡献率声明。

---

## 5. 阶段五：热点—候选溢流节点关联

### 要做什么

- 以热点为中心检索其内部和邻接范围内的节点—网格注入点；
- 结合节点溢流事件与热点积水事件，计算空间邻近和时间重叠；
- 输出候选溢流节点及关联等级；
- 明确当前 CA2D 无水源示踪条件下，关联不等于水量贡献。

### 主要输入

- `hotspots/hotspots.json`；
- `static/node_to_cell_mapping.csv`；
- `evidence/node_overflow_events.json`；
- 网格连通关系和时间关系。

### 应形成的成果

```text
relations/hotspot_node_candidates.json
relations/hotspot_node_candidates.csv
```

每条关系至少含：

```text
hotspot_id
node_id
spatial_relation
temporal_overlap_ratio
overflow_volume_m3
association_level
evidence_ids
limitations
```

### 验收标准

- 系统可以回答“哪些溢流节点与 H-001 存在高、中、低关联”；
- 所有关系均给出空间与时间依据；
- 报告不使用“贡献率”“主导水源”等超出当前模型证据能力的词。

### 本阶段不做

- 以映射权重代替水量贡献率；
- 将候选节点关联直接写成致涝主因。

---

## 6. 阶段六：热点中心局部网络证据包

### 要做什么

- 将现有“溢流节点中心证据包”扩展为“热点中心诊断包”；
- 对每个高优先级热点，按关联等级选择候选节点；
- 从候选节点提取直接上游和下游管段；
- 沿管网向上游追溯至主要支路/汇水区，向下游追溯至排口、泵站、明确瓶颈或追踪终点；
- 对追踪路径保留管段水力事件、节点水位事件、坡度/高程属性和证据 ID。

### 主要输入

- 热点—节点候选关系；
- 当前 `evidence_graph.py` 的节点中心追踪能力；
- SWMM 拓扑和静态网络属性；
- 管段和节点事件。

### 应形成的成果

```text
diagnostic_packages/hotspot_H-001_package.json
relations/hotspot_network_relation_table.csv
```

诊断包结构：

```text
H-001
  ├─ 热点空间与时间属性
  ├─ 候选溢流节点及关联证据
  ├─ 每个节点的溢流事件
  ├─ 直接上游与下游管段
  ├─ 上下游追踪路径
  ├─ 降雨和可用边界/泵站上下文
  └─ 数据可用性与限制
```

### 验收标准

- 用户或审稿人可从 `H-001` 一路追溯到节点、管段、事件和原始证据；
- “上游的上游、下游的下游”有明确停止条件，而不是固定追几级；
- 每个被纳入诊断范围的对象都能说明为什么被纳入。

## 7. 阶段七：规则版 Diagnosis Agent

### 要做什么

- 将十大问题拆为“事实规则”“候选机制规则”“不可判定规则”；
- 用声明式规则配置，而非散乱的硬编码判断；
- 让规则基于事件、拓扑、时序和静态属性输出诊断结论；
- 将结论状态统一为 `FACT`、`CANDIDATE`、`UNRESOLVED`、`VERIFIED_CAUSE`；
- 明确每条规则所需证据、触发阈值和排除条件。

### 第一批应实现的规则

1. 管段接近满流、满流、超满流及其历时；
2. 节点水位超过地面高程；
3. 节点反复溢流；
4. 管段倒坡、异常坡度或管底突变；
5. 雨峰—管段流峰—节点溢流峰的时序关系；
6. 下游输水受限候选机制；
7. 上游来水集中候选机制；
8. 流向频繁切换/疑似波动线索。

### 暂定为“数据不足即不可判定”的规则

- 下游边界顶托：需排口或受纳水体边界水位过程；
- 泵站频繁启停：需泵状态和控制规则时序；
- 数值不合理振荡：需更高频输出及时间步/参数敏感性试验；
- 工程认知一致性：需竣工资料、现场记录或专家先验。

### 应形成的成果

```text
diagnosis/diagnosis_claims.json
diagnosis/diagnostic_mechanisms.json
diagnosis/diagnostic_gap_register.json
diagnosis/risk_ranking.csv
workflow_agents/rules/diagnosis_rules.json
```

### 验收标准

- 每条结论可追溯到规则 ID、事实、关系和证据 ID；
- Agent 能明确说“下游输水受限候选”与“边界顶托不可判定”的区别；
- 不把“满流”“空间邻近”“流向改变”单独视为根因；
- 不使用 LLM 直接计算或断言水力结论。

---

## 8. 阶段八：验证与候选机制验证设计

### 要做什么

- 将现有 VerificationAgent 从“证据引用存在性核查”扩展为三层：
  1. 引用完整性；
  2. 规则前提是否全部满足；
  3. 是否存在关键缺失证据或竞争性解释；
- 为高优先级候选机制定义后续验证方案；
- 若模型与算力条件允许，建立少量对照情景验证主因/次因。

### 主要输入

- `diagnostic_mechanisms.json`；
- 规则定义；
- 可用的边界、泵站和工程资料；
- 可重跑的 SWMM–CA2D 情景。

### 应形成的成果

```text
verification/verification_report.json
verification/claim_evidence_completeness.csv
verification/mechanism_validation_plan.json
verification/counterfactual_comparison.csv   # 条件具备时
```

### 验收标准

- `supported` 仅表示规则证据充分，不被误称为因果证明；
- 每项 `UNRESOLVED` 结论都有明确缺失数据；
- 若运行对照情景，主因/次因结论必须附带风险指标变化；
- 未运行对照情景时，报告不得使用“主因已证实”。

---

## 9. 阶段九：案例报告与最低限度自然语言交互

### 要做什么

- 生成面向论文案例分析的 Markdown/HTML 报告；
- 报告以热点为中心，而非仅罗列 Top-N Cell；
- LLM 只读取结构化、已核查成果，负责解释和追问；
- 将会话明确绑定 `run_id`，并允许用户指定 `hotspot_id`、`node_id`、`link_id`；
- 支持“展开证据”“解释候选机制”“说明缺失资料”“提出验证情景”，但不自动修改模型或重跑。

### 应形成的成果

```text
reports/<run_id>_diagnostic_report.md
reports/<run_id>_diagnostic_report.html
reports/<run_id>_case_summary.json
```

热点报告最低结构：

1. 热点编号、位置、面积、最大深度和淹没历时；
2. 候选溢流节点及关联依据；
3. 关键节点、管段和时序过程；
4. 十大问题对应的事实与候选机制；
5. 证据状态、数据缺口和不确定性；
6. 建议的下一步核查或验证情景。

### 验收标准

- 报告可由固定 run 直接复现；
- 每一个工程判断可定位到证据 ID；
- 用户追问不会脱离对应 run；
- 不需要复杂前端也能完成论文案例展示。

## 10. 阶段十：多事件、多情景与 benchmark

### 要做什么

- 建立至少 3 类降雨事件：短历时强降雨、长历时降雨、峰型不同降雨；
- 建立有限且有物理含义的情景：baseline、来水增强、局部管段受限等；
- 对每个 run 自动跑证据—热点—诊断—核查链；
- 建立任务集，评价自然语言协调、工具调用、证据完整性、热点识别和诊断一致性；
- 比较至少两种模式：无证据约束的 LLM/手工流程与证据约束工作流。

### 应形成的成果

```text
benchmark/tasks.jsonl
benchmark/reference_cases/
benchmark/grading_rules.yaml
results/run_matrix.csv
results/benchmark_scores.csv
results/method_comparison_summary.md
```

### 建议评价指标

- 模拟运行成功率；
- 任务完成率；
- 工具调用准确率；
- 热点识别一致性；
- 关键节点/管段排序一致性；
- 证据引用完整率；
- 无支撑结论率；
- 人工干预次数；
- 单任务完成时间。

### 验收标准

- 论文不是单一案例演示，而有可量化的重复实验；
- 能说明 Agent 增加的价值是“组织、追溯、解释和约束”，不是替代 SWMM/CA2D 求解器；
- 所有论文图表可由脚本和 run 结果复现。

## 12. 建议的近期执行顺序

在不扩展产品化功能的前提下，近期只推进以下五项：

1. **冻结研究边界与 schema**；
2. **补齐事件层与静态网络属性**；
3. **实现积水热点 H-001 构建**；
4. **实现热点—候选节点—局部网络诊断包**；
5. **实现第一批规则诊断与热点案例报告**。

完成这五项后，再决定是否进入：

- 边界、泵站和数值振荡等扩展诊断；
- 对照情景验证主因/次因；
- 多事件 benchmark；
- 交互地图和产品化前端。

## 13. 每次开发前的自检问题

1. 该功能是否服务“热点—节点—管网—机制”的论文主线？
2. 是否会新增可复现的结构化产物？
3. 结论是事实、候选、不可判定还是已验证成因？
4. 是否给出了证据 ID、时间关系和对象关系？
5. 是否误把满流、空间邻近或引用完整性写成因果证明？
6. 是否把本应由确定性程序完成的事情交给 LLM？
7. 是否属于可延后的产品化工作？

若前五项回答不清楚，或第七项答案为“是”，则不应成为当前优先开发任务。
