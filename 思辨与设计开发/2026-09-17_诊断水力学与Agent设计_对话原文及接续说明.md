### 必须覆盖早期简化说法的后续修正

1. 满流描述断面充满状态，压力流描述压力状态，两者可同时成立。不能使用固定“非满流→满流→承压流”序列作为统一负荷等级。

## 从地表积水开始，正确的追溯逻辑

不要一开始就机械地找“上游的上游、下游的下游”。先回答三个问题：

1. 这个积水区的水量来自哪里？
2. 这些水为什么不能及时排走？
3. 是哪个位置、哪个时刻、哪个机制首先造成排水失败？

可以按下面的因果链追溯：

```text
降雨
  ↓
地表汇流 / 子汇水区产流
  ↓
雨水口或节点入流
  ↓
上游管段输送
  ↓
局部瓶颈 / 满流 / 顶托 / 泵站 / 出口边界
  ↓
检查井水位超过地面
  ↓
节点溢流或地表回涌
  ↓
地表积水
```

这里要特别区分两种积水：

- **地表径流型积水**：雨下得快、地表来水大，但雨水口或节点入流能力不足；可能尚未发生管网顶托。
- **管网溢流型积水**：检查井水位超过地面高程，节点有 Flooding/Overflow；此时积水与管网超载、下游顶托或泵站问题直接相关。
- 实际案例常常是两者叠加：先地表来水集中，随后管网超载，最后检查井溢流反过来加重地面积水。

因此，Diagnosis Agent 的第一步应是：

> 对每个地表积水区，判定其是否与节点溢流在空间上邻近、时间上同步、体积上相互匹配。

若三者同时成立，才可较有把握地说“该积水主要由管网溢流造成”。

## 找到上下游元素后，到底分析什么？

把相关节点和管段凑齐，并不是终点，而是建立一个“局部水力因果单元”。这个单元至少包括：

```text
上游汇水区 → 上游节点/管段 → 积水关联检查井
                              ↓
                       下游首段管道
                              ↓
                   下游节点/泵站/排口/边界
```

对这一单元，应做以下五类分析。

### 1. 时序：谁先发生？

这是最关键的因果证据。比较：

- 降雨峰值时刻
- 子汇水区径流峰值时刻
- 上游入流峰值时刻
- 关键管段达到满流时刻
- 节点水位超过地面时刻
- 节点溢流开始时刻
- 下游边界水位上升时刻
- 泵站启停时刻

例如：

- 若下游边界水位先升高，随后上游节点水位整体抬升，说明可能是**下游顶托**。
- 若上游流量先迅速增加、关键管段先满流、再发生节点溢流，说明可能是**局部过流能力不足**。
- 若泵站频繁启停与节点水位锯齿状波动同步，说明可能有**控制策略问题**。
- 若节点在降雨峰前就高水位，则应优先排查**初始水位、边界条件、模型设置或外水入侵**。

### 2. 能力：哪里是真正的“卡口”？

对每条关键管段计算并排序：

- 最大流量 / 满流能力比值；
- 满流持续时间；
- 最大水深 / 管径比；
- 流速是否异常；
- 上下游水位差或水力坡降；
- 是否发生倒流；
- 管径、坡度、粗糙度、高程是否突变。

真正的瓶颈通常表现为：

> 上游水位持续升高 + 本管段长期接近或达到满流 + 下游输水能力明显不足或受阻。

不要把所有满流管段都认定为瓶颈。很多上游管段满流只是被下游顶托后的“受害者”。

### 3. 体积：水量是否对得上？

用体积判断归因是否可靠：

- 积水或节点溢流体积；
- 上游各汇水区的径流体积；
- 关键节点入流体积；
- 管段输送量；
- 泵站抽排量；
- 出口排放量；
- 系统连续性误差。

例如，某节点溢流 1,500 m³，但相邻地表积水估算仅几十立方米，就不能简单把全部溢流都解释成该处积水；可能是地表路由、多个低洼区汇集，或模型中的溢流去向设定不完善。

### 4. 水力梯度：水被什么“顶住”了？

观察关键节点的水位线/HGL：

- 水位是否从下游向上游整体抬升？
- 出口或河道边界抬升时，顶托是否沿网络传播？
- 某个检查井两侧是否出现异常大的水位差？
- 某管道是否因倒坡、管底高程突变或缩径而形成局部壅水？
- 是否出现反向流？

这一步能区分：

- **局部管径不足**；
- **下游边界顶托**；
- **泵站抽排不足或控制失稳**；
- **高程/连通关系错误**。

### 5. 反事实验证：去掉某个因素，问题还在不在？

这是 Agent 最有价值的能力。对重要积水点，自动构造少量“对照场景”：

- 保持其他条件不变，降低下游边界水位；
- 保持其他条件不变，提高泵站能力或优化启停阈值；
- 放大关键瓶颈管径；
- 修正可疑倒坡或管底高程；
- 降低/分散上游汇水区入流峰值。

然后比较节点最大水位、溢流量和积水量变化。

| 对照结果 | 更可能的主因 |
|---|---|
| 降低下游边界后问题大幅缓解 | 下游顶托/外河高水位 |
| 扩大某一管段后显著缓解 | 局部瓶颈或缩径 |
| 改善泵控后水位振荡和溢流下降 | 泵站控制问题 |
| 降低上游产流后显著缓解，但下游状态变化不大 | 汇水区来水过于集中或源头减排不足 |
| 所有工程调整都不符合常识，结果仍异常 | 模型结构、参数或高程数据问题 |

## 一个可执行的 Agent 工作流

建议让 Agent 以“积水事件”为主线，而不是先扫十个问题。

```text
输入：降雨、子汇水区、节点、管段、泵站、排口/边界、地表积水结果

1. 识别积水热点
2. 关联附近检查井与溢流事件
3. 判别：地表径流主导、管网溢流主导，还是混合型
4. 以关键检查井为中心，提取局部因果单元
   - 直接上游和下游
   - 上游汇水区
   - 下游至第一个控制点：泵站、排口、边界或明确瓶颈
5. 分析时序、能力、体积、水力梯度
6. 对候选原因进行对照场景验证
7. 输出主因、次因、证据、可信度、建议措施
```

“上游上游”和“下游下游”的边界最好按**功能节点**截断，不按固定跳数截断：

- 向上游：追溯至主要汇水区、支管汇入口，或流量贡献已很小的位置；
- 向下游：追溯至首个明确控制点——瓶颈管、泵站、闸门、排口、河道边界，或水位恢复正常的位置；
- 只要没有找到控制点，就不应武断停止追溯。

### 4. AI（回答）

时间：2026-09-14 01:06:37 +08:00；记录序号：23。

不应把“是否有不合理振荡”简单等同于“模型不可信”。真实排水过程当然会有波动，尤其在泵站、闸门、潮位边界、间歇降雨和管网充满—退水转换时。

更准确地说，它属于：

> **模型结果可信度检查 + 真实水力波动识别**

也就是先识别振荡，再判定它是物理现象还是数值伪振荡。

可以这样区分：

| 特征 | 更可能是真实水力波动 | 更可能是不合理数值振荡 |
|---|---|---|

## 当收集到上下游节点、管段和汇水区后，具体分析什么？

以一个造成严重地表积水的检查井 `N0` 为中心，建立局部水力单元：

```text
上游汇水区 → 上游节点/管段 → N0（溢流源）
                                      ↓
                              下游管段/节点
                                      ↓
                        瓶颈 / 泵站 / 排口 / 边界
```

然后对同一个事件窗口做五项分析。

### 1. 时序分析：谁先发生？

比较以下时刻：

- 降雨峰值；
- 上游汇水区径流峰值；
- N0 上游入流峰值；
- 关键管段开始满流；
- N0 水位超过地面高程；
- N0 开始溢流；
- 下游边界水位上升；
- 泵站启停。

时序是因果判断的核心。

- 上游来水峰值 → 管段满流 → N0 溢流：倾向于**汇水区来水集中或管道能力不足**。
- 下游边界先抬升 → 下游至上游水位依次抬升 → N0 溢流：倾向于**下游顶托**。
- 泵启停与水位锯齿波动严格同步：倾向于**泵站控制影响**。
- 无降雨、无边界变化、无设备动作但出现剧烈跳变：需怀疑**数值或模型结构异常**。

### 2. 能力与满流分析：哪一段是“因”，哪一段是“果”？

对局部范围内每条管段计算：

- 最大流量与满流能力之比；
- 满流持续时间；
- 最大水深与管径之比；
- 上下游水位差、水力坡降；
- 是否存在反向流；
- 管径缩小、坡度突变、管底高程突变等情况。

关键点是：**长期满流不必然就是瓶颈。**

如果某管段自身接近满流、其上游水位不断抬升、下游仍有足够排水空间，它更可能是瓶颈。  
如果整个下游系统水位已经抬高，多个上游管段同时满流，则它们可能只是被下游顶托的结果。

### 3. 水位线分析：水为何排不出去？

比较局部网络的 HGL/节点水位过程：

- 水位升高是否沿下游向上游传播？
- 关键节点两侧是否有异常大的水位差？
- 是否有倒流、倒坡或局部壅水？
- 下游边界水位是否接近甚至高于排口/管内水位？

这一步用于区分“局部缩径堵住了”与“下游整体被顶住了”。

### 4. 水量与贡献分析：谁贡献了这次溢流？

对 N0 的溢流事件，统计：

- 上游各汇水区的产流量及峰值贡献；
- 各上游支管的入流量；
- N0 的溢流量与溢流历时；
- 下游输送量、泵站抽排量、出口排放量；
- 输入 CA2D 的累计溢流体积。

这一环节可回答：

> 该节点之所以溢流，是上游来水量超过局部输送能力，还是下游输送能力被顶托压缩？

## 3. 如何从 CA2D 热点追溯到 SWMM 溢流节点？

这是“后果 → 源头”的关联问题，不是反向水力耦合。

理想做法是在 CA2D 中为每个检查井溢流输入保留**来源标签/示踪变量**。这样可直接计算：

\[
C_{i,h}=\frac{V_{i\rightarrow h}}{\sum_j V_{j\rightarrow h}}
\]

其中：

- \(V_{i\rightarrow h}\)：检查井 \(i\) 最终进入热点 \(h\) 的地表水量；
- \(C_{i,h}\)：节点 \(i\) 对热点 \(h\) 的贡献率。

若 CA2D 当前不支持示踪变量，可采用两种替代方法：

1. **逐节点关闭法**：依次关闭候选检查井的 SWMM→CA2D 溢流输入，比较热点面积、深度和体积变化；
2. **地形流路 + 时间窗匹配法**：基于 DEM、道路低洼通道、空间距离和溢流开始时间筛选候选节点。它可以用于初筛，但不能像示踪或对照模拟一样严谨地给出贡献比例。

我会倾向优先实现“来源示踪”或“逐节点关闭法”。这是把“哪些检查井导致哪个热点”从经验关联变成可验证结论的关键。

## 5. 主因和次因不能“看起来像”，必须用反事实贡献来区分

这是整个 Agent 最重要的原则。

定义一个热点损失指标 \(L\)。它不宜只用淹没面积，而应由项目目标确定，例如：

\[
L=w_A A_{\max}+w_D D_{\max}+w_T T_{\mathrm{inundation}}+w_V V_{\max}
\]

也可以进一步纳入道路、建筑、医院、变电站等暴露对象的风险权重。

先计算基准情景的热点损失 \(L_0\)，再对每个候选机制构造“合理且最小化”的对照情景：

| 候选机制 | 对照情景例子 | 比较指标 |
|---|---|---|
| 下游边界顶托 | 将边界水位替换为无顶托/设计低水位过程 | \(\Delta L_{\text{boundary}}\) |
| 局部管段瓶颈 | 将关键管段临时扩容至上、下游协调水平 | \(\Delta L_{\text{pipe}}\) |
| 泵站控制 | 采用合理启停阈值或连续变频策略 | \(\Delta L_{\text{pump}}\) |
| 上游产流集中 | 以设计调蓄/削峰后的合理入流过程替换 | \(\Delta L_{\text{runoff}}\) |
| 倒坡/高程异常 | 修正为工程允许的连续管底高程 | \(\Delta L_{\text{elevation}}\) |

对每种机制计算：

\[
\Delta L_k=L_0-L_k
\]

其中，\(\Delta L_k\) 越大，说明“消除或缓解该机制”后，热点风险下降越明显，该机制的致涝贡献越大。

建议定义：

- **主因**：经对照情景验证后，对目标热点风险降低贡献最大，且证据链完整的机制；
- **次因**：贡献明显但低于主因，或仅在主因存在时才放大的机制；
- **协同因子**：单独改变效果有限，但与其他机制共同改变时效果显著的机制；
- **背景条件**：长期存在但本场事件中不构成主要增量影响的因素；
- **模型疑点**：无法由物理机制和工程资料支撑、且对参数或时间步敏感的异常。

这比“满流时间最长，所以它是主因”严谨得多。

---

## 6. 原因之间会相互作用，不能机械相加

例如，“下游顶托”和“上游来水集中”可能各自都不是唯一原因，但叠加后才触发节点溢流。

所以对关键热点，除了单因素对照，还应计算组合情景：

\[
\Delta L_{A+B}=L_0-L_{A+B}
\]

若：

\[
\Delta L_{A+B} \gg \Delta L_A+\Delta L_B
\]

说明两者存在明显协同效应。此时报告不应硬写“下游顶托是唯一主因”，而应说：

> 该热点由“下游顶托—上游来水叠加”共同驱动；下游顶托决定系统可输送能力上限，上游汇水区峰值叠加触发溢流。

若需要把交互贡献更严格地分摊给多个原因，可以用 Shapley value；但第一版 Agent 可先采用“单因素对照 + 关键双因素组合”的方式，计算量和解释性更平衡。

## 7. LLM 应放在哪里？

LLM 值得加入，但不应承担数值计算、阈值判断或因果贡献计算。

它最合适做四件事：

1. **任务编排**  
   识别用户关注的是热点、节点、管段、泵站还是某场暴雨，调用相应诊断流程。

2. **结构化证据解释**  
   将检测引擎返回的数值证据组织为可读的因果链，而不是只罗列图表和指标。

3. **不确定性表达与追问**  
   例如：“未提供排口实测水位，关于边界顶托的结论目前为中等置信度；建议补充该断面水位过程。”

4. **交互式追问与工程问答**  
   例如用户问“为什么建议优先末端调蓄而不是上游扩容？”LLM 可以引用对照情景结果解释。

推荐的边界是：

```text
确定性程序/模型：
计算热点、追踪贡献、提取局部网络、检测十大问题、
运行对照情景、量化原因贡献、生成证据表。

LLM：
选择工作流、读取证据表、组织诊断叙述、
提出数据缺口、说明不确定性、生成工程建议初稿。
```

LLM 的最终结论应当可回链到结构化证据，例如：

> “判为下游边界顶托主导（贡献 46%）”  
> → 可点击查看：边界水位—节点水位时序图、无顶托对照情景、热点损失下降量与参数设置。

这样才是“有 LLM 的智能诊断 Agent”，而不是“LLM 生成诊断文字”。

## 1. Diagnosis Agent 的正确职责

它不应负责“从所有结果自由推理”。它应接收一个标准化的诊断对象：

```text
热点 H-017
  ├─ 空间与时间属性
  ├─ 关联的候选溢流节点
  ├─ 每个节点的溢流证据
  ├─ 该节点局部上下游管网

```

然后输出三类内容：

1. **事实结论**

   例如“未导出排口水位过程，当前不能判断是否由下游边界顶托导致”。

这比现在直接写“可能是下游顶托”更严谨：前者明确区分了事实、解释和缺失证据。

## 4. 主因、次因现在该怎么办？

在当前项目阶段，我建议暂时不用“主因、次因”这两个词，而用：

- 已证实风险事实；
- 高证据候选机制；
- 中证据候选机制；
- 待核查机制；
- 数据不足，暂不可判定。

例如：

> H-017 与 N-23 溢流在空间和时间上高度关联。N-23 下游 C-12 在溢流期间持续超满流 35 min，因此“下游输水受限”列为高证据候选机制。由于缺少排口边界水位过程，暂不能进一步判定该受限是否由外部顶托引起。

只有后续具备“改一个因素并重跑”的验证能力时，才可以正式区分主因与次因：

```text
基准情景
  ↓
只消除下游顶托条件，重跑
  ↓
只改善瓶颈管段，重跑
  ↓
只调整泵控策略，重跑
  ↓
比较热点 H-017 的面积、深度、历时、体积变化
  ↓
以改善效果及证据完整度确定主因、次因或协同机制
```

因此，我建议论文第一版写“**证据约束下的候选致涝机制识别**”，不要过早承诺“自动主因识别”。

## 5. LLM 能否加入？

能，而且适合加入；但要放在确定性流程之后。

当前 [`llm.py`](E:\SWMM_Agentic\SWMM-Agentic2\llm.py) 已配置了模型客户端，不过现有核心工作流仍是确定性 Python。这是一个正确基础。

LLM 可承担：

- 用户说“解释 XX 路积水”时，定位热点或查询对象；
- 调用已有工具生成热点、证据包、诊断和核查；
- 阅读结构化结果，写成工程师可读的解释；
- 根据缺失数据生成核查建议；
- 将用户问题转化为合法工作流请求；
- 对“候选机制”和“已验证结论”使用不同措辞。

LLM 不应承担：

- 从图或表中自行估算水量；
- 自行给候选节点分配贡献比例；
- 在边界、泵站、现场资料缺失时断言根因；
- 绕过 `VerificationAgent` 输出定因结论。

可给 LLM 一个严格的结论状态：

```text
FACT             已由模拟结果直接计算
CANDIDATE        有关联证据，但未验证因果
UNRESOLVED       数据不足，不能判断
VERIFIED_CAUSE   有对照情景或独立资料验证
```

它只能使用这四种状态写报告。这样 LLM 是“受证据约束的诊断交互层”，不是取代水力诊断的黑箱。

我赞同把 LLM 加入系统；但不同意把 LLM 放到因果判定的核心位置。当前项目真正应先做的是：**将 Cell 聚合为热点、将热点关联为候选溢流节点、再复用现有证据图进行局部管网诊断。**

### 22. AI（回答）

时间：2026-09-14 02:54:58 +08:00；记录序号：177。

① 你的直觉是对的：**“雨水管按满流计算”不等于“希望它在任何雨强下都满流”，更不等于“满流就是故障”。**

先把“分流制”拆开。分流制系统包含两张不同逻辑的网：

- **污水管网**：通常按非满流重力流设计，要保留通气与水力余量；
- **雨水管网**：在其选定的雨水设计重现期下，通常按满流能力计算。

现行《室外排水设计标准》明确：重力流污水管按非满流计算；雨水管道和合流管道按满流计算。标准同时要求雨水管渠在“雨水管渠设计重现期”按重力流、满管流计算，而在更高的“内涝防治设计重现期”按压力流校核。[GB 50014-2021 水力计算条文](https://gf.cabr-fire.com/m/article-40290.htm) [标准一般规定](https://yuanlin8.com/guifan/jipaishui/2acbfb18.html)

这句话的工程含义是：

```text
小雨、常遇雨        → 多数雨水管应部分充满
设计重现期暴雨      → 关键管段允许接近或达到满流
超过设计标准暴雨    → 可能承压、节点溢流、地表积水；
                    此时考察内涝防治、退水与风险，而非要求“仍不满流”
```

所以，“满流”本身不应作为 Diagnosis Agent 的故障判据。对分流制中的**雨水管网**，应把它分成三类：

| 现象 | 诊断含义 |
|---|---|
| 设计暴雨下局部管段短时接近满流，节点不溢流 | 可能是正常设计状态 |
| 低于设计标准的雨型就大范围长期满流，且引发上游水位抬升 | 能力不足、坡度异常、下游受限等候选问题 |
| 超过设计标准时满流甚至承压，但地表积水深度和退水时间仍满足要求 | 可接受的超标工况表现 |
| 设计暴雨下节点已大量冒溢，或超标暴雨下积水风险明显超限 | 需要进一步诊断和治理 |

因此，第 1、3 项建议改写，避免“满流即异常”的隐含逻辑：

> 1. 在当前降雨标准下，管段满流/承压是否超出预期？  
> 3. 哪些管段在关键时段持续满流，并与节点溢流或热点积水具有时空关联？

对于你们当前 SWMM–CA2D 框架，第一版建议**先只做分流制雨水管网诊断**。原因是它的因果链比较干净：

```text
设计暴雨或实测降雨
  ↓
SWMM 汇水区产流
  ↓
雨水管网输送
  ↓
节点溢流
  ↓
CA2D 地表淹没
```

此时 Diagnosis Agent 的“满流判断”不是问“这段管道是否满流”，而是问：

> 在该雨型和设计标准下，这段管道的满流是否是合理运行状态，还是已经造成了上游溢流与热点风险？

合流制以后可以单独扩展，不宜现在混入。因为合流制除“内涝”外，还必须同时诊断：

- 旱流污水基流；
- 雨天合流水量；
- 截流干管和泵站能力；
- 合流制溢流口（CSO）的溢流频次与污染负荷；
- 污水处理厂接纳能力；
- “允许设计的 CSO 溢流”与“检查井冒溢致内涝”的区别。

合流管道也可以在设计雨型下按满流计算，但“冒溢”不能一概视作同一种问题：排向规定受纳水体的 CSO 与从检查井涌上道路造成内涝，诊断目标完全不同。

② 不加大语言模型，能不能称为 Agent？

**能；但要满足“自主决策与行动”的最低条件。LLM 不是 Agent 的必要条件。**

传统软件 Agent、规则 Agent、BDI Agent、规划 Agent 都可以没有 LLM。关键不是它会不会说话，而是它是否具备：

```text
观察状态 → 根据自身目标选择动作 → 执行动作 → 检查结果 → 决定下一步
```

但我也要直接指出：如果一个模块只是固定地“读取 CSV → 计算指标 → 写 CSV”，它更准确地说是**分析模块或工具**，而不应因为文件名叫 `EvidenceBuilderAgent` 就宣称它是强意义上的 Agent。

就现有项目而言：

| 当前模块 | 当前更准确的身份 | 怎样才更像真正 Agent |
|---|---|---|
| ScenarioAgent | 场景准备模块 | 判断复用已有运行、创建新运行或要求补充输入 |
| EvidenceBuilderAgent | 确定性证据提取器 | 检查数据完整性，决定补算何种证据 |
| EvidenceGraphAgent | 关系构建器 | 根据热点风险等级决定追溯深度和关联范围 |
| DiagnosisAgent | 规则诊断器 | 根据证据选择“可诊断、需补数据、需重跑、需人工核查” |
| VerificationAgent | 结论核查器 | 驳回不充分结论，并要求指定验证动作 |
| ReportAgent | 报告生成器 | 可由 LLM 驱动解释与交互 |

所以，当前项目称为“**工作流阶段型 Agent 架构**”或“**证据约束诊断工作流**”是成立的；若直接称为“多 Agent 自主协同系统”，会有被质疑“只是串行脚本”的风险。

要让它更有底气地称为 Multi-Agent，不必让每个模块都接 LLM，但至少要让每个角色拥有：

- 明确目标；
- 可读取的共享状态；
- 有限且明确的动作集合；
- 基于证据选择下一步动作的策略；
- 对其他角色可消费的结构化消息。

例如 Diagnosis Agent 不再只输出结论，而可输出：

```json
{
  "hotspot_id": "H-017",
  "decision": "REQUEST_BOUNDARY_EVIDENCE",
  "reason": "下游管段长期满流，但当前缺失排口边界水位过程，不能区分局部瓶颈与边界顶托。",
  "required_data": ["outfall_stage_timeseries"],
  "allowed_next_agent": "EvidenceBuilderAgent"
}
```

这时它即使完全基于规则，也是在“感知—判断—行动—交接”，可以合理称为 Agent。

LLM 可以加入，但我建议只放在两处：

```text
用户
  ↓
LLM Coordinator Agent
  ├─ 理解“请诊断某热点/某场雨”
  ├─ 调用确定性模块
  ├─ 解释已有证据
  └─ 追问缺失资料
  ↓
规则型 Diagnosis / Verification Agents
  ↓
LLM Report Agent
  └─ 只依据已核查证据生成面向工程师的报告
```

LLM 不负责算满流、找倒坡、判定边界顶托，更不能绕过核查机制宣布主因。它负责“组织任务、提出问题、解释证据”。

我的建议是：论文第一阶段选择**分流制雨水管网**，把系统定位为“LLM 协调的、证据约束的混合式 Multi-Agent 诊断框架”。这个表述既保留 Agent 特征，又不会把确定性水力判断交给语言模型。

## 2. 将工程语言改写成机器可判断的谓词

以“下游瓶颈/下游输水受限”为例。它不是一句自然语言，而是一组机器谓词：

```text
Flooding(N-23, E1)
DownstreamLink(N-23, C-12)
NearFull(C-12, E2)
StartsBefore(E2, E1)
TimeOverlap(E1, E2) > threshold
```

程序可以把这些写成函数：

```python
def has_node_overflow(node_id, event):
    return event.volume_m3 > rule["min_overflow_volume_m3"]

def is_direct_downstream(node_id, link_id, graph):
    return graph.is_outgoing_link(node_id, link_id)

def is_near_full(link_event):
    return link_event.max_fullness >= rule["near_fullness_ratio"]

def substantial_overlap(event_a, event_b):
    overlap = intersect_minutes(event_a, event_b)
    return overlap / event_a.duration_minutes >= rule["min_overlap_ratio"]

def begins_before(event_a, event_b):
    return event_a.start_time <= event_b.start_time
```

然后将规则写成声明式配置，而不是写死在业务代码里：

```json
{
  "rule_id": "downstream_conveyance_constraint",
  "when_all": [
    "node_overflow",
    "direct_downstream_link_exists",
    "downstream_link_near_full",
    "downstream_fullness_starts_before_overflow",
    "downstream_fullness_overlaps_overflow"
  ],
  "conclusion": {
    "status": "candidate",
    "mechanism": "downstream_conveyance_constraint",
    "text": "下游输水受限为候选机制"
  },
  "required_evidence": [
    "node_overflow_event",
    "downstream_link_fullness_event",
    "topology_relation",
    "temporal_overlap"
  ]
}
```

程序不是“理解”了顶托，而是严格执行：

> 若某组数据满足水力工程师预先定义的“顶托/下游受限证据模式”，则输出对应的候选机制，并附证据。

这就是规则推理。

## 3. 每条规则都必须有“不能判断”的出口

这是 Diagnosis Agent 最容易做错的地方。

以“水位升高是否与下游边界相关”为例，正确逻辑不是：

```text
下游满流 → 所以边界顶托
```

而是：

```text
下游满流 → 下游输水受限线索
有排口/河道边界水位时序吗？
  ├─ 没有 → 边界顶托不可判定
  └─ 有
      ├─ 边界水位先升高
      ├─ 节点水位随后抬升
      ├─ 沿下游到上游存在传播顺序
      └─ 形成“边界顶托候选机制”
```

因此，应有三值甚至四值结论：

| 状态 | 含义 |
|---|---|
| `FACT` | 直接由模型结果计算得到 |
| `CANDIDATE` | 满足某一机制的证据模式，但未完成因果验证 |
| `UNRESOLVED` | 关键证据缺失，不能判断 |
| `VERIFIED_CAUSE` | 经对照情景或独立资料验证后的机制 |

例如，当前项目中没有专门导出排口边界水位过程，所以第 5 项的严谨结果大多数只能是：

> 下游输水受限：候选；下游边界顶托：不可判定，缺少边界水位时序。

这不是能力弱，反而是避免诊断幻觉的能力。

## 4. 十大问题应拆成“事实规则”和“机制规则”

### 事实规则：可直接编程判定

例如：

```text
节点水位是否超过地面高程？
管段最大充满度是否达到 1.0？
接近满流是否持续超过设定时间？
节点是否存在多次独立溢流事件？
是否存在倒坡？
雨峰与管段流量峰相差多少分钟？
```

它们是确定性计算，没有“推测”。

### 机制规则：需要组合事实和关系

例如：

```text
上游汇流集中候选机制：
降雨峰/上游产流峰 → 上游管段高负荷 → 节点溢流

局部输水能力不足候选机制：
下游首段长期满流 → 上游水位/溢流增加 → 下游未见整体顶托证据

下游边界顶托候选机制：
边界水位先升高 → 下游节点先抬升 → 高水位向上游传播 → 节点溢流

泵控异常候选机制：
泵开停事件频繁 → 水位呈同步锯齿 → 上游水位波动/溢流同步

高程异常候选机制：
倒坡/管底突变 → 局部水位差异常 → 该处及上游壅水或满流
```

这里的箭头不是数学因果证明，而是**待核查的水力证据链**。

## LLM 在这里应做什么？

LLM 可以参与，但不负责执行上述逻辑。

它适合：

```text

  ↓

  ↓
LLM：若允许，决定下一步调用哪些诊断/验证工具
```

例如，规则引擎返回：

```text
下游输水受限：CANDIDATE
边界顶托：UNRESOLVED
原因：缺少排口水位过程
```

LLM 可以自然地回答：

> 目前不能把 N-23 的溢流归因于外河顶托；现有结果只支持下游输水受限。若补充排口水位过程，可进一步区分局部瓶颈和边界顶托。

但 LLM 不可以越过规则引擎写：

> 下游河道顶托是主因。

一句话总结：**编程负责构造“事实—关系—规则—结论状态”的可核查逻辑；LLM 负责决定先查什么、解释查到了什么、以及下一步还缺什么。**

我之前说“LLM 不参与诊断推理”过于绝对。应该限制的是无证据定因，而不是禁止 LLM 推理。

## 2. 用一个具体过程说明

下面只是未来交互示例，不是当前项目已实现的功能或真实模拟结果。

你问：

> “这个积水点为什么这么严重？”

Diagnosis Agent 不应立即运行十条规则然后交报告，而应先组织调查。

**第一轮：确定调查对象**

LLM 读取热点属性、候选节点和数据可用性，提出：

> “先调查与该热点关联的节点 N0。当前有两种解释：上游来水集中，或下游排水受限。我建议先比较 N0 溢流期间各相连管段的流量和节点水位。”

你确认后，程序提取相应时序和指标。

**第二轮：根据结果决定往哪里追**

假如结果显示：N0 下游水位提前上升，而上游流量峰尚未到达。

LLM 可以推断：

> “上游峰值叠加暂不足以解释溢流起始。下游影响值得优先调查，但还不能区分局部阻力和更远处的顶托。我建议沿下游路径继续查看节点水位。”

这里，**为什么向下游追、追哪些对象、看哪些变量，是 LLM 的诊断决策。**程序负责正确提取对象与计算结果。

**第三轮：处理竞争解释**

如果继续追踪后发现下游存在泵站，LLM 应比较：

- 泵站是否正在抽排；
- 水位变化是否与启停有关；
- 更下游是否也出现水位抬升；
- 哪些解释与现有证据矛盾。

然后更新判断，并提出下一项调查。若无泵站状态数据，就保留未决解释，而不是宣布泵站故障。

**第四轮：必要时提出验证**

LLM 可以提出一个具体对照方案：

> “为了区分边界影响与局部管段限制，建议保持降雨和其他参数不变，运行一个经确认的边界对照情景。”

你确认后再运行。结果回来，LLM 重新评估假设。

这才是你需要的“会调查、会讨论、会修正判断”的 Diagnosis Agent。

## 3. 那规则程序还有什么作用？

规则仍然重要，但它们应成为 **LLM 的分析工具和约束**，而不是预先决定所有调查路径。

| 工作 | 主要承担者 |
|---|---|
| 计算溢流体积、时间重叠、水位差 | 确定性程序 |
| 查询拓扑、提取上下游节点与管段 | 确定性程序 |
| 提出局部瓶颈、顶托、来水集中等假设 | LLM，结合领域知识与当前证据 |
| 决定先检验哪个假设、补查什么 | LLM |
| 执行模拟或对照计算 | SWMM–CA2D 与固定工具 |
| 根据新证据修改、保留或排除假设 | LLM |
| 检查数值、引用、对象和时段是否对应 | 确定性核查 |
| 质疑推理跳跃、提出竞争解释 | 审核角色，可由另一 LLM Agent 承担 |
| 确认重要调查步骤和情景改动 | 用户 |

例如，规则告诉它“满流发生了”；LLM 要结合设计工况和事件后果判断“这条满流信息是否值得继续调查”。**严重积水是调查入口，十大问题是可选择的检查项目，调查顺序可以随证据改变。**

## 4. 多 Agent 也应围绕不同的判断责任设计

我更倾向于这样的研究结构：

- **协调 Agent**：理解问题、组织计划、管理人工确认。
- **诊断 Agent**：提出假设、选择证据查询、更新解释。
- **审核 Agent**：检查诊断中的证据缺口、竞争解释和过度断言。

模拟、指标提取、拓扑追踪、绘图等可以作为它们使用的工具。报告生成是否单独设 Agent，可以后续决定。

这样，每个 Agent 都有实质性的判断责任。也不要求每个 Python 函数都包装成一个 Agent。

审核 Agent 的意见同样可能错误，所以它不能替代确定性核查或工程验证；但它可以构成有意义的“诊断—质疑—补查—修订”协作过程。

| 向下游 | 管段、泵站、排口、边界、瓶颈 | 水为什么排不出去？ |
| 回到地表 | 溢流点、地形低洼带、积水区 | 溢流后为何在此处形成严重灾害？ |

上游追踪到“主要来水贡献已经解释清楚”为止；下游追踪到“首个明确控制点”为止，例如排口、泵站、边界、明显瓶颈，或水位恢复正常的位置。

## 三、真正的核心是“时间顺序”

水力诊断不应只看最大值。要把下列时刻放在同一时间轴上：

```text
降雨开始与雨峰
上游汇水区产流峰
上游支管流量峰
关键管段开始满流
节点水位快速抬升
节点开始溢流
下游边界水位变化
泵站启停
热点开始积水、达到最大深度、退水
```

然后问“谁先发生”。

### 情形 A：上游来水主导

```text
雨峰 / 上游产流峰
  ↓
支管流量集中到达
  ↓
下游关键管段满流
  ↓
节点溢流
  ↓
地表积水
```

这说明强降雨和汇水集中可能是主要驱动；还要进一步判断管网能力是否不足。

### 情形 B：下游顶托主导

```text
排口或下游边界水位上升
  ↓
下游节点先抬升
  ↓
高水位逐步向上游传播
  ↓
上游管段满流、可能倒流
  ↓
关键节点溢流
```

这里的关键是水位从下游向上游传递。仅看到下游管段满流，还不足以证明顶托。

### 情形 C：局部管段瓶颈主导

```text
上游来水增加
  ↓
某一局部管段先达到输送极限
  ↓
该管段上游水位显著抬升
  ↓
上游节点溢流
```

常见工程原因包括局部缩径、坡度过缓、倒坡、管底高程突变、粗糙度异常或连接关系问题。

### 情形 D：泵控或调控问题

```text
泵频繁启停
  ↓
集水井水位呈锯齿状升降
  ↓
上游节点水位同步波动
  ↓
在高水位周期发生溢流
```

这可能是真实运行问题，也可能是数值控制设置问题。要看泵状态和水位是否同步，不能只看水位曲线抖动。

## 四、工程师最常用的三张“脑内图”

### 1. 水量图：水够不够排？

比较：

```text
上游产流量 + 支管来水量
vs.
下游管段输送量 + 泵站抽排量 + 排口出流量
vs.
节点溢流量
```

若来水显著大于可排出水量，差额会表现为管内蓄水、水位抬升、节点溢流和地表积水。

### 2. 水位线图：水被什么顶住？

沿关键路径比较各节点水位、水位坡降、管底高程与地面高程：

```text
上游节点水位 → 管段 → 下游节点水位 → 排口/边界
```

- 水位从出口向上游整体抬升：优先怀疑边界顶托；
- 某局部位置前后水位差异常：优先怀疑局部瓶颈或高程异常；
- 水位抬升但没有合理的外部触发：检查模型设置、初始条件或数值稳定性。

### 3. 时间图：谁是原因，谁是结果？

同一事件中，先发生的过程更可能是驱动或约束；后发生的过程更可能是传递或后果。  
但“先发生”仍不是因果证明，它只是决定下一步应该查哪里。

先只谈分流制的雨水系统。

雨水管通常按当地规定的排水设计重现期，采用“重力流、满管流”计算；而在更高一级的防涝校核重现期下，才允许/需要校核压力流工况。[《室外排水设计标准》相关条文](https://www.yuanlin8.com/guifan/jipaishui/f915532a.html) 这里的“满流”本质上是设计能力的参照上限，不是日常运行目标。

| 状态 | 水力含义 | 工程解释 |
|---|---|---|
| 非满流 | 管内有自由水面，水深小于管径 | 小雨、中雨下的正常状态 |
| 满管重力流 | 断面接近或达到充满，输水能力接近按曼宁公式计算的 \(Q_\mathrm{full}\) | 在设计暴雨的关键时段、关键管段可以出现；不必然是故障 |
| 压力流／顶托流 | 水力坡线 HGL 高于管顶，水已充满且存在正压；水位可能向上游回顶 | 下游不畅、潮位顶托、泵站控制、局部瓶颈等导致的受压输水 |

最关键的划分，不是单看“流量是否超过满流能力”，而是看**水力坡线相对管顶和地面的关系**：

\[
z_{\mathrm{crown}}=z_{\mathrm{invert}}+D
\]

\[
\Delta H_{\mathrm{pressure}}=HGL-z_{\mathrm{crown}}
\]

\[
\Delta H_{\mathrm{flood}}=HGL-z_{\mathrm{rim/ground}}
\]

- \(\Delta H_{\mathrm{pressure}}\le 0\)：未形成明确压力顶托；
- \(\Delta H_{\mathrm{pressure}}>0\)：该管段或端部已处于受压/顶托状态；
- \(\Delta H_{\mathrm{flood}}>0\)：节点发生出井溢流。

所以，**满流不等于压力流，压力流也不等于溢流。** 它们是逐步升级的状态。

\[

\]

应被解释为“超过名义满管重力输水能力”，而不是直接判为异常。必须结合 HGL、持续时间、节点溢流和下游边界一起判断。

\frac{dV}{dt}=Q_{\mathrm{in}}-Q_{\mathrm{out}}-Q_{\mathrm{flood}}
\]

这里的入流包括汇水区来水和穿过区域边界的管道来水；出流包括管道排放、泵送等，按实际方向记账，不能重复计算区域内部管道的流量。

在尚未溢流时，入流持续大于出流，区域内就会积水、增加蓄量。但**蓄量如何对应各节点水位，还由管道几何、连通关系和下游水头决定**。这也是为什么只比较流量，不能完整解释溢流。

因此，每次诊断实际都在追问四件事：

- 来水过程如何变化？
- 哪个环节限制了排水？
- 还有多少可以利用的蓄水空间？
- 哪个节点最先达到溢流条件？

SWMM 动力波能够表达回水、受压、倒流及管渠蓄水等过程，为这些分析提供基础；但模型能计算这些过程，不意味着诊断模块已经识别了其原因。[EPA SWMM 水力参考手册](https://nepis.epa.gov/Exe/ZyPURL.cgi?Dockey=P100S9AS.TXT)

**2. 第一类：上游集中来水，使系统短时间来不及排走。**

典型情形是几个支路的洪峰在汇合点附近叠加，合流后的来水使局部蓄量增加、水位升高，最终发生溢流。

工程上要看的是**到达汇合位置的流量过程**，不只是几个子汇水区的产流峰值。水在管网内有传播、蓄滞和重新分配的过程，源头峰值接近，不一定意味着汇合点峰值也接近。

支持这个解释，需要看到：

- 各支路来流及叠加发生的时段；
- 叠加期间，下游出流未能相应增加，区域蓄量上升；
- 节点水位和溢流过程与上述变化一致。

但这只能先说明“来水与排水不匹配”。还需要问：**是来水本身很大，还是本来能够排走，却被下游水位限制了？**

验证时可在明确条件下调整某一支路的入流量或到达时间，观察目标节点的溢流变化。改变洪峰时间属于机制试验；如果直接移动输入过程，应注明它是理想化试验，不冒充真实降雨情景。

**3. 第二类：某个局部输水环节形成约束，上游水位被抬高。**

可能涉及小断面、局部构筑物、较大的水头损失，或者实际存在的淤积、堵塞。

这里最容易犯的错误是：

> 找到一根持续满流的管，就认定它是瓶颈。

真正需要寻找的是：**哪个环节需要较大的水头差才能通过当前流量，并由此使上游接近溢流。**

应联看疑似位置前后的水头、流量、断面、坡度及局部损失。不能仅用节点水位差认定损失大小；比较水头损失时还需考虑速度水头、泵等因素。

支持局部约束的证据通常是：水位抬升集中在该环节上游，下游条件相对有利，而改善该环节后，上游溢流明显减轻。

还要保留一个边界：**模型没有表达堵塞，就不能从模拟结果直接诊断“存在堵塞”。** 最多指出局部输水受限，并建议检查断面、糙率、淤积和设施设置。

扩大疑似管段后，也可能只是将问题推向下游。因此应同时评价局部改善和全网后果。

**4. 第三类：下游水位约束了排水，上游发生回水和溢流。**

这是典型的“水不一定更多，但更难排出去”。

例如河道或排口水位升高，排水可用水头差减小；上游水位被抬升。严重时可能发生倒流，也可能没有倒流，仅表现为出流减小和水位升高。

应沿通往排口或控制设施的路径查看：

- 下游边界水位；
- 沿途节点水头与管道流向；
- 上游入流、末端出流和蓄水变化；
- 受压、溢流发生的时段。

“下游先升、上游后升”是有价值的线索，但不是充分证明。共同降雨也可能同时抬高河道和管网水位；水力变化传播较快时，报告时步还可能分辨不出先后。

更有区分力的试验是：保留同一来水过程，在合理范围内改变下游边界，比较目标溢流是否明显减轻。结论应表述为“对该边界变化敏感”，再结合其他证据判断其作用。

**5. 第四类：排水设施的实际运行限制了排水。**

泵站、闸门和其他控制设施会使排水能力随时间变化，不能统一当成一根固定能力的管道。

这里至少要区分两种情况：

| 情况 | 需要解释的问题 |
|---|---|
| 设施持续运行，但排水仍不足 | 实际工况下的输送能力是否不足？ |
| 设施具有潜在能力，却未及时发挥 | 启停阈值、调度、闸门开度或运行状态是否造成限制？ |

泵站分析应结合湿井水位、实际泵流量、启停状态、上下游水头和泵曲线。泵的出流取决于模型采用的泵类型与工况，不能直接拿铭牌流量作为全过程实际排量。[EPA SWMM 水力手册补充说明](https://www.epa.gov/system/files/documents/2022-02/swmm5-reference-manual-ii-addendum-20220210mas2wr-1.pdf)

频繁启停可以造成真实水位波动，但它也可能是来水变化的响应。要认定它加重溢流，需要证明运行过程减少了关键时段的排水，或者合理调整控制规则后后果改善。

所以，“泵频繁启停”和“数值振荡”不能在诊断中混为一谈。

**6. 第五类：可利用蓄量不足，或在后续雨峰到来前已经被占用。**

这种机制解释一个常见现象：

> 为什么第二个雨峰比第一个小，却造成了更严重的溢流？

因为系统具有“记忆”。第一轮来水后，管网、湿井或调蓄设施中的水尚未排空，第二轮来水到达时，剩余空间已经减少。

需要检查的是：

- 事件初始水位和蓄量；
- 各雨峰之间是否充分退水；
- 入流与出流差额的累计量；
- 关键节点和设施在第二轮来水前的状态。

验证时可以比较不同初始蓄水状态，或在有工程依据时比较不同预排、调蓄方案。不能只看峰值流量，也不能直接把管道几何总容积当成安全可用蓄量——某个低井口可能在整个系统“装满”之前就先溢流。

**7. 第六类：局部节点的溢流高程较低，成为系统先出水的位置。**

这一类特别重要，因为它解释的是**为什么在这里溢流**，而不仅是为什么系统水位升高。

在相近水头下，井口较低的节点可能先达到溢流条件。它不一定连接着最小的管道，也不一定具有最大的上游来流。

应检查井口、地面、管底和管顶高程，以及相邻节点的水头和剩余高程余量。

但需要区分：

- **水头为何升高**：可能仍由集中来水、局部约束或下游顶托造成；
- **为何这里先溢流**：可能由局部低高程决定。

抬高这个井口后，本地溢流减少，也可能把水位和溢流转移到其他节点。因此，不能把“封住最先冒水的井”自动当作解决方案。

**8. 管网为何溢流，与地面为何在某处形成严重积水，是相连的两段解释。**

对应你们的 SWMM→CA2D 流程，需要分别回答：

> 哪些水力条件造成节点溢流？  
> 溢出的水为什么汇聚到热点 A，并在那里形成较深、较久的积水？

后一个问题涉及地形低洼、地表通道、阻挡和退水路径。溢流量最大的井未必对应最深的积水点；较远处的水可能沿地表通道汇入低洼区。

因此，管网机制解释应以节点事件为对象，地表后果解释应以热点为对象，再用能够获得的输水路径和时序证据连接两者。没有源追踪证据时，不能宣称某个井贡献了热点多少比例的积水。

**9. 把这些模式放回一次实际诊断，追踪就有了目的。**

假设 N 节点发生溢流，工程师并不需要先把上下游所有元素全部收集齐。可以按下面的顺序调查：

1. **确认事件与模型设置。** 核对溢流起止、体积、水位、高程，以及结果是否存在明显数值问题。
2. **查看来水和出路。** 对齐相关流量、水头过程，判断水位升高时，主要是来水增加、出流受限，还是初始蓄水偏高。
3. **提出至少两个可竞争的解释。** 例如局部输水约束与下游边界影响，不能看到第一条线索就停止。
4. **沿有证据的方向扩展。** 上游追踪来水来源与叠加，下游追踪限制排水的控制位置；若发现设施切换，则检查运行过程。
5. **选择能区分解释的检查或试验。** 每次分析前明确：哪一种结果支持哪个假说，哪一种结果会削弱它。
6. **报告结论及未排除项。** 数据只能支持候选机制时，就保留这一证据等级。

这时，“上游的上游、下游的下游”就有了明确用途：**每多追踪一个对象，都为了回答一个尚未解决的水力问题。**

我认为你论文中最值得建立的核心单元，是：

> **失效现象 → 竞争性机制 → 预期证据 → 实际检查 → 区分性试验 → 更新判断。**

例如“持续满流”只是现象；“局部输水受限”和“下游顶托”是不同解释；真正体现工程推理的，是系统知道应比较哪些水头和流量、向哪里继续追踪，以及怎样的结果会让它改变判断。

### 63. AI（回答）

时间：2026-09-16 14:09:25 +08:00；记录序号：565。

我们先把诊断对象固定下来：**某次暴雨中，一个检查井开始溢流。工程师要解释的是，水为什么在这里抬升到溢流高程，以及为什么在这个时刻发生。**

从这个具体问题出发，管径、满流、泵站、下游水位等信息，才会各自找到位置。

下面是供我们建立诊断逻辑的工程分类，不是规范中现成的“失效模式清单”；实际事件也经常是几种机制叠加。

**先抓住两个基本关系。**

对一个包含节点、相邻管段或调蓄设施的控制区域，水量平衡可写为：

\[
\frac{\mathrm dV}{\mathrm dt}
=
Q_{\mathrm{进入}}
-
Q_{\mathrm{排出}}
-
Q_{\mathrm{溢流}}
\]

溢流发生前，进入量持续超过排出量，多出来的水就要储存在系统内，并推动水位变化。储存空间及其水位—容积关系，决定水位抬升多快。

排出流量则取决于上下游水头、管道几何与阻力、设施运行，以及非恒定过程。SWMM动力波能够表达回水、受压、倒流和管渠蓄水等现象，因此这些关系必须一起看。[EPA SWMM用户手册](https://nepis.epa.gov/Exe/ZyPURL.cgi?Dockey=P10145M6.TXT)

由此，我们可以逐个梳理六类典型机制。

**① 上游来水集中，短时间内超过系统输送与调蓄能力。**

例如，几条支管的流量峰值在干管汇合，干管能够排水，但排出的速度赶不上进入的速度，沿线水位逐渐升高，最终某处溢流。

工程上应检查：

- 哪些汇水区、支管贡献了主要来水；
- 各支路的流量峰值是否重叠，重叠持续多久；
- 节点溢流之前，区域内是否已持续出现净入流和蓄水增加；
- 同期下游边界及设施运行是否发生变化。

这里最容易犯的错误是：“雨很大，所以就是来水太多。”

所有暴雨积水都有降雨驱动，但这不足以解释**为什么偏偏这个位置溢流**。还要解释来水的空间集中、时间重叠，以及它遇到了什么输水条件。

验证时，可以保持边界和设施条件一致，分别削减某支路来水，或者在保持体积的情况下调整其峰值时序。前者检验来水量的影响，后者检验峰值叠加的影响。两者回答的不是同一个问题。

**② 局部管段或构筑物形成输水约束。**

可能涉及管径变化、坡度与高程衔接、较大局部损失、淤积堵塞或设施开度等。

水到达某处以后，继续向下游输送需要更大的水头差，上游水位因此抬升。溢流井可能位于约束位置上游，而不在约束位置本身。

应重点看：

- 疑似位置上下游的水头、流量和水位变化；
- 上游是否出现明显蓄水和受压，而下游仍有较多水位余量；
- 几何、糙率、局部损失或设施设置，是否能够解释这种水力差异。

**“某根管最细”或者“某根管满流最久”，都不足以确认它是瓶颈。** 同样，两节点水头差较大也要结合流速水头、局部损失和非恒定过程解释，不能直接当成全部沿程损失。

针对性地改变该处输水条件，再检查上游溢流是否减轻、风险是否转移到更下游，可以检验其作用。若模型没有堵塞资料，就只能提出“局部阻力或有效断面受限”的假说，不能宣布现场存在堵塞。

**③ 下游水位抬高，使上游排水受阻。**

这是我们前面反复讨论的顶托机制。

即使管径没有变化，下游水位抬高也会改变可用水头差。上游为了继续排水，可能需要更高水位；还可能出现流量减小、停滞甚至倒流。

典型线索是：

- 排口或下游控制节点水位升高；
- 连通路径上的上游水位随之变化；
- 管道已经充满或受压，但流量不一定大；
- 上游来水减弱之后，水位仍因下游约束而难以回落。

不过，**“下游先升水、上游后升水”只是支持证据，不能单凭先后顺序确认因果。** 同一场降雨也可能同时推动两处水位变化，而且不同水力条件下响应时差并不明显。

较有针对性的验证，是保持上游输入一致，比较实际下游边界与一个有明确物理意义的较低边界情景，检查溢流变化。这个对比衡量的是该边界条件在本场事件中的作用，不自动证明建设某种防顶托工程就一定有效。

**④ 泵站、闸门等设施的输水能力或控制时序不匹配。**

这类机制需要进一步区分：

- 设施持续工作，仍不足以排出进入的水量；
- 设施具备能力，但启动过晚、开启不足或控制规则不合适；
- 下游水位改变实际扬程，使泵的实际出流下降。

因此，“泵开着”不能说明排水能力足够，“启停频繁”也不能直接说明控制失效。

应把水位、实际泵流量、启停状态、控制阈值和上下游水头放在同一时间轴上，判断水位波动能否由控制动作解释，以及这些动作是否增加了溢流。

这也回应了之前的振荡问题：**与泵站控制相符的周期性涨落可以是真实运行响应。** 是否属于不合理数值振荡，需要另行检查时间步敏感性、连续性误差和水力一致性。

**⑤ 可用调蓄空间不足，或者暴雨前已被占用。**

有些系统峰值来水确实大于即时出流能力，但原本可以通过管网、调蓄池等暂存水量，等峰值过去后再排出。

问题可能出在暴雨开始时水位已经很高，或上一轮降雨尚未排空，导致这次事件可用的调蓄余量很小。

识别这类机制，不能只比峰值流量，要看：

- 暴雨开始时的水位和储水量；
- 整个事件中累计净入水量如何变化；
- 可用储水空间何时被耗尽；
- 雨峰过后是否有条件排空。

一个短而尖的峰值，和一个不那么高但持续很久的来水过程，可能造成完全不同的结果。因此，**峰值压力与累计水量压力需要分别判断。**

**⑥ 局部地面或井口较低，使其成为首先溢流的位置。**

这一类尤其重要，因为它解释“为什么在这里冒水”。

同一片区域水头整体抬升时，不同节点到井口的余量不同。地面较低的节点可能先溢流，周围较高节点仍没有出井。

这意味着：

> 溢流最严重的节点，不一定就是造成输水约束的节点；它也可能是整个受压区域最先泄水的位置。

需要比较区域内的水头分布、井口高程和管顶高程，并核实高程资料。

不能因此直接建议抬高井盖或增加允许超压深度：这种做法可能只是让水转移到别处溢出，或者提高其他位置的压力。模型中“原节点不溢流了”，不代表系统问题解决。

这六类机制，可以用下面这张表建立第一层判断：

| 工程问题 | 优先考虑的机制 |
|---|---|
| 为什么进入系统的水集中在这个时段？ | 上游来水及峰值叠加 |
| 为什么水经过这里需要较大的水头差？ | 局部输水约束 |
| 为什么下游不能继续接纳或排出水？ | 下游顶托 |
| 为什么设施没有及时排出应排水量？ | 能力与控制问题 |
| 为什么短时不平衡很快转为高水位？ | 可用调蓄不足 |
| 为什么偏偏这个井先溢流？ | 局部溢流高程较低 |

实际诊断时，这些解释往往可以连接成一条因果链。例如：

> 多条支路来水叠加，使干管入流增加；同期出口水位抬高，限制排出；区域储水逐渐增加；其中地面最低的检查井首先溢流。

在这条链中，“上游来水”“下游顶托”“低井口”都发挥了作用，但回答的是不同问题。**如果问溢流量为什么增加，和问为什么由这个井溢出，所谓“主因”可能不同。** 所以，我们必须先明确主因是针对溢流发生、溢流体积、溢流位置，还是地表最大水深而言。

这也给“追到上游的上游、下游的下游以后干什么”一个具体答案：把追到的对象用于建立一段水量收支、一条水头剖面和一组事件时间线，然后比较竞争性解释。追踪范围由尚未解释的现象决定：

- 来水来源不清，就继续向上游追；
- 排水约束不清，就沿水力联系向下游追；
- 溢流位置不清，就比较周边节点高程；
