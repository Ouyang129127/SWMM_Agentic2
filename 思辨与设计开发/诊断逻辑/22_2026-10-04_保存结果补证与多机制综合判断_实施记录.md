# 保存结果补证与多机制综合判断

日期：2026-10-04。

## 目标与边界

补证基本能力：在当前已保存模拟结果范围内，按请求提取、计算并生成可追溯证据。只有确实超出保存数据能力时才提出重新模拟或其他调查。缺少 JSON 中的现成指标不等于缺少原始数据；尚无提取方法也不等于必须重新模拟。

首轮仍然从 EvidenceBuilder 的统一 JSON 开始，对全部冒溢事件先交付初步诊断。批准补证后，由同一任务执行保存结果提取、重新诊断、引用核查和新版报告交付。R1、R2 是同一任务的成果修订，不是新老两套 DiagnosisAgent。

本次没有运行 SWMM 或 CA2D，没有执行模型生成的代码，没有引入 token、字符或证据行数预算。默认时窗属于公开的工程范围约定，显式时窗可以扩展到整个保存期间，返回所有匹配样本。

## 原有缺口及实现位置

原来的 `evidence` 动作只能在不可变快照里执行 `evidence_lookup`。对于尚未预构建的储量、满度和地表时序，记录 `unavailable` 后交付初稿；没有实际提取或计算入口。

新增 `workflow_agents/saved_result_evidence.py`，负责请求校验、能力规划、读取保存文件、计算、生成证据和核对来源。`investigation.py` 的 evidence 动作负责批准后的执行与持久化；`investigation_flow.py` 负责同一任务的继续路由和重复请求判断。首轮初稿之后，原请求中的已支持指标会被重新规划；此前已结束的旧任务也可通过明确“继续”恢复补证，而无需重跑或建立另一份首轮任务。

## 支持的请求

| metric_name | 数据与计算 | 判断边界 |
| --- | --- | --- |
| fullness_time_series | 保存 links.tsv 的水深、带符号流量，圆管水深／直径 | 满度代理量，不直接证明失效、设计输水能力或原因 |
| max_fullness | 指定事件／时窗内各圆管上述代理量的最大值及其保存时刻 | 不以全场最大值替代事件最大值 |
| storage_volume_process | model.out 的原生节点、管段体积，及相邻保存时刻体积变化和平均储量变化率 | 保存状态不等于可用调蓄量；不把节点和管段简单相加作为独立控制体积 |
| local_process_series | model.out 的节点水深、水头、总入流、侧向入流、冒溢、体积，以及管段有符号流量、水深、体积、两端水头差 | 保存步长内过程和反事实因果仍不能凭此恢复 |
| ponding_depth_time_series | 保存 surface_depth.tsv 的指定网格水深；也可通过节点—网格映射请求 | 几何对应不是冒溢水源追踪，也不是管网回流证据 |

目前管网提取器支持 SI/LPS。圆管以外的断面不会猜测参考高度。缺失、非有限值或没有样本不得当作零。

原生节点体积使用 toolkit 的 `NodeAttribute.PONDED_VOLUME` 槽位，但其物理含义按 SWMM 输出的 `NODE_VOLUME` 记录解释，并非 CA2D 的地表积水量。核对依据为 [EPA SWMM node_getResults 源码](https://github.com/USEPA/Stormwater-Management-Model/blob/develop/src/solver/node.c)。实际补证记录保存所读 binary 的求解器版本和单位；提取时核对 SI/LPS，未调用 Simulation。

类型化请求示例：

```json
{
  "tool": "saved_result_extract",
  "metric_name": "fullness_time_series",
  "object_type": "link",
  "object_ids": ["G6", "G7"],
  "event_ids": ["P7:E001"],
  "time_start": "2024-01-01 01:30:00",
  "time_end": "2024-01-01 01:50:00",
  "reason": "比较起溢前后 G6/G7 的保存水深与流量过程，判断来水叠加和排出受限的同期关系。"
}
```

单对象和单事件也支持 `object_id`、`event_id`。旧诊断中的分号事件列表可兼容解析；新提示要求用数组。请求不能提供任意文件路径、代码或脚本。`reason` 只是调查目的，不会作为可执行规则或时间过滤器。旧请求未显式指定时间时，默认事件前后各扩展一个相应结果的保存步长；请求中写在 reason 里的额外时段没有被默认为执行参数，实际范围会在计划与证据里公开。

节点管网请求默认读取目标节点的直接连接管段与管段两端节点，不自动扩展全部上游。管段过程请求读取该管段和两端节点。地表节点请求对应映射网格，不自动宣称某邻近区域由该节点的冒溢造成。

`sample_interval_seconds` 表示请求需要的时间分辨率。已保存结果比请求更细时保留全部真实样本；请求比实际保存更细时明确返回缺口，不插值制造观测。显式时窗统一转换为模拟时间格式；超出保存范围标明实际覆盖，空时窗返回 no_match，不反复重新诊断。

## 持久化与可追溯性

1. 原始 `evidence/evidence_package.json` 与任务 `evidence_snapshot.json` 保持不变。
2. 批准执行后，一个逻辑请求生成一份不可变 `supplement_<内容SHA256>.json`；同一请求的多个事件放在同一文件，避免为每个节点再造一个文件。
3. 每条补证记录包含 `SUP_...` EvidenceID、模型／运行／事件、实际覆盖、完整样本、计算方法、请求范围、源文件 SHA256、缺项和解释限制。
4. `task.json` 的 supplements 清单保存补证文件名和哈希。后续加载核对文件内容、EvidenceID、运行归属和原始来源哈希；源文件变更不能继续作为有效补证。
5. 诊断、调用审计、核查、报告保存本版的 `evidence_binding`：原快照哈希、补证清单、可见 ID 和整体绑定哈希。可以追溯该修订使用了什么证据；不以当前“最新文件”冒充 R1 的输入。
6. 重复请求按对象、事件、时窗和方法的语义范围复用已有记录，既支持批量请求的单事件子集，也兼容第一批补证文件的索引。不因换一种请求写法就把重复数据算作新进展。

地表映射文件属于本次提取所用的当前静态辅助输入。它被单独约束到当前模型目录并记录哈希；不声称它是当时模拟保存的冻结映射。当前项目的 SWMM→CA2D 传递是单向的，地表水深不能证明水回流进 SWMM 节点。

空时窗或无法满足的保存分辨率作为未满足请求写入任务，保留原因，不制造证据。源文件中途改变、原生单位与声明冲突、补证内容被改动属于绑定／数据错误，会阻止提交。没有新证据时不重复调用诊断模型。

## 多机制综合判断

每个新生成的事件诊断必须提供 `joint_assessment`：

```json
{
  "status": "supported",
  "mechanism_ids": ["M1", "M2", "M4"],
  "conclusion": "来水叠加与排出受限共同作用，节点达到井口冒溢条件后发生冒溢。",
  "interaction_explanation": "把同一事件内的来水、实际排出、水头、储水及冒溢过程连接起来。",
  "evidence_ids": ["本事件的可见证据ID"],
  "limitations": "下游影响仍为候选，尚未通过反事实比较识别其贡献。"
}
```

程序检查机制 ID、状态一致性、本事件的可见引用及必要字段。supported 综合判断不能把 candidate、not_applicable 或 not_investigated 机制列成已支持原因。报告在六机制逐项判断之后增加“综合机制判断”“作用关系”“判断边界”，不只并列机制清单。

程序没有固定 “M1 supported + M2 supported ⇒ 共同致因” 规则。综合解释由模型根据本事件过程提出。两个支持标签不自动证明共同因果，来源体积占比不是致涝贡献率，引用通过也不等于水力或反事实因果验证。旧报告原样保留，不补写假装当时已经生成的综合判断。
