# 诊断链路V1总表：事件、证据、机制与Agent交接

日期：2026-09-24  
性质：工程诊断设计讨论稿，不是已实现功能清单，也不是案例结论。  
承接：02号原话记录、05号阶段共识及06号上游来水诊断模板。历史原话不改写；本文件新增内容均为设计建议，除下述明确确认项外，不视为用户已经批准具体实现。

## 1. 这次要确定的成果

不是把一个案例解释得越来越复杂，而是形成可复用的诊断组织方式：

> 给定一次模拟结果和用户问题，识别分析对象与事件，组织可追溯证据，由DiagnosisAgent选择并比较机制，由VerificationAgent核查，再由ReportAgent准确回答原问题。

已确认的来水表达口径：用户问整次事件的主要来水时，以事件体积组成为主，关键时刻流量组成为补充；明确问某个时刻时，按瞬时口径回答。此确认不等于批准全部程序实现或新增模拟。

当前优先闭合的是“主要来水路径诊断与可信交接”。下面六类机制的完整设计，为后续扩展预留共同骨架，不表示论文提交前必须实现所有分支。

## 2. 五问、四问与六类机制各司其职

保留用户的五问：

1. 水从哪里来？
2. 水在什么之后集中在什么位置？
3. 水在管网的什么位置被卡住？
4. 水为什么没有排出去？
5. 水最终从哪冒溢到地表并淹没了什么位置？

第三问实际调查“哪些位置或条件限制输送”，不预设唯一瓶颈。

一个节点事件的四问：

1. 为什么此时开始溢流？
2. 为什么这个位置溢流？
3. 为什么溢流体积大？
4. 为什么持续或反复？

六类机制是候选调查方向，而不是固定执行顺序，也不是六项得分相加得到主因。不同机制可以共同作用，同一机制对不同问题的解释力也不同。

基本分析单元：运行 × 节点 × 事件。热点另有独立标识，通过有证据的关联连接节点事件；不能把热点与最近检查井直接等同。

## 3. 七个角色如何衔接

| 角色 | 输入与工作 | 向下一环节交付 |
|---|---|---|
| StatefulOrchestrator | 保存用户原话、意图解释、运行/对象/事件/时段及确认状态；协调合法转向 | 版本化任务上下文与任务状态 |
| ScenarioAgent | 当用户确认需要新情景时，准备并检查模型、降雨及参数变更 | 可执行的已确认情景；已有结果诊断不必重新经过此步骤 |
| SimulationAgent | 执行已确认情景，登记结果与运行状态 | 运行标识、产物位置和执行记录 |
| EvidenceBuilderAgent | 按问题调用计算工具，组织拓扑、时序和指标；记录来源与计算口径 | EvidencePackage，不代替Diagnosis作机制结论 |
| DiagnosisAgent | 理解目标，选择机制调查，比较解释，形成判断及有理由的补证请求 | Claim集合、证据引用、推理说明、解释范围及下一步建议 |
| VerificationAgent | 核查对象/时段/单位/计算/证据匹配与推理是否越界 | 按Claim及版本关联的核查结果；问题退回相应环节 |
| ReportAgent | 联合原始问题、任务上下文、诊断和核查结果组织回答 | 可追溯的回答/报告；新分析需求回交Orchestrator |

BenchmarkAgent保留为评测扩展，不改变上述七角色主架构。

已有结果的通常路径是：Orchestrator → EvidenceBuilder → Diagnosis → Verification → Report。补证由Diagnosis说明目的，经Orchestrator协调回到EvidenceBuilder；新情景经人工确认后才进入Scenario与Simulation。

Verification若发现计算错误，回到证据构建；若发现解释越界，回到Diagnosis。依赖内容修订后重新核查，不能沿用旧版通过状态。

## 4. 六类机制诊断总表

表中“判断”是拟支持的诊断输出类型，不是本案例已成立的结论。

| 调查方向 | EvidenceBuilder准备的核心证据 | Diagnosis需要比较什么 | Verification重点 | Report可表达的成果 |
|---|---|---|---|---|
| ①上游来水集中与峰值叠加 | 直接连接与实际流向；侧向入流；来源时序；关键时刻流量组成；事件进入体积；局部峰和较大来水时段 | 哪些路径构成主要来水；上升与汇入过程如何对应冒溢起始、峰值和持续；是否有时间重叠 | 分母、方向、重复计数、时间窗；瞬时占比与体积占比是否混用 | 主要来水路径及其时间作用，明确对应时刻或事件 |
| ②局部管段或构筑物输水能力受限 | 上下游水头时序与统一基准高程；流量/水深；几何、连接及设施属性；局部蓄排变化 | 来水增加时，出流与水头差如何变化；候选约束在何处；局部属性与下游水位作用哪个解释更吻合 | 是否只凭满流、管径小或出流平台即认定瓶颈；是否忽略水头和流向 | 有证据支持的受限位置及过程表现；结论强度随证据明确 |
| ③下游水位顶托 | 下游相邻及必要更远节点水头；上游响应；连接管流量/方向；出口边界类型及可用边界序列 | 下游水位变化是否通过相连路径影响排出条件；与来水变化、局部约束如何区分 | 是否把同时升高当成方向证明；是否把内部回水误写为外部边界抬升 | 顶托影响的证据链、空间范围与发生时段；区分内部与外部来源 |
| ④局部地面或井口高程影响冒溢位置 | 节点地面/井底等高程与实际溢流相关设置；水头时序；邻近连通节点相应属性 | 在该次水头分布下，为何该处先或更容易冒溢；是地面条件还是局部水头更关键 | 是否误用深度代替绝对水位；是否只按井口高低排序；是否把低井口当成持续冒溢的完整解释 | 对“为什么在这里冒溢”的解释，随后另接地表传播分析 |
| ⑤泵闸能力与控制时序 | 设施是否存在；状态/流量/前后水位；控制规则及实际动作；有记录时提取启停 | 动作与来水、水位变化的先后关系；实际排水表现是否符合控制条件；是否存在值得验证的调整方向 | 不把频繁启停自动当故障；不把水位波动一概当数值问题；没有状态记录时不虚构动作 | 已观察的运行响应及与冒溢的关系；优化建议与效果预测分开 |
| ⑥初始蓄水与可用调蓄空间 | 初始水位/储量；有效几何或储量关系；事件蓄量及进出流；连接和运行约束 | 雨前已占用多少空间；储量如何变化；可接纳的空间是否在关键时段可达且可用 | 不把全网几何空容积直接视作可调用调蓄；不混用井上蓄水和管网/设施内部储水 | 初始状态与蓄排过程对事件的解释；新增调蓄效果须另行检验 |

共同要求：每条判断绑定明确问题与证据，不用六类机制标签替代具体推理。

## 5. 拿到上下游元素之后，究竟干什么？

不是继续无限扩展拓扑，而是把这些元素组成“同一事件的过程对照”。

### 5.1 先建立事件背景

对目标节点提取冒溢开始、峰值、结束及是否存在分段。分析窗口应包含必要的冒溢前后过程；具体前后扩展长度由任务与已有结果决定，不在本稿硬设固定分钟数。

在同一时间基准下准备：

- 各来水路径与侧向来水；
- 目标节点入流、出流、储量或可用储量变化；
- 目标及相邻节点水头；
- 下游排出条件；
- 若存在，设施动作与储量状态。

有足够数据时核对局部水量收支；不能把“入流减出流”未经储量及其他交换项核对就全部解释为冒溢。

### 5.2 围绕四问比较过程

| 四问 | 要比较的过程 | 需要避免的跳步 |
|---|---|---|
| 为什么此时开始？ | 起溢前后的来水变化、排出条件、水头和可用空间 | 只看洪峰一帧解释整个起溢过程 |
| 为什么这个位置？ | 连通节点的水头与各自溢流相关高程/设置、局部连接条件 | 只挑最低井口或最近热点 |
| 为什么体积大？ | 事件累计来水、排出、储量变化和冒溢体积 | 用最大瞬时流量或一次占比解释累计体积 |
| 为什么持续或反复？ | 分段来水、排水条件恢复、设施动作和蓄排恢复 | 把每次短暂中断机械地解释成独立致灾机制 |

### 5.3 再决定是否追踪更远

每次扩大范围，Diagnosis必须说清楚：

> 当前在回答什么问题；现有证据在哪一步不足；要查看哪个对象、什么时段、什么变量；补证可能区分哪两种解释。

例如：为区分目标节点出流受局部条件限制还是受下游水位影响，先补齐相邻下游节点的水头；若该节点水位变化本身仍需解释，再追踪其下游。上游扩展则服务于汇流来源、变化传播等具体问题。

停止条件建议：问题已在当前范围回答；某分支经设施清单判定不适用；可用产物不足以推进且需用户选择；或达到本次确认范围。不要用固定拓扑层数代替工程判断，也不要无限追踪。

## 6. LLM如何深度参与，而不是只写结尾

以下为拟实现的行为约束，并非宣称当前代码已具备。

1. 理解问题：区分“主要来水”“冒溢位置”“致灾机制”“改善措施”等不同任务。
2. 制定调查：围绕四问选择候选机制和所需证据，说明原因。
3. 解释证据：读取计算工具产生的事实，比较竞争或共同作用的解释。
4. 调整判断：遇到不支持原假说的证据，修订解释并保留修订理由。
5. 提出有目的的补证：提交对象、变量、时段、方法及预期区分目标。
6. 回答追问：Report可重新组织已有经核查内容；需要新判断时回到Diagnosis。

确定性程序负责数值计算、单位/时间对齐、工具参数校验及流程状态约束。LLM负责问题驱动的调查和解释，但不自行编造数值、证据和模拟结果。

建议保留可供论文检验的过程记录：用户问题 → 调查理由 → 工具请求 → 返回证据 → 诊断修订 → 核查结果 → 最终回答。创新性应通过这些实际行为和效果来展示，不能只靠角色名称或报告语言。

## 7. 主因与次因：先锁定所解释的结果

同一事件可能分别有“决定冒溢位置的条件”“影响冒溢开始的过程”“影响总量与持续的过程”。不要先给全事件贴一个主因标签，再用它回答所有问题。

建议输出层次：

- 事实层：指标、时序、拓扑和属性。
- 过程诊断层：主要来水路径、排出受限表现、空间与时间关联。
- 机制解释层：比较候选解释，给出适用问题及支持/冲突证据。
- 效应验证层：在经确认的对照或敏感性分析中，评价改变条件后的指标响应。

若要进一步排序主次，先明确目标指标、候选机制、比较方式及证据要求。例如“影响冒溢体积”与“决定冒溢位置”不能混用一套排名。对照中的单项改善幅度也不自动等于可相加的因果贡献率，机制间可能存在交互。

本轮不制定主因分数、固定置信度阈值或自动对照模拟。报告优先正面表达实际取得的过程诊断成果，而不是用未经检验的主因标签填满章节。

## 8. 从节点事件接到地表淹没后果

六类机制主要解释管网侧过程；第五问还需要地表结果承接。沿用已确定的无回流研究边界，本轮不扩展耦合方式。

拟建立热点记录：

| 内容 | 必须明确的口径 |
|---|---|
| 热点编号 | 与运行、识别方法和输出版本关联 |
| 坐标位置 | 坐标系及位置代表方式，如最深点或区域中心 |
| 淹没面积 | 是某时刻面积、最大瞬时面积，还是事件淹没范围；注明水深阈值 |
| 淹没深度 | 最大水深及位置/时刻；若给平均值，说明空间和时间范围 |
| 淹没时间 | 超过约定阈值的起止、累计持续时间与是否分段 |
| 关联冒溢节点 | 关联依据、冒溢过程及传播证据；不能仅凭距离认定来源 |
| 数据来源 | CA2D产物位置、网格与时间信息、计算方法 |

若现有产物没有来源示踪或等效可验证方法，不生成多节点“致淹占比”。先呈现已支持的淹没特征与关联传播线索，再决定是否扩展来源归属分析。

本表为数据要求，不是已检查当前输出齐备。阈值和热点识别方法尚需在实现前确定。

## 9. 分支状态与报告表达

建议区分：

- 适用且已分析；
- 适用但尚需证据；
- 模型结构中不适用；
- 当前确认范围内尚未开展。

“模型无泵站”可支持泵站分支不适用；“没发现泵站数据文件”不支持该判断。“有文件”也不等于数据足以解释机制。

Verification通过意味着该版本判断通过规定核查，不等于机制已获得独立实验验证。Report保留解释目标、对象、时段和证据范围，不自行增加因果排序或优化效果。

## 10. 最小验收集与近期实施顺序

| 顺序 | 要完成什么 | 可检查的成果 |
|---|---|---|
| 1 | 核对现有代码与本设计的实际差距 | 七角色实际入口、现有接口、缺口及最小修改清单 |
| 2 | 打通单节点事件的来水诊断交接 | 原问题、EvidencePackage、Claim、Verification、回答可逐条对应 |
| 3 | 测试追问与纠错 | 瞬时/事件口径切换；主因追问正确转交；错对象/错时段被发现 |
| 4 | 联合设计局部输水约束与下游顶托的区分 | 水头—流量过程证据表、竞争解释及补证请求；先不自动重跑 |
| 5 | 按已实现能力形成论文材料 | 架构图、事件证据图、交接示例和实际测试结果，不填虚构完成项 |

优先保证第2—3步形成一个真实可运行、可核查、可交互的闭合流程，再扩展机制覆盖面。第4步属于下一阶段，不要求本轮穷尽案例。
