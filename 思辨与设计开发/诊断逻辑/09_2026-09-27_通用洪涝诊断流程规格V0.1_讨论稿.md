# 通用洪涝诊断流程规格 V0.1（讨论稿）

日期：2026-09-27  
用途：将近期水力学讨论归并为多Agent工作流的通用设计依据。  
状态：设计规格，不是已实现功能、已通过测试或论文方法完成声明。  
范围：只整理逻辑与交接；不修改代码、模型和旧运行产物，不调用项目LLM，不开展案例分析或新模拟。

## 0. 接续说明：本稿纠正什么

用户明确纠正：目标是构建并完善通用多Agent诊断工作流，不是完善某个事件的分析报告；不能将仅有上游来水模块的实现当成完整诊断框架成立。

因此，本稿在设计推进顺序上取代07号第10节、08号末尾“立即开始任务契约与P6来水包实现”的建议。保留原文件，避免改写历史。08号代码核查仍是2026-09-24的静态检查快照，本稿没有重新检查代码。

当前顺序：统一完整工程推理关系 → 审定关键执行约定 → 对照真实接口形成实现任务 → 分阶段开发和验证。案例仅用于验证通用逻辑，不把节点名称、时间和占比写成规则。

## 1. 已形成的方向与本稿新增建议

### 1.1 已形成的共同方向

- 五问组织整体洪涝过程，四问明确节点事件的解释目标，六类机制提供调查方向。
- 来水、排出、储水和冒溢条件共同组织工程解释。
- 机制可以共同作用，局部约束与下游顶托可能位于同一作用链不同位置。
- 来源占比、过程关联、机制解释和干预效果是不同结论，不相互替代。
- 前四类机制重点展开；泵闸和初始蓄水/调蓄保留基本检查，不深入控制或调蓄优化。
- 事件主要来水默认以事件体积组成为主、关键时刻流量为辅；明确问瞬时时按瞬时口径。
- 保持StatefulOrchestrator加六个工作环节Agent的七角色架构，BenchmarkAgent为评测扩展。
- LLM参与调查选择、解释比较和修订，不只是将规则结果改写成自然语言。
- 有人在回路，既有无回流研究边界不变，暂不做新前端。
- 当前不修改程序。

### 1.2 本稿新增的组织建议

阶段编号、交接包名称、调查记录结构、确认粒度和验收情形均为本稿提出的设计，不冒充既有接口或逐字共识。具体阈值、算法、字段类型及代码映射尚未定稿。

## 2. 工程问题层次

### 2.1 五问：保持用户原表述

1. 水从哪里来？
2. 水在什么之后集中在什么位置？
3. 水在管网的什么位置被卡住？
4. 水为什么没有排出去？
5. 水最终从哪冒溢到地表并淹没了什么位置？

第三问调查输送受限的位置或条件，不预设唯一卡点；第五问需要管网冒溢与地表传播共同回答。

### 2.2 四问：节点事件的解释目标

1. 为什么此时开始溢流？
2. 为什么这个位置溢流？
3. 为什么溢流体积大？
4. 为什么持续或反复？

并非每个用户问题都要求回答全部四问。完整事件诊断应记录四问各自的回答状态；简单来源查询不强制升级为完整机制调查。

### 2.3 六类候选机制

M1 上游来水集中与峰值叠加。  
M2 局部管段或构筑物输水能力受限。  
M3 下游水位顶托。  
M4 局部地面或井口高程影响冒溢位置。  
M5 泵闸能力与控制时序。  
M6 初始蓄水与可用调蓄空间。

这些编号只便于记录，不表示执行次序、优先级或因果排名。M4解释水头过程为何在某处表现为冒溢；地表积水传播另行承接。

## 3. 共同入口与任务边界

| 用户入口 | 第一项工作 | 不得默认的事情 |
|---|---|---|
| 整场模拟 | 明确是筛查、对象排序，还是完整诊断；列出候选事件和选择依据 | 自动把风险最高对象替换成用户唯一关心对象 |
| 指定节点 | 检查是否冒溢、有哪些分段，绑定事件或比较范围 | 节点全年/全场汇总等于某次事件 |
| 地表热点 | 明确热点及时间范围，建立与节点事件的可核查关联 | 最近检查井就是主导来源 |
| 已有结论追问 | 判断能否由当前经核查内容回答，或是否需要新分析 | Report在解释文字时自行增加机制结论 |
| 措施/情景请求 | 明确改变什么、评价什么，并进入新的确认流程 | 来源占比可直接换算为减灾效果 |

任务上下文至少保留：原始问题、意图解释、模型与运行、对象/事件集合、四问目标、事件窗口、过程窗口、统计口径、确认范围与版本。

分段默认保留，不自动合并。没有冒溢时，不构造冒溢事件和主因；返回事实，是否调查临界状态由任务范围决定。

## 4. 统一流程：八个阶段

以下是拟议的任务级流程，不能直接替换现有run级状态机。

| 阶段 | 负责角色 | 工作与输出 | 进入下一步的条件 |
|---|---|---|---|
| S0 明确任务 | Orchestrator | 绑定问题、对象、事件、范围和确认状态 | 用户意图及执行范围明确 |
| S1 建立共同背景 | EvidenceBuilder | 基本事实、时序、属性、数据可用性和来源 | 足以开始相应问题分析，或明确列出缺项 |
| S2 制定调查 | Diagnosis | 选择相关机制，说明支持线索、竞争解释和需要的证据 | 提交用户确认的调查计划 |
| S3 执行补证 | Orchestrator协调EvidenceBuilder | 受允许工具计算，返回证据或明确失败/缺项 | 只执行已确认范围；超范围返回确认 |
| S4 比较并修订解释 | Diagnosis | 形成Claim、支持/冲突证据、解释范围及继续/停止理由 | 可以提交核查，或回到S2/S3 |
| S5 独立核查 | Verification | 数值/对象/时段/版本/引用及解释范围检查 | 通过的部分可发布；错误退回对应角色 |
| S6 回答问题 | Report | 面向原问题组织经核查结果，保留引用 | 不新增未经核查的机制判断 |
| S7 处理追问 | Orchestrator与Report/Diagnosis | 复用已有结果，或创建关联的新调查任务 | 原对象和问题范围得到保留或明确变更 |

人工确认建议：每个有工程含义的阶段保留确认点；同一证据提取步骤中的批量计算可作为一次确认的工具包执行，不要求用户逐行批准计算。更改目标/事件、扩大调查范围、新模拟、修改参数必须重新确认。此粒度尚待用户审定，不将“继续”视为无限授权。

补证返回同样缺项且没有新来源时，不重复循环；给出可用成果和待决问题。运行次数或工具预算需后续配置，本稿不设任意固定次数。

## 5. 共同证据背景

最低限度是明确下列信息的可用状态，不是缺少任意一项就阻止全部分析：

1. 目标节点冒溢开始、峰值、结束、体积、持续及分段。
2. 局部连接、实际进出方向、节点/管段/设施属性、冒溢相关设置。
3. 各进入和排出路径的时间过程，侧向入流及可用收支校核项。
4. 目标与相关相邻节点水头；有可用数据时记录储量过程。
5. 变量单位、时间基准、事件与过程窗口、源文件、计算方法和版本。

在边界明确且交换项完整时，用“进入－排出＝储量变化＋冒溢”组织水量核对。质量守恒用于检查数量和过程，不能单独定位致因。管道储量、设施储量及其他交换项不能因未取得而被默认为零。

所有行标明已取得、缺失、不适用或未开展。未知不得转换为正常或排除。

## 6. 六类调查分支的证据要求

下列为调查与审查要求，不是自动充分条件；不可直接写成满足N项即判定原因。

### M1 上游来水集中

- 线索：关键时段入流增加、来源占比较大、多来源较大来水过程重叠。
- 调查：实际进入方向、来源覆盖、侧向入流、瞬时组成与事件体积、来水与出流/储水响应。
- 比较：主要来源与集中形成不是同一判断；来水增加与排出受限可共同作用。
- 输出：主要来水路径、集中时段和汇入过程；对冒溢作用的解释必须引用相应排出/储水证据。
- 禁止跳步：来源比例＝冒溢贡献率；最大来源＝瓶颈；削减来源可按比例削减淹没。

### M2 局部输水受限

- 线索：相关位置满流、水头抬升、出流响应有限、断面或构筑物变化。
- 调查：几何与连接、局部及沿线水头、流量时序、上游蓄水/冒溢对应。
- 比较：下游条件、设施控制及非恒定过程；不能只按满流或流量平台判定。
- 输出：本次工况下受到证据支持的约束位置和作用过程。
- 禁止跳步：小管径＝瓶颈；满流＝失效；实际出流＝固定最大能力。

### M3 下游顶托

- 线索：较高或变化的下游水位，以及相关的流量/水头响应；高水位可能持续存在。
- 调查：连通路径、水头空间分布、排出响应；必要时继续追踪高水位的形成位置。
- 比较：上游来水、局部约束及共同驱动；下游先涨或发生倒流均不是必需条件。
- 输出：下游条件影响目标排出的过程、时段及相关路径；区分内部回水和外部边界作用。
- 禁止跳步：同步升高＝因果；下游满流＝外部边界顶托；未倒流＝无顶托。

M2与M3应允许联合调查。某处局部约束可以形成水位抬升，再向上游表现为顶托；不强制互斥分类。

### M4 冒溢位置条件

- 线索：部分节点先冒溢或表现不同，冒溢相关高程/水头余量存在差异。
- 调查：实际溢流相关设置、同基准水头、连通节点的相对条件。
- 比较：控制高程较低、水头抬升较大或二者共同作用。
- 输出：解释为什么该位置触及冒溢条件；与M1—M3等水头形成过程连接。
- 禁止跳步：全网最低节点必先冒溢；冒溢点即瓶颈；低井口独立解释长持续或大体积。

### M5 泵闸（基本覆盖）

- 先确定设施是否存在且与任务相关。
- 有关时提取可用状态、流量、前后水位、控制规则及动作记录。
- 比较动作与蓄排变化；频繁启停不自动等于故障，没有记录不等于运行正常。
- 输出基本运行表现及值得后续调查的问题，不深入最优控制或宣称措施收益。

### M6 初始蓄水与调蓄（基本覆盖）

- 检查初始水位/储量及事件蓄排过程，关注与目标连通且实际可接纳来水的空间。
- 区分几何剩余空间与本时段可利用空间；无专门调蓄池不等于无管网储水。
- 输出初始状态与缓冲过程的基本解释，不深入预排优化与调蓄规模设计。

## 7. 判断、反证与停止条件

### 7.1 每条解释的审查维度

- 对象与路径是否相关；
- 时段与过程是否匹配；
- 解释是否符合所观察的水力过程；
- 足以改变判断的竞争解释是否得到必要检查。

记录支持和冲突证据。只有在观测范围/数据确实能识别某现象时，其未出现才可能作为反对某解释的证据。

以上不是自动因果证明。区分事实、调查线索、过程解释、主次排序与干预效果。

### 7.2 停止状态

| 状态 | 后续行为 |
|---|---|
| 当前问题已回答 | 提交核查，回答用户 |
| 过程解释已形成但有待区分环节 | 报告已有成果，列出具体待区分环节及可选调查 |
| 现有产物不足 | 说明缺什么、为何影响问题、怎样补证，交用户决策 |
| 超出确认范围或需要新情景 | 停在确认点，不自动扩展或重跑 |
| 该分支不适用 | 记录模型/连接依据，结束该分支而非整个任务 |

不以“解释语言顺畅”、检查项数量或固定拓扑层数作为停止标准。达到任务预算但尚未回答，也不能标记已解决。

主因/次因排序尚未定稿：必须先明确解释结果、候选机制、比较方法。未完成排序不妨碍输出明确的来源与过程成果，不强行填主次标签或高置信度。

## 8. Agent之间交什么：概念契约

| 交接内容（拟议名称） | 必要内容 | 所有权与边界 |
|---|---|---|
| TaskContext | 原问题、意图、运行/对象/事件、窗口、范围、确认与版本 | Orchestrator维护；摘要不能替代用户原话 |
| EvidencePackage | 事实、时序引用、计算口径、来源、覆盖/缺项、版本 | EvidenceBuilder计算组织，不生成致因结论 |
| InvestigationRequest | 对应四问、候选机制、已知线索、竞争解释、请求变量/时段/对象及用途 | Diagnosis提出，Orchestrator协调确认 |
| DiagnosisRecord/Claim | 判断类型、文本、证据、支持/冲突、替代解释、适用范围及停止/补证理由 | Diagnosis形成并修订；不是要求保存模型隐藏思维，只保存可审查的工程理由 |
| VerificationRecord | Claim及证据版本、检查结果、问题与允许发布范围 | Verification独立核查；不暗改Claim |
| ReportResponse | 原问题对应回答、经核查Claim引用、下一步需求 | Report组织语言，不新增诊断 |

证据更新后，依赖的Claim与核查状态需要重新评估；核查执行完毕不等于所有Claim通过。部分通过与未知类型不能自动当作全部通过。

LLM在Diagnosis中负责调查和解释，在EvidenceBuilder中组织受允许的工具请求，在Verification中辅助审查解释范围，在Report中理解并回答问题。数值计算、单位与时间检查、版本和权限由程序约束。上述为目标设计，不宣称每个现有阶段已具备LLM执行层。

Scenario负责已确认新情景的准备，Simulation负责执行与产物登记；既有运行诊断不必重新经过这两步。

## 9. 地表后果承接

热点独立记录编号、坐标与坐标系、面积口径、水深指标、起止和持续时间、阈值、网格与时序来源。将节点冒溢与地表传播证据连接，保持无回流边界。

邻近、同期或体积相近本身不能直接构成来源分配方法。现有证据只支持关联时，不生成来源占比；没有示踪或其他可验证归属方法时，不给出“某节点贡献热点淹没X%”。

地表关联缺失只限制相应淹没解释，不阻断已经有证据的管网过程诊断。

## 10. 实现前验收情形：验证通用性，不围绕P6定制

这些是待构建的测试要求，不是已运行结果，也不是新增模拟授权。

| 情形 | 预期行为 |
|---|---|
| 相同节点多个冒溢分段 | 保留事件区分，按确认范围回答 |
| 相同证据问瞬时来源或事件来源 | 正确选择流量/体积口径 |
| 管段倒流、侧向入流或来源缺项 | 正确标记方向、避免重复计数并说明覆盖范围 |
| 满流但未冒溢 | 不自动判成冒溢失效 |
| 下游持续高水位而非先涨 | 仍能保留下游影响调查方向 |
| 更下游约束导致目标处顶托 | 允许关联机制解释，不强迫二选一 |
| 较低井口但水头余量较大 | 不仅按高程判定最先冒溢 |
| 没有泵闸或专门调蓄池 | 区分不适用与无数据，保留管网储水检查 |
| 用户只问来源，随后追问主因 | 第一问不强制六分支全查；第二问进入新的机制调查 |
| 用户指定节点而排名首位是别处 | 不自行替换对象 |
| 引用错事件、错单位或旧版本 | Verification识别并退回 |
| 补证失败或反证出现 | 不编造事实，不无限重复请求，修订或停在决策点 |
| 热点来源关联不足 | 不默认最近节点，不生成无依据贡献率 |

可先用小型人工构造的数据验证计算/路由逻辑，再用既有真实运行验证兼容性；合成测试不替代模型案例验证。

## 11. 尚需定稿的三组执行约定

1. 事件与窗口：分段识别、间断如何处理、用户未指定事件时怎样选择、过程窗口如何扩展。
2. 调查与人工确认：一次确认允许的工具范围、补证的确认粒度、跨阶段与追问路由、无进展时停止方式。
3. 判断与核查：哪些结论类型首期发布、必需证据组合、数值容差及语义核查方式；主次排序单独设门槛。

本稿建议：先共同审阅完整流程与以上三组约定，再按通用功能拆分开发，不再先做一个特定节点的上游诊断后宣称整体逻辑完成。
