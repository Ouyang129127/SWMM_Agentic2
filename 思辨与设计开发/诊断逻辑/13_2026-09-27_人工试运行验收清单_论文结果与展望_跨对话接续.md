## 1. 最后到底要交付什么

### 1.1 本文核心成果

一个以自然语言问题启动、由人逐步确认、使用可追溯模拟证据开展工程诊断的工作流：

用户问题 → 明确模型/运行/对象/事件 → EvidenceBuilder组织证据 → Diagnosis开展机制调查与解释 → Verification检查引用 → Report面向原问题表达结果 → 用户追问后进入下一次有边界的调查。

LLM不能只是把规则输出润色成文字。它应该参与：

1. 理解当前要回答的是全局评估、节点事件解释还是某项追问。
2. 在四问与六类机制框架下比较来水、排出、储水及冒溢条件。
3. 组合多条证据，提出有依据的解释、竞争解释或共同作用。
4. 指出下一项调查需要什么证据、用于区分什么解释。
5. 根据补证或引用核查反馈修订结论。

程序负责可重复的计算、数据提取、事件划分、范围约束、证据编号、引用核查和状态控制。不能把未经测试的模型输出当作工程真值。

### 1.2 用户最终应能拿到的东西

| 成果 | 应包含什么 | 本轮定位 |
|---|---|---|
| 模拟与动态淹没结果 | 可定位到具体运行的SWMM结果、CA2D时序、动态淹没图及静态深度图 | 复用已有结果，核对绑定关系 |

## 2. 已确认的诊断骨架：不要换一轮对话就重写

### 2.1 五个底层问题（保留讨论原意）

1. 水从哪里来？
2. 水在什么之后集中在什么位置？
3. 水在管网的什么位置被卡住？
4. 水为什么没有排出去？
5. 水最终从哪冒溢到地表并淹没了什么位置？

第三问用于寻找输送约束，不预设只有一个“卡点”。五问贯穿全过程；不要求每条简单查询都写一篇五问报告。

### 2.2 拿到一个冒溢节点后的四问

| 编号 | 工程问题 | 需要组织的证据方向 |
|---|---|---|
| Q1 | 为什么在这个时候开始冒溢？ | 入流变化、水头抬升、排出变化、边界或控制变化的时间关系 |
| Q2 | 为什么在这个位置冒溢？ | 节点高程/设置、相邻水头、局部连接、可用冒溢条件 |
| Q3 | 为什么冒溢量这么大？ | 事件内来水、排出、储水变化及持续冒溢条件 |
| Q4 | 为什么持续这么久，或反复冒溢？ | 多次过程、排水恢复、持续约束、来水峰值及可能的控制作用 |

不是“只追踪上游”四次。对节点的调查应同时考虑来水、排出、储水和水头/冒溢条件。

### 2.3 六类机制及本文深度

| 编号 | 机制 | 本文预期深度 |
|---|---|---|
| M1 | 上游来水集中与峰值叠加 | 重点：组成、方向、时序及事件尺度解释 |
| M2 | 局部管段或构筑物输水能力有限 | 重点：结构与过程共同判断，不以满流单指标判定 |
| M3 | 下游水位顶托 | 重点：水头关系、输送变化、上下游过程；同步不能单独证明因果 |
| M4 | 低地面或井口决定溢流位置与径流扩散 | 重点：位置解释；地表扩散关联能力另行核实 |
| M5 | 泵闸能力和控制顺序 | 基本适用性/运行检查；不承诺控制优化 |
| M6 | 初始蓄水和可调用的调蓄空间 | 基本设置与状态检查；不承诺完整调蓄优化 |

六机制不是互斥标签。局部约束可能表现为其上游的顶托，来水集中也可以与排出约束共同作用。

“六组首轮证据”与“六类机制”不是一一对应，更不等于六类机制均已验证。

### 2.4 关键表述约定

- 满流不自动等于失效、承压或瓶颈；负荷不能按“非满流→满流→承压”简单排一个单调等级。
- 来源份额回答“水从哪里进入”，不直接回答“哪个因素导致多少冒溢”。
- 单点水深、单个流量峰值、单段长期满流都不能自动生成主因。
- 允许输出明确的过程解释，例如“主要来水路径”“排出受限的过程特征”“共同作用机制”；不要求所有结论都降格成空泛的“可能”。
- 主因/次因排序必须写明比较依据、作用阶段和竞争解释；当前没有已验收的通用自动排序方法。
- 仅凭观察不能给出未经评估的改造收益，例如“扩容该管段一定无效”。
- 振荡先检查是否有对应的降雨、边界、泵闸控制或水力变化；真实过程也可能波动，不能“有振荡=模型不可信”。
- 不把缺失、未提取、未调查当作不存在或已排除。

## 3. 七角色分工与当前实现边界

七角色是 StatefulOrchestrator + 六个业务Agent，不是七个业务Agent再加协调器。

| 角色 | 应负责 | 不应越权 |
|---|---|---|
| StatefulOrchestrator | 保存原问题、绑定运行/任务/对象/事件，组织确认、路由与追问 | 不静默更换分析对象，不自行完成未授权步骤 |
| ScenarioAgent | 整理并校验用户确认的情景 | 不擅自改变模型参数 |
| SimulationAgent | 执行既定SWMM–CA2D并记录产物 | 不把旧产物当作新运行 |
| EvidenceBuilderAgent | 从已有结果进行确定性加工，生成带单位、范围、方法、ID的证据 | 不依赖Diagnosis臆造基础过程 |
| DiagnosisAgent | LLM参与工程调查、机制比较、解释和修订 | 不绕过证据层读取原始结果，不伪造缺失量 |
| VerificationAgent | 当前版本检查EvidenceID可追溯性及任务/运行一致性 | 不把引用存在认证为因果正确 |
| ReportAgent | 忠实面向原问题表达当前有效诊断，保留条件和范围 | 不新造原因，不把事实升级为主因 |

BenchmarkAgent是未来评估扩展，不是当前第八个在线角色。旧CodeRunner/DataAnalyzer等辅助能力不能替代这里的职责划分。

角色名称与实现方式分开写：当前证据计算、核查和任务级报告主要由程序执行，真实LLM调查通过Diagnosis接口发生；不能写成“七个角色都已各自具备经验证的自主LLM推理能力”。本文要证明的是LLM深度参与且受证据与流程约束，而不是简单数名称。

## 6. 人工试运行：先做什么，怎么看，保留什么

### 6.1 最小顺序

1. 固定模型和run_id，先使用已有模拟结果，不更换降雨或模型参数。
2. 明确走新的LLM调查入口，还是旧运行级规则筛查；本次要验的是前者。
3. 从一个清晰的问题启动，确认系统识别的范围正确。
4. 执行一次诊断，检查返回与落盘文件。
5. 有补证请求时先看它为什么需要这些证据，再决定是否执行。
6. 无补证时进行引用核查；失败则由Diagnosis修订，不直接交Report洗掉问题。
7. 核查后生成报告，人工对照证据和原问题。
8. 再问一个追问，检验是否保留范围、是否按需回到Diagnosis。
9. 保存成功与失败记录，填第10节对齐表，再决定补丁。

不要一开始就要求系统同时完成所有热点、多轮全部机制、主次排序、改造建议和最优方案。可以先缩小任务检查链路，但缩小后的节点结果不能作为全局任务完成的证据。

```powershell
.\.venv\Scripts\python.exe run_workflow.py --model urban_drainage --run-id chicago_single_4h_80mm__baseline__20260922_221102 --investigation-action prepare --question "请对本次模拟进行首轮全局洪涝诊断，围绕四问和六类机制组织已有证据。"
```

执行诊断（会向已配置服务发送任务及可见结构化证据；由用户决定执行）：

```powershell
.\.venv\Scripts\python.exe run_workflow.py --model urban_drainage --run-id chicago_single_4h_80mm__baseline__20260922_221102 --investigation-action diagnose --task-id <实际task_id>
```

后续仍使用同一model/run/task，按返回状态将action换成evidence、diagnose、verify或report。不要把这些动作无条件写成一次连续执行脚本。修改问题要新建任务，不能拿旧task_id静默换题。

若用户决定原样重试已有失败任务，可以使用已记录的task_id；若缩小范围或修改问题，必须新建任务。现阶段不建议反复重复大上下文请求作为默认排障方式。

注意：

- 单独使用 --stage diagnosis 或旧 --until 路径是运行级旧规则流程，不证明新的LLM调查成功。
- --until现在只执行一个合法阶段后等待确认，不等于无停顿跑完。
- 当前run状态仍为RUN_READY，但证据文件已存在。不要为了“修正状态”先覆盖重建证据；先核对来源与任务绑定。
- 当前人工确认依赖显式动作和协调提示，不是完整防绕过审批系统。
- 原始模型与凭据不应随便上传；共享日志时去除API key、.env和其他敏感配置。

## 11. 补丁优先级：先修什么，不做什么

### P0：阻止核心验收的问题

- 真实请求无法返回或失败不留痕：先确认实际调用入口、错误、输入规模、客户端重试/总耗时；再由用户决定补丁和复验。
- 运行/任务状态矛盾导致误操作、走旧链路、覆盖证据或读错版本。
- 单位、流向、分母、事件边界错误。
- 无效引用仍被发布，报告新增未经诊断的判断。

### P1：尽快成为论文可用成果

- 证据投喂按问题/事件组织，避免一次塞入过长时序；保留原证据和下钻能力。摘要不能静默删去相反证据。
- 报告清楚呈现四问、机制状态、证据与范围。当前report主要逐条渲染claims，没有自动完整展示所有四问/六机制评估；是否补模板由实际输出决定。
- 明确新追问转诊断的连接；当前“请求重新诊断”的标记不等于自动完整闭环已验收。
- 对确实阻碍前四类机制的过程窗口或相邻范围缺口，补最小通用工具，不硬编码案例。
- 热点指标若作为本文承诺，则做可复用提取与图表；若无法及时完成，应与用户明确收敛论文承诺，不能以手写数字替代系统能力。
- 主次机制若作为核心结论，必须补比较依据与验证设计；不因期限紧把来源占比充当主因分数。

### P2：下一篇或后续版本

完整泵闸优化、可调用调蓄调度、多跳自适应调查、强语义/因果核查、干预模拟与定量因果贡献、复杂审批与产品化界面。

本轮不做：大规模前端重构、反复更换模型和降雨、重写所有旧文档、为某个节点单独做特殊逻辑、没有明确必要性就启动批量外部调用。

建议最小图表包：

1. 总体流程图：七角色与人确认位置，明确数据流和判断流。
2. 诊断逻辑图：五问作为工程主线、四问作为事件任务、六机制作为解释框架；不是三套平行重复清单。
3. 一组过程图：降雨/来水、冒溢、上下游水头和连接流量共用时间轴；标出事件窗口与关键判断引用。
4. 地表结果图：最大深度、必要时刻图或动态过程；热点定义成立后再标热点编号。
5. 证据—诊断—报告追溯表：原问题、Claim、EvidenceID、数值/时段、工程解释、核查状态。
6. 少量运行与交互统计表：真实成功/失败、耗时、输出、补证与修订，不把离线模拟和真实调用混在一起。

若要证明“优于规则/普通LLM”，需要另有同输入同任务的比较设计和评价标准；当前接入LLM本身不证明性能提升。可先与用户决定论文主张究竟是框架可行性还是量化优越性，再确定最小对照，不能先写提升幅度再找数据。

### 12.1 指标如何记，避免后来混乱

- 端到端完成：明确分母是预先确定的任务数；重试次数另记。生成空结论报告与生成有实质结论的报告分别统计。
- 引用可追溯：说明是按claim还是按引用计数。本版本输出字段需按实际定义引用，不能换一个分母沿用名称。
- 无claims时比例记N/A，不记100%正确。
- 工程合理性：由人工按明确标准审读，和自动ID核查分开。没有工程审读就不报“准确率”。
- 耗时：区分单次调用、整个任务、人工确认等待；失败也保留。
- 六机制覆盖：报告每类状态与依据；没有设施时有依据的“不适用”不是漏诊，也不是成功识别一次故障。
- 证据条数不是实验样本数。单个运行中的许多节点也不能不加说明当作独立城市验证。
- 当前一次超时是开发事实，应保存在实验日志；不能纳入成功耗时均值后隐去失败。

方法中的必要定义仍应清楚：保存步长事件口径、证据加工方法、引用核查范围、角色实际职责。未来工作用于说明下一步深化，不能替代对当前方法的准确交代。
