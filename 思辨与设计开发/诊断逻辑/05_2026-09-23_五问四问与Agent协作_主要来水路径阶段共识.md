## 2. 当前完成到哪里

本阶段明确的是：组织来水证据、形成有范围限定的主要来水路径判断，并由ReportAgent准确回应用户，不将来源占比升级为致涝贡献率或主因结论。

## 3. 整体分析的底层“五问”

保留用户先前表述：

1. 水从哪里来？
2. 水在什么之后集中在什么位置？
3. 水在管网的什么位置被卡住？
4. 水为什么没有排出去？
5. 水最终从哪冒溢到地表并淹没了什么位置？

解释约定：第二问关注集中时间、位置及前序过程；第三问中的“卡住”是直观说法，分析时应调查哪些位置或条件限制了输送，不预设存在唯一瓶颈。

五问用于组织来水—输送—排出—冒溢—淹没的整体过程。当前主要来水路径判断推进了第一问，并为第二问提供线索；不能据此声称第三、四问已解决。

## 4. 一个节点事件的“四问”

1. 为什么此时开始溢流？
2. 为什么这个位置溢流？
3. 为什么溢流体积大？
4. 为什么持续或反复？

四问界定需要解释的结果。来水规模、变化、时间重叠等证据可服务于这些问题，但不能将一项来水占比当作四问的共同答案。

事件基本单元保留“运行×节点×事件”；同一节点先识别各段冒溢，再判断是否属于连续水力过程。

## 5. 六类机制的位置

保留此前的候选解释：上游来水集中与峰值叠加、局部输水约束、下游顶托、局部井口高程、泵闸能力与控制、初始蓄水及可用调蓄。

六类机制是后续调查假说，不替代五问与四问，也不要求每个模型都具备所有机制。本阶段不对它们进行主次排序。

## 6. Agent协作与本阶段交付边界

主架构为StatefulOrchestrator加六个工作环节Agent，共七个角色。BenchmarkAgent为另行规划的评测扩展。

| 角色 | 当前问题中的责任 |
|---|---|
| StatefulOrchestrator | 保留用户原始问题与意图理解，绑定运行、节点、事件和任务范围；协调合法步骤与人工确认 |
| ScenarioAgent | 准备并核对情景请求，不因报告追问自动改变模型情景 |
| SimulationAgent | 执行已确定的模拟任务，不因需要解释结果而自动重跑 |
| EvidenceBuilderAgent | 构建来源流量、侧向入流、总入流、占比与时间信息，记录单位、分母、计算口径和证据定位 |
| DiagnosisAgent | 形成“在某时刻/时段，哪条路径是主要来水路径”的判断；注明尚未确定致涝主因 |
| VerificationAgent | 核查对象、时段、数值、占比分母、证据匹配，以及是否将来源判断错误升级为因果判断 |
| ReportAgent | 根据用户问题表达诊断及核查结果，解释其边界，不自行新增致涝原因或贡献率 |

EvidenceBuilder不生成致涝原因；Diagnosis不绕过结构化证据；Verification不悄悄替Diagnosis改结论；Report不在组织语言时新增诊断。

Report需要同时获得用户原始问题、Orchestrator提供的任务上下文、Diagnosis结果和Verification状态。意图摘要不能替代用户原话。

## 7. 当前建议的最小交接内容

这是待实现的内容要求，不声称已经存在对应字段或接口。

- 对应用户问题。
- 运行、节点、事件与分析时段。
- 正在回答五问/四问中的哪一问；若只是补充背景事实，应明确标注。
- 已确认事实及证据位置。
- Diagnosis判断及其适用范围。
- 尚不能推出的结论。
- Verification状态与问题。
- 是否需要进一步分析；提出需求不等于自动执行。

本例中允许输出：

> G4在P6冒溢高峰时刻提供约64%的入流，是该时刻主要来水路径。

不能自行改写为：

- G4贡献了64%的冒溢体积。
- G4是已确认的致涝主因。
- G4是瓶颈管段。
- 削减G4来水即可按相同比例减少淹没。

## 8. 当前阶段的验收口径

1. 来水路径判断有明确对象、时段、分母和证据。
2. Diagnosis将主要来水路径与致涝主因分开。
3. Verification能检查这种表达是否超出证据。
4. 用户追问“是否主因”时，Report能准确说明已有结论和未解决问题。
5. 回答始终关联五问和四问，不把案例局部事实替代完整机制解释。
6. 新的主因分析保留为后续任务，本轮不自动展开。
