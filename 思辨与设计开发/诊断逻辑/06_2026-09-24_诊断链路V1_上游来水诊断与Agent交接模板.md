# 诊断链路V1：上游来水诊断及Agent交接模板

日期：2026-09-24  
状态：供用户审定的完整首条链路；非程序实现或测试完成声明。  
目的：用一条明确链路固定取证、诊断、核查、报告和补查接口，再复用到其余机制。本轮只新增设计文档，不修改代码或运行数据。

## 1. 本阶段正面任务定义

DiagnosisAgent识别冒溢事件的主要来水路径，解析各来源在关键时段的流量组成与汇入过程，形成证据支持的来水诊断。

本定义采用9月23日后续讨论的正面表述，更新05文档中以“不得直接认定主因”为核心职责的措辞；数值、引用与推断范围的核查仍保留为内部质量要求。

整体五问组织过程，节点四问明确解释目标，六类机制组织候选调查。本链路直接回答“水从哪里来”和“何时集中到何处”，可为冒溢起始、体积和持续性解释提供来水证据。它不是其余机制的替代品。

## 2. 任务入口

以“运行×目标节点×冒溢事件”为基本单元。同一节点先分别识别各段事件，再讨论连续性。全部分析采用本次已有记录，不增加精细采样研究。

Orchestrator同时保留用户原话和结构化理解：

- task_id、question原文、model_id、run_id。
- node_id、event_id、事件来源与识别口径。
- 五问/四问目标；纯来源查询可标记为背景取证，不强行对应完整原因解释。
- analysis_window：起止时间、选取理由。
- scope：本次要完成的分析及已确认的扩展范围。
- 输出受众、详略要求、人工确认记录。

用户指定时段时优先按该时段分析；用户只问“这次事件”时，建议先提供事件整体来源组成，再补充关键时刻，不能擅自将整个事件缩为峰值瞬间。冒溢前背景窗口的长度需有理由，不设置未经确认的固定分钟数。

## 3. 七个Agent的职责保持不变

| Agent | 本链路职责 |
|---|---|
| StatefulOrchestrator | 绑定用户问题与任务状态，调度取证、诊断、核查、报告，组织补查与确认 |
| ScenarioAgent | 核对情景与输入身份；已有运行解释不自动改变情景 |
| SimulationAgent | 提供已有模拟产物；仅在已确认的新模拟任务中运行模型 |
| EvidenceBuilderAgent | 选择并调用计算工具，组织可追溯的来水及关系证据，不承担成因判断 |
| DiagnosisAgent | 解释来源规模、时序变化及汇入关系，提出有理由的补查需求 |
| VerificationAgent | 独立核查结论与证据对应、计算口径及推断范围，返回问题而非代写诊断 |
| ReportAgent | 根据用户原话、任务上下文、诊断与核查结果回答；新的分析需求返回Orchestrator |

BenchmarkAgent仍是评价扩展，不增加为本次在线流程的第八环节。LLM可参与任务理解、取证计划、诊断解释和报告组织，数值计算与对象查询由工具完成。各Agent具体调用次数和实现方式须在开发时核查，不能用角色表宣称已完成独立LLM部署。

## 4. 第一条完整链路

| 步骤 | EvidenceBuilder生成什么 | Diagnosis判断什么 | Verification核查什么 | Report可表达什么 |
|---|---|---|---|---|
| A 确认来源 | 所有直接相连管段、实际流向、侧向入流及其组成；来源口径清单 | 直接来源由哪些路径组成 | 拓扑、符号、单位及重复计数 | “目标节点经这些路径和直接入流获得来水” |
| B 比较规模 | 指定时刻的流量与占比；指定时段的正向进入体积及占比 | 主要来水路径及排序 | 分母、时段、积分方法、排名和总量一致性 | “某时刻/某时段，某路径提供了多少来水，占比多少” |
| C 比较变化 | 升水、冒溢及恢复时段内各来源曲线与增量 | 哪些路径在关键时段增加，规模排序与增长排序是否不同 | 起止时刻、变化量、方向以及是否将增量当成全事件贡献 | “某来源在这一时段增加明显，与合计来水上升相伴” |
| D 比较汇入时序 | 多来源在共同时间轴上的流量及局部峰值、用户确认阈值下的重叠指标 | 较大来水是否同时出现，是否值得进一步调查集中汇入 | 是否只靠全局峰值时差定性，阈值是否明确，所比较时段是否一致 | “在该时段，多条来水路径共同维持较大流量” |
| E 组织调查方向 | 待查询路径的拓扑、可获得变量和数据缺口 | 继续追哪条路径、希望解决什么疑问 | 补查理由能否关联用户问题，是否越出已确认范围 | “下一步沿某路径补查其上游汇入组成” |

没有确认“高流量”阈值前，步骤D直接报告流量曲线和数值，不输出假装标准化的“峰值叠加指数”。“主要”在首版中以明确排序表达，不设任意百分比作为通用工程阈值。

## 5. 指标口径

### 5.1 来源与方向

每条直接相连管段根据目标节点所在端点及有符号流量定义“朝目标节点为正”。模型From/To编号不是固定实际来水方向。直接侧向入流单列；总入流是核对项，不作为一个来源再加入来源合计。

存在负侧向入流时，单列为取水/损失方向，不混入正来水来源。环网或倒流情况下，当前来水路径不等于最终产流起源；追溯需要记录已经访问的对象，避免循环。

### 5.2 瞬时与时段指标

瞬时路径占比：该路径正向入流 / 同时刻已纳入来源的正入流合计。分母为零时占比为null并说明无正入流，不能输出0/0。

时段路径体积：对该路径正向入流在指定窗口内积分。时段占比以各路径正向进入体积之和为分母；方向反转的外出体积另记，不用净值伪装成来源比例。

上述份额描述到达节点的路径组成，不是水质示踪来源份额。以来源合计为分母时同时保留其与SWMM总入流的差异；如存在未覆盖来源，标明这是已覆盖来源内部的组成，不能宣称完整来源占比。

瞬时占比、时段体积占比、增长量、冒溢体积及方案改变后的响应是不同指标，不互相替换。超过一层的占比不能直接连乘当作远端汇水区贡献，需处理传播、储水与时间对应。

## 6. 最小交接内容

### 6.1 EvidenceBuilder → Diagnosis

EvidencePackage至少包含：

- package_id、version、task_id、run_id、node_id、event_id、window。
- source_inventory：路径、类型、方向、覆盖状态。
- evidence_rows：evidence_id、对象、变量、数值、单位、时间、来源文件与提取/计算方法。
- series_refs：可回查过程数据的位置。
- calculation_context：分母、积分与符号口径、采用的阈值。
- availability：已有、可补取、未保存、模型不适用。

EvidenceBuilder可通过LLM将需求转为工具查询计划，但工具结果与原始定位必须保留；不能仅提交一段自然语言结论。

### 6.2 Diagnosis → Verification

每条Claim至少包含：

- claim_id、task_id、所回答问题、对象与时段。
- claim_type：如瞬时来源组成、时段来源组成、来水增长特征、汇入时序特征。
- claim_text、evidence_ids、关键推理依据。
- 解释覆盖范围，以及仍需分析的部分。
- 如需补查：对象、变量、时段、问题、选择理由。

### 6.3 Verification → Report / Orchestrator

每条核查结果绑定claim_id与诊断版本，分别记录对象/时间一致性、数值/口径一致性、表达支持程度，以及明确问题和处理建议。既有supported等标签的具体语义需与代码对齐；“通过引用核查”不自动改名为“因果验证通过”。

需要修订时，经Orchestrator返回Diagnosis；需要补证据则调度EvidenceBuilder。核查者不直接替诊断者修改结果。证据或结论更新后，依赖旧版本的核查需要重新执行。

### 6.4 Report的输入

同时读取用户原话、当前任务解释、Diagnosis输出、Verification结果和相关证据。报告陈述能关联claim_id；事实补充可直接定位evidence_id。缺少完整答案时，准确回答已覆盖部分，并提出剩余分析需求，不以填满“四问”为目标补写原因。

## 7. 报告与追问示例

以下沿用既有会话中对运行chicago_single_4h_80mm__baseline__20260922_221102的读取，未在本次重新计算；仅作为设计样例，不冒充Agent已生成的输出。

用户：“P6冒溢高峰时的水主要从哪里来？”

报告：“按本次1分钟记录，01:40时G4来水约188.81 L/s，约占P6当时总入流的64%，是该时刻主要来水路径；其余来水经G5及直接侧向入流进入。”

用户：“所以G4就是致涝主因吗？”

报告：“从来水组成看，G4是该时刻的主要入流通道，因此是本轮上游追踪的重点。若进一步解释冒溢形成机制，下一步应结合该时段的下游输水条件开展联合诊断。”

用户：“那整次事件也是64%吗？”

Report先检查已有结果是否包含同一事件的体积占比：若有且已核查，引用对应结果；若没有，将“计算事件窗口的来源体积组成”交回Orchestrator，不将瞬时占比改写成整场比例。

用户：“把G4来水削减20%会怎样？”

识别为新的情景分析需求，交回Orchestrator组织方案及确认；不是Report的直接算术回答，也不自动启动模拟。

## 8. 补查与停止

本版建议：第一轮完成直接来水来源诊断；用户问题已回答且引用核查通过时，可以报告并结束该任务，不要求追到所有汇水区。

需要更远来源、时序解释或机制比较时，由Diagnosis提出补查，Orchestrator判断其与已确认范围的关系。新增调查方向及对照模拟需按人在回路要求确认。底层文件读取和一次已确认步骤内的计算不必每次另询问。

不设置未经确认的固定跳数和百分比停止阈值。数据不足、来源未覆盖与机制不适用分别标记。反复出现同一补查请求而无新增证据时，应说明当前可得结果与剩余需求，避免无限循环。

## 9. 本条链路的验收示例（待实现）

| 检查 | 预期行为 |
|---|---|
| 查询峰值时刻的主要来源 | 返回明确时刻、来源、流量及占比分母 |
| 查询整个事件的主要来源 | 使用事件体积或明确说明缺少该证据 |
| 同一管段发生倒流 | 按实际方向区分进入与外出 |
| 总入流已包含侧向入流 | 不重复计数 |
| 证据对象/时段错配 | Verification指出具体错配并返回修订 |
| 用户追问主因 | 解释现有来水诊断并衔接机制调查 |
| 用户提出新情景 | 经Orchestrator回到相应环节，不由Report虚构预测 |

## 10. 本轮需要审定的两个设计选择

1. 用户问“整次事件的主要来水”时，以事件体积组成作主结果，关键时刻流量组成作补充；用户明确问瞬时时按其要求。
2. 默认先完成直接来水来源诊断，是否扩大上游范围由问题和证据决定，经既有协调与人工确认流程推进。
