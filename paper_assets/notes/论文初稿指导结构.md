## 2. 一句话研究主线

本文面向 SWMM-二维元胞耦合城市内涝模拟，构建流程型多 Agent 诊断框架，将一次暴雨模拟产生的海量节点、管段和地表元胞时序结果转化为结构化证据、诊断 claim 与证据核查结果，从而实现可追溯、可解释、可量化可信度的洪涝灾害诊断。

更凝练的表达：

> 本研究不是让大语言模型直接读取海量模拟结果，而是先通过确定性工具将模型输出证据化、结构化和可核查化，再由 Agent 基于证据完成诊断解释与连续追问。

---

## 3. 研究背景与问题意识

城市排水内涝模拟通常会生成大量复杂的时空结果，包括检查井水深、节点溢流、管段流量、管段水深、地表积水深度和积水持续时间等。传统 SWMM 或二维地表模型能够完成数值模拟，但模拟结果本身并不直接等同于工程诊断结论。工程人员仍需从大量输出中识别风险对象、判断异常机制、追溯证据来源，并将结果解释给不同类型的决策者。

直接将模型输出交给大语言模型存在明显局限：

- 原始结果规模大，直接输入会消耗大量 tokens。
- 原始时序数据噪声高，关键风险对象容易被淹没。
- 大模型可能生成看似合理但无法追溯到具体数据行的判断。
- 图片或深度图可以展示空间分布，但难以保留对象编号、时间过程、阈值、排序和证据来源。

因此，本文提出的核心思路是：将 LLM 置于“模型软件与工程决策之间的认知组织层”，让确定性程序负责模拟执行、证据提取和规则核查，让 LLM/Agent 负责自然语言任务理解、流程组织、证据解释和交互式追问。

## 4. 对标论文迁移逻辑

对标论文面向 EPANET 给水管网开发 Agentic 系统，其对象主要是给水系统中的节点、管段、水源、泵阀等规则化网络对象。本文将研究对象迁移到 SWMM-二维元胞耦合排水内涝系统，研究对象和任务复杂性发生了明显变化。

### 对象迁移

从：

```text
EPANET 给水管网 Agentic
```

迁移到：

```text
SWMM-CA2D 排水管网-地表淹没耦合 Agentic
```

### 迁移后的复杂性

- **物理过程更复杂**：排水内涝包括降雨径流、管网汇流、检查井冒溢、地表积水扩散和退水过程。
- **模型对象更多元**：不仅有 node、link，还包括 subcatchment、rainfall event、scenario、cell、node-cell mapping 等。
- **诊断任务更开放**：不仅要回答“模型能否运行”，还要回答“哪里积水、哪里溢流、哪些管段接近满流、结论是否有证据”。

## 5. 五个核心创新点

### 创新点一：研究对象创新

本文将 Agentic 系统的作用对象由 EPANET 给水管网扩展到 SWMM-二维元胞耦合城市排水内涝系统，使智能体从处理相对规则的管网水力对象，转向处理降雨驱动、管网-地表耦合、时空动态演化的复杂洪涝模拟对象。

可写入论文的表达：

> 与面向给水系统的 EPANET-Agent 不同，本研究面向 SWMM-CA2D 耦合模型，构建适用于城市排水内涝分析的 Agentic 框架，实现研究对象从供水管网交互分析向排水-地表淹没耦合诊断的扩展。

### 创新点二：Agent 架构创新

对标论文更偏向按照模型操作动作或执行层工具能力划分 Agent；本文按照洪涝灾害评估的工作流程组织 Agent，形成“情景准备-耦合模拟-证据构建-灾害诊断-证据核查-解释报告”的流程型多 Agent 架构。

当前主链路：

```text
User / Expert Request
  -> StatefulOrchestrator
  -> ScenarioAgent
  -> SimulationAgent
  -> EvidenceBuilderAgent
  -> DiagnosisAgent
  -> VerificationAgent
  -> ReportAgent
```

核心转变：

```text
执行动作分工 -> 灾害评估流程分工
工具调用导向 -> 证据诊断导向
模型结果输出 -> 结论-证据-对象-时段-来源文件链条
```

### 创新点三：证据约束的洪涝灾害诊断机制

本文引入 evidence-grounded flood diagnosis 机制，将 SWMM-CA2D 模拟输出转化为结构化证据表，再由 DiagnosisAgent 基于规则生成诊断 claim，最后由 VerificationAgent 检查每条 claim 是否有 evidence_id 支撑，并计算 unsupported rate。

核心价值：

- 避免 LLM 直接面对海量原始数据。
- 避免自然语言诊断脱离证据。
- 将“是否有证据”变成可计算的指标。

### 创新点四：立体化关系证据网的拓展方向

当前系统已实现对象级证据诊断，即分别识别地表元胞、检查井节点和管段的异常指标。下一步拟进一步构建地表-管网-泵站-排水分区的关系证据网，将成熟给排水工程师的成因追溯思维显式化。

未来关系证据链设想：

```text
降雨强度
  -> 地表积水热点
  -> 附近检查井/雨水口
  -> 节点冒溢
  -> 相连管段充满度
  -> 上下游管段顶托/回流
  -> 泵站运行状态
  -> 排水分区承载与联动关系
```

可写入讨论部分：

> 当前版本完成了 object-level evidence diagnosis，后续可进一步发展 relation-level evidence graph，使 Agent 的诊断过程从“识别异常对象”推进到“沿空间位置与水力拓扑追溯成因”。

### 创新点五：评价与优化创新

本文拟建立面向 Agentic 洪涝诊断工作流的多维评价指标体系，包括任务成功率、工具调用准确率、平均代码生成尝试次数、平均人工干预次数和 unsupported rate 等，用于比较直接 LLM、工具调用型 LLM、传统脚本流程和完整 workflow-stage Agentic 系统之间的差异。

评价目标：

- 证明流程型 Agentic 系统更可靠。
- 证明证据约束机制能降低无证据输出。
- 证明结构化工作流能减少工具调用错误、无效尝试和人工干预。

## 6. 系统组成与 Agent 职责

### 6.1 StatefulOrchestrator

负责工作流状态管理和合法阶段推进，避免跳步、重复执行或将诊断任务错误路由到临时代码生成。

状态链条：

```text
START
  -> SCENARIO_READY
  -> RUN_READY
  -> EVIDENCE_READY
  -> DIAGNOSIS_READY
  -> VERIFIED_READY
```

### 6.2 ScenarioAgent

负责模型项目、降雨事件和情景配置准备，生成 `scenario_request.json`，并将运行状态推进到 `SCENARIO_READY`。

### 6.3 SimulationAgent

负责调用固定 SWMM -> CA2D 耦合模拟管线，生成标准运行目录，包括 SWMM 输出、CA2D 输出和运行摘要。

### 6.4 EvidenceBuilderAgent

负责从 SWMM/CA2D 原始结果中提取结构化证据，生成：

```text
evidence/evidence_table.csv
evidence/evidence_summary.json
```

### 6.5 DiagnosisAgent

负责读取 `evidence_table.csv`，基于 `diagnosis_rules.json` 生成结构化诊断 claim，输出：

```text
diagnosis/diagnosis_claims.json
diagnosis/risk_ranking.csv
```

### 6.6 VerificationAgent

负责核查诊断 claim 是否真的有证据支撑，输出：

```text
verification/verification_report.json
verification/unsupported_rate.txt
```

### 6.7 ReportAgent

负责读取已验证结构化成果，生成面向用户的自然语言报告。当前已增强为包括：

- 运行概况
- 证据与诊断概况
- 主要风险信号
- 完整诊断清单
- 证据核查结果
- 综合判断与使用边界

## 7. 结构化证据体系

### 7.1 evidence_table.csv 的核心含义

`evidence_table.csv` 是将原始模拟结果转化为诊断证据的核心数据结构。每一行代表：

```text
某次运行 + 某个模型对象 + 某个指标 + 指标值 + 时间信息 + 来源文件 + 诊断辅助信息
```

主要字段：

| 字段 | 含义 |
|---|---|
| `evidence_id` | 证据唯一编号 |
| `run_id` | 模拟运行编号 |
| `event_name` | 降雨事件 |
| `scenario_name` | 工程情景 |
| `source_model` | 来源模型 |
| `source_file` | 来源结果文件 |
| `object_type` | 对象类型：node/link/cell |
| `object_id` | 对象编号 |
| `metric_name` | 诊断指标 |
| `value` | 指标值 |
| `unit` | 单位 |
| `time_start` / `time_end` | 指标发生或统计时间 |
| `duration_minutes` | 持续时间 |
| `rank` | 同类指标排序 |
| `threshold` | 诊断阈值 |
| `exceedance_flag` | 是否超过阈值 |

### 7.2 当前证据指标

| 对象 | 指标 | 含义 | 用途 |
|---|---|---|---|
| cell | `max_depth` | 最大地表积水深度 | 识别地表积水热点 |
| cell | `ponding_duration` | 地表积水持续时间 | 识别长时间积水区域 |
| node | `total_flooding_volume` | 节点累计溢流量 | 识别主要冒溢节点 |
| node | `max_flooding_flow` | 节点最大溢流流量 | 节点溢流辅助证据 |
| node | `flooding_duration` | 节点溢流持续时间 | 节点溢流辅助证据 |
| node | `max_node_depth` | 节点最大水深 | 节点状态辅助证据 |
| link | `max_flow` | 管段最大绝对流量 | 管段流量规模辅助证据 |
| link | `max_link_depth` | 管段最大水深 | 管段水力状态辅助证据 |
| link | `max_fullness` | 管段最大充满度 | 识别高负荷/接近满流管段 |
| link | `flow_direction_changes` | 管段流向改变次数 | 识别可能顶托、回流或水力震荡 |

### 7.3 为什么加入充满度

单纯最大流量容易偏向主干管，因为大管径管段本来就应该承担更多流量。相比之下，充满度反映的是管段水深相对于满管深度的比例，更能表达某根管段是否接近自身能力上限。

当前实现：

```text
max_fullness = max(depth_m / full_depth_m)
```

其中 `full_depth_m` 来自 SWMM `[XSECTIONS]` 中的断面几何参数。

### 7.4 为什么加入流向变化

管段流向频繁改变可能提示下游顶托、局部回流、满管流扰动或水力震荡。当前实现以 SWMM 管段定义方向作为基准方向：

```text
正方向 = [CONDUITS] 中 From Node -> To Node
flow_Ls > 0 表示沿定义方向
flow_Ls < 0 表示反向流
接近 0 的流量忽略
```

然后统计每根管段流量符号正负切换次数，生成 `flow_direction_changes`。

## 8. DiagnosisAgent 当前诊断依据

当前 DiagnosisAgent 主要基于 5 类证据进行对象级诊断：

1. **地表积水深度**：`cell + max_depth`
2. **地表积水持续时间**：`cell + ponding_duration`
3. **节点累计溢流量**：`node + total_flooding_volume`
4. **管道最大充满度**：`link + max_fullness`
5. **管道流向变化次数**：`link + flow_direction_changes`

辅助保留证据：

- `link + max_flow`
- `link + max_link_depth`
- `node + max_node_depth`
- `node + max_flooding_flow`
- `node + flooding_duration`

### 当前诊断 claim 类型

| claim_type | 中文含义 | 依据证据 | 当前 possible_cause |
|---|---|---|---|
| `surface_hotspot` | 地表积水热点 | `max_depth` | `local_depression_or_concentrated_overflow` |
| `long_duration_ponding` | 长时间积水区域 | `ponding_duration` | `long_duration_surface_ponding` |
| `major_overflow_node` | 主要冒溢节点 | `total_flooding_volume` | `network_overflow_source` |
| `high_load_link` | 高负荷管段 | `max_fullness`，兜底为 `max_flow` | `possible_network_bottleneck` |
| `unstable_flow_direction_link` | 流向不稳定管段 | `flow_direction_changes` | `possible_backwater_or_hydraulic_oscillation` |

### 当前规则阈值

| 规则 | 当前阈值 | 说明 |
|---|---:|---|
| 地表中等积水 | `max_depth >= 0.3 m` | 待规范校准 |
| 地表高风险积水 | `max_depth >= 0.5 m` | 待规范校准 |
| 地表严重积水 | `max_depth >= 0.75 m` | 待规范校准 |
| 长时间积水 | `ponding_duration >= 60 min` | 待规范校准 |
| 主要溢流节点 | `total_flooding_volume >= 10 m3` | 待规范校准 |
| 高负荷管段 | `max_fullness >= 0.8` | 待规范校准 |
| 严重高负荷管段 | `max_fullness >= 0.95` | 待规范校准 |
| 流向频繁改变 | `flow_direction_changes >= 3` | 待规范校准 |
| 严重流向不稳定 | `flow_direction_changes >= 6` | 待规范校准 |

注意：当前规则主要用于验证机制可行性，后续需要回归城市内涝评价规范、排水工程教材、设计标准和工程经验进行系统校准。

## 9. VerificationAgent 与 unsupported rate

VerificationAgent 的作用是检查每条诊断 claim 是否真的能被 `evidence_table.csv` 支撑。

核查逻辑包括：

1. claim 是否填写了 `evidence_ids`。
2. `evidence_id` 是否能在证据表中找到。
3. claim 类型是否引用了正确的指标类型。
4. claim 对象编号是否与证据对象编号一致。
5. 引用证据值是否为正值。

输出结构：

```text
verification/verification_report.json
verification/unsupported_rate.txt
```

`unsupported_rate` 的意义：

```text
unsupported_rate = unsupported_claims / total_claims
```

它将“无证据结论”从隐藏的自然语言问题变成可计算、可比较的评价指标。

## 11. 方法章节可用文字草稿

### 11.1 总体方法草稿

本文构建了一个面向 SWMM-CA2D 耦合城市内涝模拟的流程型多 Agent 诊断框架。该框架将一次暴雨模拟过程划分为情景准备、耦合模拟、证据构建、灾害诊断、证据核查和报告生成六个阶段。与直接让大语言模型读取原始模拟结果不同，本文首先通过确定性工具将 SWMM 节点、管段和 CA2D 地表元胞输出转化为统一的结构化证据表，再基于诊断规则生成可追溯的诊断 claim，最后对每条 claim 与证据之间的对应关系进行核查。通过这种方式，系统将海量时序结果压缩为 AI 更易读取、工程意义更明确且可核查的证据链。

### 11.2 EvidenceBuilderAgent 草稿

EvidenceBuilderAgent 负责将原始模拟输出转换为面向诊断的结构化证据。其输入包括 SWMM 节点溢流文件、节点状态文件、管段状态文件、CA2D 地表水深文件以及运行摘要文件。该 Agent 按对象类型和指标类型对结果进行分组统计，提取地表最大积水深度、积水持续时间、节点累计溢流量、节点最大溢流流量、管段最大充满度、管段流向变化次数等指标，并为每条证据分配唯一 `evidence_id`。该过程使后续诊断不再直接依赖杂乱的原始结果，而是基于统一的“对象-指标-数值-时间-来源文件”证据结构展开。

### 11.3 DiagnosisAgent 草稿

DiagnosisAgent 负责将结构化证据转化为诊断 claim。当前版本采用规则约束的对象级诊断机制，分别识别地表积水热点、长时间积水区域、主要冒溢节点、高负荷管段和流向不稳定管段。每条诊断 claim 均包含诊断对象、诊断类型、风险等级、结论性语句、可能原因标签、证据编号和规则编号。该设计避免了大语言模型直接生成无约束自然语言结论，使诊断结果可以追溯到具体证据行。

### 11.4 VerificationAgent 草稿

VerificationAgent 负责对诊断 claim 进行证据核查。其核心任务不是生成新的诊断结论，而是检查已有 claim 是否与 `evidence_table.csv` 中的证据行形成有效连接。核查内容包括 evidence_id 是否存在、诊断类型与指标类型是否匹配、对象编号是否一致以及证据值是否有效。未能通过核查的 claim 将被标记为 unsupported，并计入 unsupported rate。该指标可用于衡量 Agentic 诊断系统的无证据输出风险。

### 11.5 ReportAgent 草稿

ReportAgent 负责将已核查的结构化诊断结果转化为面向用户的自然语言报告。当前报告内容包括运行概况、证据与诊断概况、主要风险信号、完整诊断清单、证据核查结果、综合判断和使用边界。与普通摘要式报告不同，ReportAgent 的输出受到 verification 结果约束，报告中的诊断结论均来自 supported 或 partially supported claim，从而保证报告内容可以回溯到具体证据。

## 12. 结果章节可用文字草稿

### 12.1 结构化证据构建结果

在 `songhua_swmm_2d` 模型的两个基线降雨事件中，系统均生成了 318411 条结构化证据。证据覆盖地表元胞、SWMM 节点和 SWMM 管段三类对象，包含地表积水深度、积水持续时间、节点溢流量、节点水深、管段流量、管段水深、管段充满度和管段流向变化等指标。这表明 EvidenceBuilderAgent 能够将大规模 SWMM-CA2D 模拟输出稳定转化为统一证据结构。

### 12.2 诊断 claim 生成结果

在 `rain1` 事件中，DiagnosisAgent 生成 50 条诊断 claim，包括 10 条地表积水热点、10 条长时间积水区域、10 条主要冒溢节点、10 条高负荷管段和 10 条流向不稳定管段。在 `rain4` 事件中，系统生成 40 条诊断 claim，包括地表积水热点、长时间积水区域、主要冒溢节点和高负荷管段各 10 条。由于 `rain4` 下管段流向改变次数未达到当前阈值，因此未生成流向不稳定管段 claim。

### 12.3 证据核查结果

两个已处理事件的 VerificationAgent 均显示 unsupported rate 为 0.0。其中，`rain1` 的 50 条诊断 claim 均为 supported，`rain4` 的 40 条诊断 claim 也均为 supported。这说明当前由规则生成的对象级诊断结论均能够回溯到有效 evidence_id。

注意：该结果只能证明当前规则生成 claim 的证据引用一致性，不能直接证明规则阈值已达到工程最优。规则阈值仍需进一步依据规范、教材和工程经验校准。

## 13. 讨论章节关键点

### 13.1 LLM 与确定性程序的分工

本文的关键不是让 LLM 替代数值模型或后处理脚本，而是让 LLM 工作在认知组织层。确定性程序负责可复现的模拟、统计和核查；LLM 负责自然语言任务理解、多步骤流程组织、证据解释、面向不同用户的表达转换和开放式追问。

可用表达：

> 程序负责“算得准”，LLM 负责“问得懂、调得对、讲得清、追得下去”。

### 13.2 为什么不能直接喂原始数据或图片

直接将海量模拟结果输入 LLM 会带来 token 消耗大、噪声高、关键对象难以定位和证据不可追溯等问题。直接输入积水深度图虽然能展示空间分布，但难以保留时间过程、对象编号、指标值、阈值、排序和来源文件。本文通过 evidence_table、diagnosis_claims 和 verification_report 将模拟结果组织成 AI 可读、低冗余、可核查的数据结构。

### 13.3 当前系统的边界

当前系统主要实现对象级证据诊断，还未完全实现地表积水点与相邻检查井、上下游管段、泵站和排水分区之间的关系级成因追溯。因此，当前 ReportAgent 输出的原因解释应理解为基于结构化模拟证据的工程线索，而不是完整现场定因。

## 15. 摘要初稿骨架

城市排水内涝模拟能够生成高时空分辨率的水力结果，但如何从海量模拟输出中形成可解释、可追溯的工程诊断结论仍是实际应用中的关键问题。本文提出一种面向 SWMM-二维元胞耦合模型的证据约束型 Agentic 诊断框架。该框架将城市内涝分析过程划分为情景准备、耦合模拟、证据构建、灾害诊断、证据核查和报告生成等阶段，通过多 Agent 协同将原始节点、管段和地表元胞时序结果转化为结构化证据表、诊断 claim 和核查报告。系统进一步引入 unsupported rate 作为无证据诊断比例的量化指标，用于约束大语言模型在模拟结果解释中的无依据输出。基于 `songhua_swmm_2d` 大规模 SWMM-CA2D 模型的初步实验表明，该框架能够稳定生成覆盖地表积水、节点溢流、管段充满度和流向变化等指标的结构化证据，并形成可由 evidence_id 追溯的诊断结论。本文为城市内涝模拟结果的智能解释和可信诊断提供了一种流程型 Agentic 方法。

## 16. 引言段落草稿

城市内涝问题具有显著的时空动态性和系统耦合性。基于 SWMM 的一维排水管网模型能够刻画节点、管段和汇水区之间的水力响应，二维元胞或地表淹没模型则能够进一步描述地表积水扩散过程。然而，在实际应用中，模型运行完成并不意味着诊断完成。一次暴雨模拟往往产生大量节点、管段和地表网格时序结果，工程人员需要进一步识别积水热点、冒溢节点、管段高负荷状态和可能的水力异常机制。如何将模拟输出转化为可解释、可追溯、可核查的诊断结论，是城市内涝模拟走向决策支持的关键环节。

近年来，大语言模型和 Agentic 系统为模型交互、工具调用和结果解释提供了新的技术路径。已有研究已经探索了面向 EPANET 给水管网的 Agentic 分析框架，但给水系统与排水内涝系统在对象组成、物理过程和诊断任务上存在明显差异。排水内涝不仅涉及管网内部水力过程，还涉及降雨驱动、检查井冒溢、地表积水扩散和管网-地表耦合关系。因此，直接迁移给水系统 Agentic 框架难以充分满足城市内涝成因分析的需求。

为此，本文提出一种面向 SWMM-CA2D 耦合模型的证据约束型多 Agent 诊断框架。与直接让大语言模型读取海量模拟结果不同，本文首先通过确定性工具将原始结果转化为结构化证据，再由诊断 Agent 生成可追溯 claim，并由核查 Agent 对 claim-evidence 关系进行验证。该框架旨在将大语言模型的自然语言理解和解释能力，与传统程序的可复现计算和规则核查能力结合起来，为城市内涝模拟结果提供更可靠的智能诊断路径。

## 17. 论文贡献表述

本文贡献可概括为：

1. 提出面向 SWMM-CA2D 城市排水内涝耦合模型的 Agentic 诊断对象迁移，将 Agentic 应用从给水管网交互分析扩展到排水-地表淹没耦合诊断。
2. 设计流程型多 Agent 架构，将洪涝灾害评估组织为情景准备、耦合模拟、证据构建、灾害诊断、证据核查和报告生成的状态化工作流。
3. 构建结构化 evidence table，将海量 SWMM/CA2D 输出转化为对象、指标、数值、时段和来源文件可追溯的诊断证据。
4. 建立基于 evidence_id 的诊断 claim 与证据核查机制，并引入 unsupported rate 量化无证据诊断输出。
5. 在对象级证据诊断基础上，提出面向后续深化的地表-节点-管段-泵站-分区关系证据网构想，为工程师式成因追溯提供扩展方向。

## 18. 当前写作风险与需谨慎表述处

1. **规则阈值不能写成最终规范结论**  
   当前阈值是机制验证用，需要后续规范校准。

2. **unsupported rate = 0 不能过度解释**  
   它说明当前 claim 有 evidence_id 支撑，不等于诊断规则已完全正确。

3. **关系证据网目前是拓展方向**  
   当前已实现对象级证据诊断，关系级成因追溯仍需开发。

4. **LLM 贡献不能说成替代程序**  
   应强调 LLM 与确定性程序分工协作。

5. **ReportAgent 当前是证据解释，不是现场定因**  
   需说明缺少 DEM 细节、土地利用、现场巡查、泵站实测状态等外部信息。
